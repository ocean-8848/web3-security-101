# 04 访问控制与权限：谁有权按这个按钮

学习目标：读完本章，你能——

- 列出 6 种常见的访问控制缺陷，并为每种写出修复代码。

前置章节：02 EVM 与 Solidity 安全基础交互实验：storage-proxy-lab.html ｜ 示例合约：examples/02-AccessControl.sol

## 1. 一句话理解

合约的每个状态修改函数都必须回答一个问题：谁可以调用我？如果答案是"任何人"，就必须证明任何人调用都安全。

访问控制（Access Control）：限制特定函数只能由特定地址或角色调用的机制。

🎯 打个比方：合约像一栋写字楼。

- public 函数是大堂的门：谁都能进。

- onlyOwner 函数是机房的门：要刷卡。

- 漏洞 1：机房门忘了装刷卡器（缺少修饰器）。

- 漏洞 2：刷卡器只检查"刷卡的人是不是从总裁办公室出来的"，而不检查刷卡的人是谁（tx.origin）。

- 漏洞 3：大楼刚建好时，第一个走进物业办公室并宣布"我是物业经理"的人，就成了物业经理（未初始化）。

- 漏洞 4：总裁的门卡一直放在前台抽屉里（私钥管理）。

比喻的局限：写字楼可以换锁。合约如果没有升级能力，"锁"一旦装错就永远是错的。

## 2. 威胁模型

 | 

 | 攻击者身份
 | 能力
 | 典型攻击

 | 任意外部地址
 | 调用所有 public / external 函数
 | 调用未保护的 mint、setOwner、initialize

 | 恶意合约
 | 在 owner 交互时插入调用
 | 利用 tx.origin 冒充 owner

 | 被钓鱼的特权用户
 | 签下自己看不懂的交易
 | 前端篡改、盲签（Bybit 2025）

 | 获得私钥的攻击者
 | 完全等同于特权角色
 | 跨链桥验证者私钥泄露（Ronin 2022）

 | 内部人员
 | 合法持有特权
 | 跑路、恶意升级

## 3. 六种常见缺陷

### 3.1 缺少权限检查

// ❌ 漏洞：任何人都能增发
function mint(address to, uint256 amt) external {
    _mint(to, amt);
}
// ✅ 修复
function mint(address to, uint256 amt) external onlyRole(MINTER_ROLE) {
    _mint(to, amt);
}

💡 注意：Solidity 0.5 之前，函数默认可见性是 public。旧合约忘写可见性，就等于把内部函数暴露给所有人。

### 3.2 用 tx.origin 做鉴权

// ❌ 漏洞
require(tx.origin == owner);
// ✅ 修复
require(msg.sender == owner);

攻击路径：owner 调用攻击者的合约（例如领取空投）→ 攻击者合约调用你的合约 → tx.origin 仍是 owner → 检查通过。

### 3.3 未保护的初始化函数

可升级合约和克隆合约用 initialize() 代替构造函数。如果初始化函数没有被调用，或者可以被重复调用，任何人都能成为 owner。

// ❌ 漏洞：任何人都可以调用，且可以重复调用
function initialize(address _owner) external {
    owner = _owner;
}
// ✅ 修复：OpenZeppelin Initializable
function initialize(address _owner) external initializer {
    owner = _owner;
}
// ✅ 同时在实现合约的构造函数中锁死实现合约本身
constructor() { _disableInitializers(); }

### 3.4 任意外部调用 / 任意 delegatecall

// ❌ 漏洞：用户可以让合约以自己的身份调用任何地址
function execute(address target, bytes calldata data) external {
    target.call(data);
}

如果这个合约持有代币授权（allowance），攻击者可以构造 data = transferFrom(受害者, 攻击者, 金额)。如果这里是 delegatecall，攻击者的代码会直接改写本合约存储。

### 3.5 单步所有权转移

// ❌ 风险：输错地址，权限永久丢失
function transferOwnership(address newOwner) external onlyOwner { owner = newOwner; }
// ✅ 修复：两步转移（Ownable2Step）——新 owner 必须主动 acceptOwnership()

### 3.6 签名鉴权写错

用签名代替 msg.sender 鉴权时，ecrecover 对无效签名返回 address(0)。如果被比较的签名者变量未设置（默认 0），检查会通过。签名的完整陷阱见 08 章。

## 4. 防御方法：特权角色设计

### 4.1 最小权限

把一个 owner 拆成多个角色，每个角色只做一件事：

 | 

 | 角色
 | 能做什么
 | 建议持有者
 | 建议延迟

 | UPGRADER
 | 升级实现合约
 | 多签 + 时间锁
 | 48 小时以上（示例）

 | PARAM_ADMIN
 | 调整费率、抵押率
 | 多签 + 时间锁
 | 24 小时（示例）

 | PAUSER
 | 紧急暂停
 | 小型多签或监控机器人
 | 无延迟

 | MINTER
 | 增发
 | 只授予特定合约
 | —

💡 注意：暂停权限要"快"，升级权限要"慢"。暂停只能止损，不能转走资金；升级可以做任何事。

### 4.2 多签 + 时间锁

[图]
flowchart LR
  P["提案者<br/>（多签 3/5）"] -->|"schedule()"| T["时间锁合约<br/>延迟 48h（示例）"]
  T -->|"延迟到期后 execute()"| C["目标合约"]
  M["监控与社区"] -.->|"观察队列中的操作"| T
  G["守护者 Guardian"] -.->|"发现恶意操作时 cancel()"| T
  U["用户"] -.->|"不同意时，在延迟期内退出"| C
[/图]

读图要点：

- 时间锁给用户一个"退出窗口"。恶意升级被公开排队后，用户有时间撤资。

- 守护者可以取消操作，但不能发起操作。权限是不对称的。

- 局限：如果多签的签名人被同时钓鱼（例如前端被篡改），多签只能防"单个私钥被盗"，不能防"所有人看到同一个假界面"。

### 4.3 L2 视角：Mantle 的升级权限

L2 的桥合约持有用户全部跨链资产。谁能升级桥合约，谁就能决定这些资产的去向。根据 L2BEAT 截至 2026 年的页面：

- Mantle 的 MantleSecurityMultisig（6/14）可以无延迟升级 L1 上的桥和输出预言机合约。

- L2BEAT 把"无升级延迟、无退出窗口"标为关键风险。

这不是代码漏洞，而是信任假设：用户相信这 14 个签名人中至少 9 个不会合谋或同时被攻破。细节见 C03 Mantle 专题。

## 5. 账户层权限：TRON 的案例

以太坊的 EOA 只有一把私钥。TRON 账户原生支持多重权限（TRON 官方文档与安全公司公开资料）：

 | 

 | 权限
 | 作用

 | Owner
 | 最高权限，可以修改其他权限，包括增删签名人

 | Active
 | 日常操作：转账、质押、调用合约；可以有多个，每个可以限定允许的操作类型

 | Witness
 | 超级代表（出块节点）相关操作

每个权限有一组地址、每个地址有权重、权限有阈值。权重之和达到阈值，操作才执行。

"多签诈骗"的攻击路径：

[图]
flowchart LR
  A["受害者在假钱包 / 钓鱼页<br/>泄露私钥"] --> B["攻击者修改账户权限<br/>把 Owner 和 Active 改成自己"]
  B --> C["受害者仍能看到余额<br/>但无法转出"]
  C --> D["新的 USDT 继续转入<br/>（转入不需要签名）"]
  D --> E["攻击者择机转走全部资产"]
[/图]

读图要点：

- 攻击者不立即转走资产。账户看起来正常，受害者还会继续往里转钱。

- 这类骗局常见于 OTC 交易：骗子提供一个"有余额但转不出来"的账户私钥，诱导对方支付"手续费"。

- 防御：定期检查账户权限配置；只从官方渠道下载钱包；不要导入别人提供的私钥。

- 对合约开发者的含义：TRON 上"一个地址 = 一把私钥"不成立。收到一个地址时，不能假设它由单一私钥控制。

## 6. 真实案例

### 6.1 Parity 多签钱包（2017 年，以太坊）

- 7 月：钱包合约把未匹配的调用 delegatecall 给库合约。库里的 initWallet 没有保护。攻击者通过钱包调用 initWallet，把自己设为 owner，转走约 153,037 ETH（约 3,000 万美元）。

- 11 月：修复后的新库合约本身没有初始化。一个用户调用库的 initWallet 成为库的 owner，然后调用 kill 自毁库合约。所有依赖它的钱包失去代码逻辑，约 51 万 ETH 被永久冻结。

- 教训：实现合约（库）本身也需要初始化或在构造函数中锁死。

### 6.2 Ronin Bridge（2022 年 3 月）

- 跨链桥需要 9 个验证者中的 5 个签名。攻击者控制了其中 5 把私钥（公开报道称通过社会工程获得），伪造提款，损失约 6.2 亿美元。

- 其中一把签名权来自一个早已不需要、但未撤销的授权。

- 教训：特权清单要定期审计。阈值要和私钥的独立性匹配。

### 6.3 BNB Chain Token Hub（2022 年 10 月）

- 攻击者支付 100 BNB 注册为跨链中继者（Relayer），再利用证明验证缺陷伪造消息，凭空铸造 200 万 BNB。

- 修复硬分叉（Moran）把中继者改为白名单。

- 教训：注册中继者"只要付押金就行"是一个权限决策。详见 C01。

## 7. 审计检查点

-  每个修改状态的外部函数，都有明确的权限检查或"任何人可调用"的安全论证。

-  没有任何地方用 tx.origin 做鉴权。

-  初始化函数有 initializer 修饰；实现合约构造函数调用了 _disableInitializers()。

-  不存在用户可控的任意 call / delegatecall 目标。

-  所有权转移是两步式。

-  特权角色已拆分；升级和参数修改经过时间锁。

-  特权私钥的持有者、存放方式、阈值已文档化，并有撤销流程。

-  部署链的账户模型是否与以太坊一致？（TRON 账户可多权限）
