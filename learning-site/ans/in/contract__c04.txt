## 1. 一句话理解

合约的代码一旦部署就不能修改。项目方能做的只有三件事：换一个新合约、让旧合约指向新代码、或者让旧合约停下来。

合约生命周期（Contract Lifecycle）：一份合约从源码到被弃用的全部阶段。

🎯 打个比方：合约像一块公开刻在广场石碑上的规则。

- 编写 = 起草条文。测试 = 在草稿纸上反复推演。

- 编译 = 把中文条文翻译成石匠能刻的符号。

- 部署 = 石匠把符号刻进石碑，立在广场上。石碑的位置就是合约地址。

- 源码验证 = 在石碑旁边贴一张"原文对照表"，任何人可以核对符号和原文是否一致。

- 调用 = 市民走到石碑前，按规则办事。

- 刻好的字不能改。项目方想改规则，只能另立一块新碑。

可升级合约像换门牌：广场上的"1 号门牌"一直不变，市民总是去 1 号。但管理员可以把门牌从旧石碑上摘下，挂到新石碑上。市民不用改地址，规则却已经换了。

比喻的局限：真实的门牌更换需要施工时间，路人能看见。链上的"换门牌"只需一笔交易。如果没有时间锁，用户可能来不及反应。另外，石碑不收钱；合约部署和调用都要付 Gas。

这个比喻点出了本章的核心矛盾："不可变"带来信任，"可升级"带来修复能力。两者不能同时拿满。

## 2. 业务视角：它解决什么问题

### 2.1 为什么项目方要关心"生命周期"

传统软件可以随时发布补丁。合约不能。合约上线后会遇到三类业务需求：

 | 

 | 业务需求
 | 传统软件怎么做
 | 合约怎么做
 | 代价

 | 修复漏洞
 | 发布补丁，服务器重启
 | 部署新合约，再迁移或升级
 | 迁移成本；升级权限本身是风险

 | 新增功能
 | 发新版本
 | 部署新版本；或通过代理升级
 | 用户和集成方要更新地址，或接受"可被改"的事实

 | 紧急止损
 | 关停服务
 | 调用暂停函数（如果事先写了）
 | 暂停权限也能被滥用

 | 下线产品
 | 关停服务器，迁移数据
 | 合约永远在链上；只能标记弃用、引导迁移
 | 旧合约里的资金和授权仍然存在

 | 让外部信任
 | 公司信誉、合同、监管
 | 公开源码 + 审计 + 限制自己的权限
 | 放弃部分控制权

读表要点：

- 合约没有"关服务器"这个选项。代码一旦上链，只要链还在，任何人都能调用它。

- 修复能力必须在部署前设计进合约。部署后才想起来要暂停，已经来不及。

### 2.2 两种人，两种关心点

- 项目方关心：上线快、成本低、出事能修。

- 用户和投资人关心：项目方不能随便改规则、不能随便动钱。

这两种需求互相拉扯。第 3.6 节讲业界用什么工具在中间取平衡。

💡 注意："合约代码不可变"不等于"合约行为不可变"。合约里如果有 owner 可以改的参数（例如手续费率、黑名单），项目方不升级代码也能改变合约行为。读合约时，先找所有带权限检查的函数。

### 3.2 编写、测试、编译

- 开发者用 Solidity 写源码。

- 开发者在本地链上运行单元测试。

- 开发者在主网分叉（Mainnet Fork）上测试和真实合约的交互。

- 编译器把源码编译成字节码（Bytecode）和 ABI。

主网分叉（Mainnet Fork）：在本地复制一份主网某个区块的状态，用来模拟真实环境。

字节码（Bytecode）：EVM 能执行的机器指令序列。

ABI（Application Binary Interface）：描述合约有哪些函数、参数是什么类型的说明书。前端和钱包靠它编码调用。

编译器输出两段字节码，初学者经常混淆：

 | 

 | 名称
 | 英文
 | 用途
 | 会上链吗

 | 创建码
 | Creation Code / Initcode
 | 部署时运行一次，执行构造函数，然后返回运行时码
 | 只出现在部署交易的数据里

 | 运行时码
 | Runtime Code
 | 合约地址上永久保存的代码，每次调用都执行它
 | 是，存到合约地址

💡 注意：构造函数（Constructor）只在部署时运行一次。运行时码里没有构造函数。所以"部署后再调用构造函数"是不可能的。

测试和审计流程的安全细节（静态分析、模糊测试、不变量测试、形式化验证）见 《安全手册》12 章：审计、测试与开发流程。本章不重复。

### 3.3 部署：地址从哪里来

部署（Deploy）：发送一笔特殊交易，把字节码写到链上的一个新地址。

以太坊系有两种创建合约的操作码：

[图]
flowchart LR
  subgraph C1["CREATE"]
    S1["部署者地址"] --> H1["keccak256<br/>RLP 编码"]
    N1["部署者 nonce"] --> H1
    H1 --> A1["合约地址<br/>取后 20 字节"]
  end
  subgraph C2["CREATE2"]
    F2["工厂合约地址"] --> H2["keccak256"]
    SA["salt 盐值"] --> H2
    IC["keccak256 initcode"] --> H2
    X["固定前缀 0xff"] --> H2
    H2 --> A2["合约地址<br/>取后 20 字节"]
  end

[/图]

读图要点：

- CREATE 的地址由"谁部署"和"这是他的第几笔交易"决定。部署者先发了一笔别的交易，地址就变了。

- CREATE2 的地址由"哪个工厂"、"哪个盐值"、"哪段创建码"决定。三者不变，地址就不变。这个地址可以在部署前算出来。

- 会出错的地方：CREATE2 的创建码包含构造函数参数。参数改一个字节，地址就完全不同。

- 局限：TRON 也支持 CREATE2，但地址前缀规则不同。迁移时要实测，见 《安全手册》12 章第 4 节。

nonce：一个账户已发送交易的计数器。每发一笔交易，nonce 加 1。

盐值（salt）：部署者自选的一个 32 字节数字，用来区分同一工厂部署的不同合约。

CREATE2 的业务用途：

 | 

 | 用途
 | 怎么用
 | 例子

 | 多链同地址
 | 同一工厂、同一 salt、同一创建码，在多条链上得到同一个地址
 | 很多基础设施合约在各链地址相同（业界通用做法）

 | 先给地址，后部署
 | 用户先往算好的地址转账，需要时再部署合约
 | 智能合约钱包的"反事实部署"（见 08 章）

 | 按交易对生成地址
 | 交易对地址由两个代币地址算出，不需要查表
 | Uniswap V2 的交易对工厂（公开源码）

⚠️ 警告：CREATE2 让"同一地址部署不同代码"在某些条件下成为可能（销毁后重部署、工厂代码可变）。以太坊 2024 年 3 月的 Dencun 升级（EIP-6780）限制了 SELFDESTRUCT，但这类攻击的思路仍需了解。不要只因为"地址相同"就信任一个合约。

### 3.4 一个代币从代码到浏览器上可见

下面用示例合约 MinimalToken 走一遍完整流程。

[图]

  participant Dev as 开发者
  participant Solc as 编译器 solc
  participant Wallet as 钱包
  participant Node as RPC 节点
  participant Block as 区块
  participant Scan as 区块浏览器

  Solc-->>Dev: 返回创建码与 ABI

  Wallet->>Node: 广播已签名交易
  Node->>Block: 交易进入内存池，被打包进区块

  Block-->>Node: 回执含新合约地址
  Node-->>Wallet: 返回交易回执
  Scan->>Node: 索引新区块与事件日志
  Scan-->>Dev: 显示合约地址、字节码、代币转账
  Dev->>Scan: 提交源码、编译器版本、优化参数
  Scan->>Solc: 用相同参数重新编译
  Scan->>Scan: 对比字节码，一致则标记已验证
  Scan-->>Dev: 显示源码、读写函数页面

[/图]

读图要点：

- 部署交易的 to 字段为空。节点看到空的 to，就知道这是创建合约。

- 第 7 步的 Transfer(0x0, 部署者, 初始供应) 事件让浏览器知道"这是一个代币，有人收到了它"。没有这个事件，浏览器的代币持有人列表就是空的。

- 第 12–15 步是源码验证。浏览器不信任开发者提交的源码，而是自己重新编译并对比。

- 会出错的地方：编译器版本、优化次数、EVM 版本任一不同，字节码就对不上，验证失败。

### 3.5 示例合约关键片段

完整代码见 examples/02-MinimalToken.sol（约 90 行，Solidity ^0.8.20，已用 solc 0.8.24 编译通过）。下面节选三段（格式略有压缩）：

// 余额就是一个 mapping：代币记在合约的账本里，不在钱包里。
mapping(address => uint256) public balanceOf;

// 事件写入交易日志。浏览器和钱包扫描日志，才知道谁转了多少。
event Transfer(address indexed from, address indexed to, uint256 value);

// 构造函数只在部署时运行一次。from = address(0) 表示"铸造"。
constructor(string memory name_, string memory symbol_, uint256 initialSupply) {
    name = name_;
    symbol = symbol_;
    totalSupply = initialSupply;
    balanceOf[msg.sender] = initialSupply;
    emit Transfer(address(0), msg.sender, initialSupply);
}

// 转账 = 账本里一个数字减少，另一个数字增加，然后发事件。
function _transfer(address from, address to, uint256 value) internal {
    if (to == address(0)) revert ZeroAddress();
    uint256 fromBalance = balanceOf[from];
    if (fromBalance < value) revert InsufficientBalance(from, fromBalance, value);
    unchecked { balanceOf[from] = fromBalance - value; }
    balanceOf[to] += value;
    emit Transfer(from, to, value);
}

逐段说明：

- balanceOf 是一个映射（mapping）。每个地址对应一个数字。"我有 100 个代币"的意思是"这个合约的账本里，我的地址对应 100"。

- Transfer 事件不改变任何余额。它只是一条日志。但钱包、浏览器、交易所的充值系统都靠它发现转账。

- 构造函数把全部初始供应记到部署者名下。这就是"部署者收到代币"的全部原理。

- _transfer 先检查余额，再改账本，最后发事件。如果余额不足，整笔交易回滚，账本不变。

自定义错误（Custom Error）：用 error 关键字声明的错误类型。它比字符串错误信息更省 Gas，前端也能解码出参数。

mapping 在存储里怎样分配槽位？打开 evm-storage-lab.html，输入 balanceOf[某地址]，观察槽位如何由 keccak256 算出。

💡 注意：示例里的 approve 有一个经典竞态问题。如果把授权从 N 直接改成 M，被授权人可以抢先花掉 N，再花掉 M。授权风险见 《安全手册》06 章第 5 节。完整的 ERC-20 讲解见 06 章。

### 3.6 源码验证

源码验证（Source Code Verification）：把源码和编译参数提交给浏览器，浏览器重新编译并确认结果与链上字节码一致。

 | 

 | 平台
 | 覆盖的链
 | 特点

 | Etherscan
 | 以太坊及 Etherscan 系浏览器
 | 用户最常看的入口；验证后显示"Read / Write Contract"页面

 | BscScan
 | BNB Smart Chain
 | Etherscan 系，流程相同

 | Mantlescan / 其他 L2 浏览器
 | Mantle 等 L2
 | 多数沿用 Etherscan 或 Blockscout 的验证流程

 | Tronscan
 | TRON
 | 填写合约地址、主合约名、编译器版本、优化设置，上传源码后比对（TRON 官方文档）

 | Sourcify
 | 多条 EVM 链
 | 开源、去中心化的验证仓库；用编译元数据做"完全匹配"

验证成功后，任何人都可以：

- 阅读源码。

- 在浏览器页面直接调用只读函数（例如 balanceOf）。

- 让审计报告和链上代码一一对应。

⚠️ 警告：未验证源码的合约，用户只能看到字节码。交易所和安全团队通常把"未验证"视为高风险信号。上币尽调的要求见 《安全手册》A05 上币尽调。

### 3.7 升级：代理模式一句话版

代理合约（Proxy）：一个只负责保存数据和资金、把调用转发给"实现合约"的合约。用户永远调用代理的地址。

实现合约（Implementation）：保存业务代码的合约。升级 = 让代理指向一个新的实现合约。

 | 

 | 模式
 | 一句话区别
 | 升级函数在哪里

 | 透明代理（Transparent Proxy）
 | 升级逻辑写在代理里；管理员和普通用户走不同路径
 | 代理（由 ProxyAdmin 合约管理）

 | UUPS（Universal Upgradeable Proxy Standard，ERC-1822）
 | 代理只转发；升级函数写在实现合约里
 | 实现合约

 | 信标代理（Beacon Proxy）
 | 很多代理共同读一个"信标"里的实现地址；改一次信标，全部代理一起升级
 | 信标合约

三种模式的存储布局、初始化、选择器冲突等安全问题，见 《安全手册》09 章：可升级合约与代理。本章只讲"谁拿着钥匙"。

### 3.8 谁拿着升级钥匙

[图]
flowchart LR
  K1["单个私钥<br/>EOA"] -->|"一笔交易立即生效"| P["代理合约<br/>用户资金在这里"]
  K2["多签钱包<br/>例如 3/5"] --> T["时间锁<br/>例如 48 小时"]
  G["DAO 投票"] --> T
  T -->|"等待期结束后执行"| P
  P -.->|"delegatecall"| I["新实现合约"]
  U["用户"] -->|"等待期内可以退出"| P

[/图]

读图要点：

- 最上面一条路：单个私钥可以立即升级。私钥被盗或团队作恶，用户没有反应时间。

- 中间和下面的路：多签降低"一个人说了算"的风险；时间锁给用户留出退出时间。

- 会出错的地方：时间锁只有在用户监控它的时候才有用。如果没人看队列，等待期形同虚设。

- 局限：多签的签名人如果都属于同一家公司，"多签"只是形式上分散。

多签（Multisig）：需要 M 个签名人中的 N 个同意才能执行操作的钱包，例如 3/5。

时间锁（Timelock）：一个合约，它要求操作排队，等待固定时间后才能执行。

### 3.9 暂停与弃用

合约不能删除，但可以停下来。

 | 

 | 手段
 | 做法
 | 例子与提醒

 | 暂停（Pause）
 | 合约内置 paused 开关；暂停后拒绝转账或存款
 | 必须在部署前写进代码

 | 只出不进
 | 暂停存款和借款，保留提款
 | 业界通用做法：让用户能安全离开

 | 弃用转发
 | 旧合约记录新地址，把调用转发到新合约
 | 以太坊上的 USDT（TetherToken）合约有 deprecate 函数，可把调用转到新地址（公开源码）

 | 迁移
 | 部署新合约，用户主动把资产搬过去
 | 用户不搬，旧合约里的资产就一直留在旧合约

 | 自毁
 | selfdestruct
 | 2024 年 3 月 Dencun 升级（EIP-6780）后，只在"同一交易内创建并销毁"时才真正删除代码。不应再依赖它下线合约

💡 注意：弃用之后，用户以前给旧合约的授权仍然有效。如果旧合约后来被发现漏洞，攻击者仍能利用这些授权。项目方弃用合约时，应提醒用户撤销授权。

### 4.3 Solana：默认可升级

这是本章最重要的多链差异。

- 开发者用 Solana CLI 或 Anchor 部署程序。

- 部署者地址自动成为升级权限（Upgrade Authority）。

- 升级权限持有人可以随时替换程序代码。

- 持有人可以把升级权限转给多签。

- 持有人也可以把升级权限设为空。设为空后，程序永久不可变（Solana 官方文档）。

升级权限（Upgrade Authority）：Solana 上有权替换程序代码的那个地址。

🎯 打个比方：以太坊的合约默认是"石碑"，要升级得事先装"门牌"。Solana 的程序默认是"白板"，持笔的人可以擦了重写，除非他把笔扔掉。

比喻的局限：Solana 程序的数据存在独立账户里。擦掉白板上的代码，账户里的数据还在。新代码必须能读懂旧数据。

⚠️ 警告：评估一个 Solana 项目时，第一件事是查"升级权限在谁手里"。如果它在一个普通个人地址上，项目方可以随时换掉全部代码。

## 5. 商业视角：谁付钱，谁赚钱

### 5.1 谁付部署费

部署费由发起部署交易的账户支付，通常是项目方。部署费流向链的出块者和销毁机制（见 02 章）。

部署费的数值示例（示例，不是报价）：

- 示例合约 MinimalToken 开启优化后，运行时码约 1,573 字节（本机 solc 0.8.24 实测）。

- 以太坊对每字节运行时码收取 200 Gas 存储费。1,573 × 200 ≈ 31.5 万 Gas。

- 加上交易基础费 21,000、创建费 32,000、构造函数写存储，整笔部署约 50–60 万 Gas（示例）。

- 如果 Gas 价格是 1 gwei，部署费约 0.0006 ETH。如果 Gas 价格是 20 gwei，部署费约 0.012 ETH（示例）。

为什么不同链的部署成本差很多：

 | 

 | 链
 | 成本由什么决定
 | 为什么通常更便宜或更贵

 | 以太坊主网
 | 字节数 × 200 Gas + 执行 Gas；Gas 价格随区块拥堵变化
 | 区块空间最稀缺，Gas 价格波动最大

 | L2（例如 Mantle）
 | L2 执行费 + 把交易数据发布到 L1 的数据费
 | 执行在 L2 完成；L1 数据费分摊给很多交易

 | BSC
 | 同以太坊的 Gas 规则
 | 验证者数量少，出块快，Gas 价格长期较低（公开资料称）

 | TRON
 | 按能量计费；可以质押 TRX 换能量，也可以燃烧 TRX
 | 项目方质押足够 TRX 后，部署的现金支出可以接近零

参数会变的部分（Gas 价格、基础费）去 eip1559-burn-lab.html 调节观察。在测试网动手部署一次，见 附录 A1。

💡 注意：部署费通常只占项目成本的很小一部分。审计费、漏洞赏金、持续运营的成本远高于部署费。不要用"部署便宜"来判断一条链"开发便宜"。

### 5.2 可升级性对信任的影响

 | 

 | 设计
 | 对用户的含义
 | 对投资人的含义
 | 典型做法

 | 完全不可变
 | 规则永远不变；有漏洞也修不了
 | 项目方无法"挪钱"，但也无法挽救
 | Uniswap V2 / V3 核心合约不可升级（公开资料）

 | 可升级 + 单私钥
 | 项目方随时可以改规则、动资金
 | 信任完全落在团队身上
 | 早期项目常见；尽调中的红旗

 | 可升级 + 多签 + 时间锁
 | 有等待期，用户可以先退出
 | 治理流程透明，可监控
 | 大型 DeFi 协议的常见做法（业界通用做法）

 | 可升级 + DAO 投票 + 时间锁
 | 代币持有人决定升级
 | 治理代币有实际权力
 | Compound、Aave 等协议的治理流程（公开资料）

读表要点：

- 越不可变，用户越不需要信任团队；但出事时也越难救。

- 越容易升级，产品迭代越快；但"升级钥匙"就是整个协议的最大单点风险。

### 5.3 "上架"的门槛

项目要进入交易所、钱包代币列表、数据聚合网站，通常要过几道门槛（业界通用做法）：

- 合约源码已在浏览器验证。

- 至少一份公开审计报告，审计的版本和链上代码一致。

- 权限说明：谁能增发、谁能暂停、谁能升级、有没有时间锁。

- 代币分配和解锁计划（见 13 章）。

交易所怎样逐项检查这些内容，见 《安全手册》A05 上币与合作项目尽调。

💡 注意："审计过"只对审计时的那个版本成立。项目升级后，新实现合约需要新的审计。

 |

 | 没有设计暂停

⚠️ 警告：暂停权限和升级权限是同一类"超级权限"。它们能救用户，也能伤害用户。评估项目时，要同时问两个问题：出事时谁能停下来？谁能保证这个人不会自己作恶？

💡 注意：示例合约 MinimalToken 没有暂停、升级、增发功能。它的规则在部署后完全固定。这对学习是好事，对生产项目通常不够。

 |

## 8. 思考题
