# 出发准备：知行合一、守正出奇、团队意识

学习目标说清审计员的职业底线；画出负责任披露流程；理解团队协同审计为什么能减少漏报。

前置章节无

## 1. 一句话理解

技术决定你能找到多少漏洞；底线决定你能不能留在这个行业。

## 2. 知行合一：学习要有输出，输出要有实践

只读文章不会让你找到漏洞。每学一个漏洞类型，做三件事：

- 用自己的话写一段原理说明（博客、笔记、GitHub）。

- 用 Foundry 写一个能复现的 PoC。

- 在一份真实审计报告或一个历史事件里找到同类漏洞。

[图]
flowchart LR
  R["读：文档 / 报告 / 事件复盘"] --> W["写：用自己的话解释"]
  W --> P["做：Foundry PoC / CTF"]
  P --> S["分享：GitHub / 博客 / 团队分享"]
  S -- "别人的反馈暴露盲区" --> R
[/图]

读图要点

- 这是一个闭环。断在"读"这一步的人最多。

- GitHub 开源文化是这个闭环的加速器：你的 PoC 仓库就是你的简历（见"求职"章）。

- 推荐知识源：慢雾安全团队知识库（slowmist/Knowledge-Base），包含审计报告、事件分析和安全指南。

## 3. 守正出奇：底线与黑客思维

### 3.1 守正：三条底线

- 遵守法律：不攻击未授权的目标。不利用漏洞获利。

- 保守秘密：客户代码和未修复漏洞属于保密信息。审计期间不公开、不交易相关代币。

- 负责任的披露：发现线上漏洞时，先私下通知项目方，给出修复时间，再公开。

FIRST（Forum of Incident Response and Security Teams）道德守则是行业参考。它要求：保护信息、尊重隐私、协调披露、避免伤害。

### 3.2 负责任的披露流程

[图]
sequenceDiagram
  autonumber
  participant R as 研究员
  participant P as 项目方
  participant B as 赏金平台 / 安全团队
  participant U as 用户与社区
  R->>R: 在本地 fork 复现，不碰主网资金
  R->>B: 提交报告（私密渠道）
  B->>P: 验证并转交
  P->>P: 评估、暂停合约或修复
  P-->>R: 确认严重性与奖励
  P->>U: 发布修复公告
  R->>U: 约定时间后公开技术细节
[/图]

读图要点

- 第 1 步最关键：在本地 fork 上复现。在主网上"试一下"本身就可能构成攻击。

- 如果项目方没有联系方式，可以通过赏金平台、安全公司或 SEAL 911 这类白帽应急组织转交。

- 风险点：如果漏洞正在被利用，时间比流程重要。此时要并行联系项目方和安全团队（见 3.6 应急分析）。

### 3.3 出奇：黑客思维

开发者问"这个功能能不能用"。审计员问"这个功能能不能被滥用"。黑客思维有四个习惯：

 |  | 习惯 | 问题模板 | 例子

 | 反向思维 | 如果我是攻击者，我最想改哪个变量？ | 价格、份额、权限、时间戳

 | 边界思维 | 输入为 0、1、最大值、自己时会怎样？ | 转账给自己、借 0 元、第一个存款人

 | 顺序思维 | 如果我改变调用顺序、在回调里再调用一次会怎样？ | 重入、抢跑、闪电贷

 | 组合思维 | 如果我同时使用另一个协议会怎样？ | 用 AMM 价格操纵借贷协议的预言机

🎯 打个比方：开发者像设计门锁的工程师，他测试"钥匙能不能开门"。审计员像开锁师傅，他测试"不用钥匙能不能开门"——撬、拆铰链、从窗户进。

## 4. 团队意识：为什么审计要多人协同

一个人的知识面有限。研究显示，不同审计员找到的漏洞重合度不高。团队审计用两种方式提高覆盖率：

- 协同审计流（技术手段）：例如慢雾的 MistPunk 审计工作台。它把检查项、批注、发现集中在一个平台，并把经验沉淀为检查清单。

- 审计工作流（管理手段）：交叉审计、内部复核、报告审核。每个发现至少两人确认。

- Hacking Time 文化：团队成员随时分享新思路和新攻击手法，对齐团队能力。

[图]
flowchart LR
  K["项目启动范围 / 文档 / 威胁模型"] --> A["审计员 A按模块审"]
  K --> B["审计员 B按业务流程审"]
  A --> X["交叉复核互换模块"]
  B --> X
  X --> Q["内部评审定级 / 去重 / PoC"]
  Q --> RP["初版报告"] --> FX["项目方修复"] --> RV["修复复查"] --> FR["终版报告"]
[/图]

读图要点

- A 和 B 用两个不同视角审同一份代码：模块视角找局部错误，流程视角找跨合约错误。

- 修复复查经常发现"修复引入的新漏洞"。不能省略。

- 局限：协同不能代替个人能力。团队里每个人都要能独立完成一轮完整审计。
