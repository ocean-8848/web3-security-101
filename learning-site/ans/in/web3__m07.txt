## 1. 一句话理解

Web3 前端不保管用户数据，也不保管私钥。它的工作是：读链上状态、构造交易、请钱包签名、追踪交易直到确认。

打个比方Web2 前端像餐厅服务员：你点菜，他把单子交给后厨，后厨（服务器）替你做决定。

Web3 前端像一张填好的支票：前端帮你把金额、收款人写好，但签字必须你亲手在钱包里签。签完以后，支票交给银行（区块链）处理，前端只能在旁边告诉你“银行处理到哪一步了”。

## 2. 四方关系

读图要点

- 数据流读操作前端直接走 RPC；写操作必须经过钱包签名。前端永远拿不到私钥。
- 关键EIP-1193 是钱包暴露给网页的统一接口（window.ethereum.request）。wagmi/viem 封装了它。
- 出错点用户钱包连在主网，DApp 需要 Base 链。前端必须检测 chainId 并请求切换网络（wallet_switchEthereumChain）。
- 风险前端本身是攻击面：DNS 劫持或依赖包投毒可以把“授权”交易的 spender 换成攻击者地址。2023 年 Ledger Connect Kit 的 npm 包就被投毒。

## 3. 用 viem 读写合约

TYPESCRIPTimport { createPublicClient, createWalletClient, custom, http, parseUnits } from 'viem'
import { base } from 'viem/chains'

const pub = createPublicClient({ chain: base, transport: http() })
const wallet = createWalletClient({ chain: base, transport: custom(window.ethereum) })

// 1. 连接钱包，拿到地址
const [account] = await wallet.requestAddresses()

// 2. 读：查询余额（不需要签名，不花 Gas）
const bal = await pub.readContract({ address: USDC, abi: erc20Abi, functionName: 'balanceOf', args: [account] })

// 3. 先模拟，再写：模拟失败就不弹钱包，避免用户白付 Gas
const { request } = await pub.simulateContract({
  account, address: USDC, abi: erc20Abi, functionName: 'transfer',
  args: [to, parseUnits('25', 6)],       // USDC 精度是 6，不是 18
})
const hash = await wallet.writeContract(request)

// 4. 等待回执，再更新 UI
const receipt = await pub.waitForTransactionReceipt({ hash, confirmations: 1 })

注意金额永远用 bigint 和代币的 decimals 处理。JavaScript 的 number 只有 53 位精度，0.1 + 0.2 !== 0.3，会导致金额错误。

## 4. 签名：交易签名 vs 消息签名

 |  | 类型 | 方法 | 上链吗 | 用途 | 风险
 | 交易签名 | eth_sendTransaction | 是，花 Gas | 转账、调用合约 | 用户能在钱包看到明确的转账金额
 | 个人消息 | personal_sign | 否 | 登录（Sign-In with Ethereum） | 低
 | 结构化数据 | eth_signTypedData_v4（EIP-712） | 否，但可被他人提交上链 | Permit 授权、链下订单 | 高：一个 Permit 签名就能授权别人转走代币

警告“签名不花钱”不等于“签名没风险”。钓鱼网站最常用的手法是诱导用户签 Permit / Permit2 消息。签名后，攻击者在链上提交它，转走代币，用户钱包里甚至没有出现过一笔交易。前端应该把 EIP-712 消息的关键字段（spender、amount、deadline）翻译成人话展示。

## 5. 交易状态机：前端最难的部分

一笔交易从点击按钮到最终确定，要经过很多状态。很多 DApp 只处理“成功”和“失败”，导致用户看到转圈圈就重复点击。

前端视角的交易状态机点击图放大 ⤢
图加载中…
读图要点

- 关键拒签（错误码 4001）不是错误，是用户的正常选择。前端应该安静地回到可操作状态，不要弹红色报错。
- 出错点用户在钱包里点“加速”，交易 hash 会变。如果前端只盯着旧 hash，会永远显示“处理中”。viem 的 waitForTransactionReceipt 会处理替换。
- 出错点回执 status=0 表示交易上链了但执行失败（Revert）。Gas 已扣。前端要解析 revert 原因并告诉用户。
- 局限前端关闭后，状态机就停了。长时间的交易（例如跨链）需要后端或索引服务持续追踪。

## 6. 前端安全清单

 |  | 检查项 | 为什么
 | 锁定依赖版本，审查 lockfile 变化 | 防止 npm 包投毒
 | 设置严格的 CSP 和 SRI | 防止注入脚本替换交易参数
 | 授权额度默认等于本次金额，不默认无限 | 降低授权被滥用时的损失
 | 展示交易模拟结果（资产变化） | 让用户在签名前看到“将转出什么”
 | 地址显示校验和格式，并完整对比 | 防止地址投毒（前后几位相同的假地址）
 | 所有金额用 bigint 和 decimals 计算 | 防止精度错误
