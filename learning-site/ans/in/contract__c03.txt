## 1. 一句话理解

EVM 是一台全世界节点同时运行、结果必须一致、每一步都要付费的计算器。合约是写进这台计算器的程序。

以太坊虚拟机（EVM, Ethereum Virtual Machine）：执行合约字节码的虚拟机。每个以太坊节点都运行一份 EVM。同一笔交易在所有节点上得到同一个结果。

🎯 打个比方：EVM 像一个公证处里的标准化流水线。

- 你递交一张申请单（交易）。申请单写明要找哪个窗口（合约地址）、办哪项业务（函数）、附带哪些材料（参数）。

- 流水线上的每个工位只做一个固定动作：取一个数、加一下、存进档案柜。每个动作都有明码标价（Gas）。

- 你预付一笔"最多花这么多"的手续费（Gas 上限）。如果钱花完时业务还没办完，流水线撤销全部动作，手续费不退。

- 全国每个公证处都按同一本手册重做一遍你的业务。结果不一致的公证处会被其他人发现。

- 档案柜（存储）里的东西永久保存，所以往柜子里放东西最贵。草稿纸（内存）用完就扔，所以便宜。

比喻的局限：真实公证处可以查外部档案、打电话核实。EVM 不能主动访问互联网，也不能主动定时执行。它只处理别人递进来的申请单。链下数据要靠预言机写进来（见 10 章）。

本章是"原理入门"。每一种机制背后的安全陷阱，统一链接到《智能合约安全学习手册》02 章，这里不展开。

## 3. 技术视角：它如何实现

### 3.1 从 Solidity 到字节码到操作码

开发者写 Solidity。EVM 不认识 Solidity，只认识字节码。

- 开发者用 Solidity 编写合约。

- 编译器 solc 把源码编译成字节码。

- 部署交易把字节码写到链上的一个新地址。

- 用户调用合约。EVM 逐条读取字节码，执行对应的操作码。

字节码（Bytecode）：合约编译后的一串十六进制字节，是链上实际保存的程序。
操作码（Opcode）：EVM 的一条基本指令，占 1 个字节。例如 0x01 是 ADD，0x55 是 SSTORE。

[图]
flowchart LR
  A["Solidity 源码<br/>count = count + 1;"] -->|"solc 编译"| B["字节码<br/>0x6080604052..."]
  B -->|"反汇编"| C["操作码序列<br/>PUSH1 · SLOAD · ADD · SSTORE"]
  C -->|"EVM 逐条执行"| D["状态变化<br/>slot 0：5 → 6"]
  C -->|"每条扣 Gas"| E["Gas 账单<br/>SSTORE 占大头"]

[/图]

读图要点：

- 一行 Solidity 会展开成几条到几十条操作码。Gas 按操作码收费，不按代码行数收费。

- 链上只保存字节码。源码要靠区块浏览器的"源码验证"才能公开对照（见 04 章）。

- 局限：反汇编出来的操作码难以阅读。研究者通常依赖已验证的源码和 ABI。

count = count + 1; 大致对应下面几条操作码（简化示意，省略了编译器生成的辅助指令）：

PUSH1 0x00   // 把槽位号 0 压入栈
SLOAD        // 从存储 slot 0 读出 count，压入栈
PUSH1 0x01   // 把常数 1 压入栈
ADD          // 弹出两个数，相加，结果压回栈
PUSH1 0x00   // 再次压入槽位号 0
SSTORE       // 把结果写回存储 slot 0

### 3.3 四个数据区：栈、内存、存储、calldata

EVM 执行时，数据放在四个不同的地方。它们的寿命和价格差别很大。

- 栈（Stack）：EVM 做计算的工作台。最多 1,024 层，每层 32 字节。只能操作栈顶附近的元素。

- 内存（Memory）：一次调用内的临时字节数组。调用结束就清空。

- 存储（Storage）：每个合约永久保存的键值表。键和值都是 32 字节。

- 调用数据（Calldata）：调用者传进来的只读输入字节。

- 瞬态存储（Transient Storage，EIP-1153，2024 年 3 月 Cancun 升级）：一笔交易内有效、交易结束自动清零的存储，常用于重入锁。

### 3.4 存储槽布局

存储槽（Storage Slot）：存储里一个 32 字节的位置，用 0、1、2…… 编号。

编译器按固定规则给状态变量分配槽位：

- 普通变量按声明顺序，从 slot 0 开始。

- 如果相邻的小变量合计不超过 32 字节，编译器把它们打包进同一个槽。

- mapping 本身占一个槽 p，这个槽里不放数据。元素 m[key] 放在 keccak256(key . p)。这里的 . 表示把 key 和 p 各补齐到 32 字节后首尾相接。

- 动态数组占一个槽 p，里面存数组长度。元素 a[i] 放在 keccak256(p) + i。

哈希函数 keccak256：把任意长度的输入变成 32 字节输出的函数。输入改一位，输出完全不同。

下面是一个小合约（示例，仅演示布局）：

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Shop {
    uint256 public totalSales;   // slot 0：独占 32 字节
    address public owner;        // slot 1：20 字节
    bool    public paused;       // slot 1：1 字节，和 owner 打包
    uint64  public openedAt;     // slot 1：8 字节，20+1+8 = 29 ≤ 32，继续打包
    mapping(address => uint256) public balances; // slot 2：只占位
    uint256[] public orders;     // slot 3：存数组长度
}

 | 

 | 数据
 | 槽位
 | 怎么算
 | 结果（用 Foundry cast 计算）

 | totalSales
 | 0
 | 顺序第一个
 | 0x00

 | owner + paused + openedAt
 | 1
 | 三者共 29 字节，打包
 | 0x01

 | balances 本身
 | 2
 | 占位，槽内为空
 | 0x02

 | balances[0x1111…1111]

读表要点：

- 打包能省 Gas：读一个槽就拿到三个变量。代价是改其中一个时要先读出整个槽，再拼回去。

- mapping 的元素散落在 2²⁵⁶ 的巨大空间里。哈希让不同 key 几乎不可能撞到同一个槽。

- 局限：mapping 不记录"有哪些 key"。合约无法遍历 mapping。想列出所有持币人，要靠事件（3.5 节）。

去 evm-storage-lab.html 输入你自己的变量和 mapping key，观察槽位如何分配。

⚠️ 警告：可升级合约如果改变变量顺序，新代码会读错旧数据。这是代理合约最常见的事故类型，详见 安全手册 09 章 · 存储冲突。

### 3.5 事件与日志

事件（Event）：合约在执行中发出的一条记录，写进交易收据（Receipt），供链外程序读取。
日志（Log）：事件在 EVM 里的底层形式，由 LOG0–LOG4 操作码生成。

一条日志由三部分组成：

 | 

 | 字段
 | 内容
 | 用途

 | address
 | 发出事件的合约地址
 | 区分"哪个代币"

 | topics
 | 最多 4 个，每个 32 字节。topic0 = 事件签名的哈希
 | 可按 topic 快速筛选

 | data
 | 其余参数，ABI 编码
 | 存放不需要筛选的数值

ERC-20 的 Transfer 事件这样定义：

event Transfer(address indexed from, address indexed to, uint256 value);

一次 Transfer 产生的日志：

 | 

 | 位置
 | 值
 | 说明

 | topic0
 | 0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef
 | keccak256("Transfer(address,address,uint256)")

 | topic1
 | from 地址，左侧补 0 到 32 字节
 | 带 indexed，可筛选

 | topic2
 | to 地址，左侧补 0 到 32 字节
 | 带 indexed，可筛选

 | data
 | value，32 字节
 | 不带 indexed，放在 data

为什么链外系统依赖事件：

- 合约读不回日志。日志只给链外看，所以它比存储便宜得多。

- 节点支持按"合约地址 + topic"过滤日志（eth_getLogs）。索引器不需要逐个读存储槽。

- 存储只记录"现在是多少"，事件记录"发生过什么"。账单、历史、K 线都需要后者。

💡 注意：如果交易回滚，它发出的日志也一起作废。只读"成功交易"的日志。

### 3.6 ABI 与函数选择器

应用二进制接口（ABI, Application Binary Interface）：规定"函数名和参数怎样编码成字节"的标准。钱包按 ABI 拼 calldata，合约按 ABI 解析 calldata。
函数选择器（Function Selector）：函数签名哈希的前 4 字节，calldata 的开头。合约靠它决定执行哪个函数。

下面拼一笔 ERC-20 转账：向 0x1111…1111 转 1,000,000 个最小单位（示例：USDT 有 6 位小数，即 1 USDT）。

- 写出规范签名：transfer(address,uint256)。不带空格、不带参数名。

- 计算哈希：keccak256("transfer(address,uint256)")，结果开头为 a9059cbb…。

- 取前 4 字节：选择器 = 0xa9059cbb。

- 编码第 1 个参数：地址左侧补 0 到 32 字节。

- 编码第 2 个参数：1,000,000 = 0xf4240，左侧补 0 到 32 字节。

- 按顺序拼接：4 + 32 + 32 = 68 字节。

a9059cbb                                                          ← 选择器
0000000000000000000000001111111111111111111111111111111111111111  ← to
00000000000000000000000000000000000000000000000000000000000f4240  ← amount = 1,000,000

这段数据就是交易的 data 字段，也就是被调用合约看到的 calldata。可用 cast calldata "transfer(address,uint256)" <to> 1000000 验证。

💡 注意：选择器只有 4 字节。不同函数签名有可能算出同一个选择器。安全影响见 安全手册 02 章 · 第 4 节 和 09 章 · 选择器冲突。

拿到一段陌生 calldata 时，研究者的第一步是查前 4 字节对应哪个函数。这个技能在 16 章 和 tx-decoder-lab.html 中练习。

### 3.7 三种调用：call / delegatecall / staticcall

合约 A 调用合约 B 时，有三种方式。三者的区别在于"用谁的存储""调用者是谁""能不能写"。

- call 是"去别人的窗口办事"。delegatecall 是"借别人的规程，在自己的档案柜上办事"。

- 代理合约（Proxy）用 delegatecall 实现升级：代理保管数据，实现合约提供逻辑。概览见 04 章。

- 局限：本节只讲区别。delegatecall 的存储冲突、低级 call 不自动回滚、重入等陷阱，见 安全手册 02 章 · 2.3 节 和 09 章。

## 4. 多链对照：以太坊 / BNB Chain / Polygon / Mantle / TRON 有什么不同

### 4.1 EVM 兼容链

以下数据截至 2026 年 10 月公开资料（来源类型：各链官方文档、官方博客、L2BEAT）。

预编译合约（Precompiled Contract）：放在固定低位地址、用节点原生代码实现的"内置函数"，例如 0x01 的签名恢复 ecrecover。它比用操作码实现便宜得多。

读表要点：

- "兼容 EVM"保证字节码能跑，但不保证 Gas 账单一样。同一笔 transfer 在不同链上消耗的 Gas 单位接近，单价和计价币完全不同。

- L2 多出一项 L1 数据费：L2 要把交易数据发布到以太坊，这部分成本转嫁给用户。Mantle 的 eth_estimateGas 返回值已包含 L1 和 L2 两部分（公开文档）。

- 公开资料称，Mantle 在 2025 年 9 月接入 OP Succinct 的 ZK 有效性证明，并在 2026 年 4 月 Arsia 升级中把数据可用性改为只使用以太坊。细节见 X04 Mantle 和 09 章。

- 出块时间不同，会让"按区块数计时"的合约在不同链上行为不同。安全影响见 安全手册 02 章 · 第 4 节第 7 条。

### 4.2 TRON 的 TVM：长得像 EVM，计价方式不同

TRON 虚拟机（TVM, TRON Virtual Machine）：TRON 的合约执行环境，大部分操作码与 EVM 相同，Solidity 合约可以迁移过去。

读表要点：

- TRON 把"计算"变成可以提前质押、出租的资源。这催生了能量租赁市场，见 X03 TRON。

- 从以太坊迁移到 TRON 时，地址处理、依赖 GASPRICE 或 block.difficulty 的逻辑都要重新检查。

- 比特币、Solana、XRPL 不使用 EVM 式的执行模型。它们的账户和执行方式在 05 章 讲解。

## 5. 商业视角：谁付钱，谁赚钱

### 5.1 Gas 让"计算"变成一种商品

在 EVM 上，每一次加法、每一个存储槽都有价格。区块空间是一种有限的商品。

 | 

 | 角色
 | 付出什么
 | 得到什么

 | 用户
 | Gas 费
 | 合约执行结果

 | 验证者 / 出块者
 | 硬件、质押资本
 | 小费、MEV（见 11 章）

 | 以太坊协议
 | 无
 | 基础费被销毁，减少 ETH 供应（见 13 章）

 | L2 运营方（例如 Mantle）
 | 向以太坊付数据费
 | 向用户收 L2 执行费 + L1 数据费，差额是运营收入

 | TRON 能量出租方
 | 质押的 TRX
 | 出租能量的租金

公链卖的是"可验证计算"。Gas 单价越高、需求越旺，链的收入越多；但用户越少用。这是每条链都在平衡的生意。

### 5.2 存储昂贵带来的设计取舍

下面用示例数字感受差距（示例：Gas 单价 1 gwei；1 gwei = 10⁻⁹ ETH）：

 | 

 | 做法
 | Gas（约）
 | 费用（示例）

 | 把 1 KB 数据写进 32 个新存储槽
 | 32 × 22,100 ≈ 707,000
 | 约 0.000707 ETH

 | 把 1 KB 数据放进一个事件的 data
 | 375 + 8 × 1,024 ≈ 8,600
 | 约 0.0000086 ETH

 | 只在链上存一个 32 字节哈希，原文放链下
 | 约 22,100
 | 约 0.000022 ETH

由此产生三种业界通用做法：

- 事件代替存储：合约自己不需要再读的数据（转账历史、订单记录）只发事件。

- 链下存储 + 链上哈希：NFT 图片放在 IPFS 或 Arweave，链上只存元数据地址或哈希。

- 打包变量：把多个小字段塞进一个槽，减少 SSTORE 次数。

💡 注意：省 Gas 有代价。数据放链下，就要信任链下存储的可用性。只发事件，合约本身就无法据此做判断。项目研究时，要看清"哪些数据真的在链上"。
