# 09 可升级合约与代理：维修门的两面

学习目标：读完本章，你能——

- 画出透明代理、UUPS、信标代理的调用关系，说出各自的权限位置。

前置章节：02 EVM 与 Solidity 安全基础、04 访问控制与权限交互实验：storage-proxy-lab.html ｜ 示例合约：examples/07-ProxyStorage.sol

## 1. 一句话理解

代理合约保存数据和资金，实现合约提供代码。升级 = 换掉代理指向的实现。谁能换实现，谁就拥有全部资金。

代理合约（Proxy）：把所有调用通过 delegatecall 转发给实现合约的合约。

🎯 打个比方：代理合约是一个保险柜，实现合约是保险柜的操作手册。

- 柜员每次都按手册操作柜子（delegatecall：用手册，改柜子）。

- 升级 = 换一本新手册。

- 如果新手册把"第 3 格放现金"改成了"第 3 格放钥匙"，柜员会把现金当钥匙用（存储冲突）。

- 如果新手册的第一页写着"第一个读到这页的人是柜子主人"，而没人先读过它（未初始化），路人就能成为主人。

- 如果有人偷换了手册（升级权限被盗），柜子里的东西就归他了。

比喻的局限：真实保险柜换手册需要时间。如果没有时间锁，链上换实现只需一笔交易。

## 2. 三种代理模式

[图]

  subgraph T["透明代理 Transparent"]
    U1["用户"] --> P1["Proxy<br/>升级逻辑在代理里<br/>admin 调用不转发"]
    P1 -. delegatecall .-> I1["Implementation"]
    A1["ProxyAdmin"] --> P1
  end
  subgraph U["UUPS"]
    U2["用户"] --> P2["Proxy<br/>只做转发"]
    P2 -. delegatecall .-> I2["Implementation<br/>含 upgradeTo()"]
  end
  subgraph B["信标 Beacon"]
    U3["用户"] --> P3a["Proxy A"]
    U3 --> P3b["Proxy B"]
    P3a --> BC["Beacon<br/>保存实现地址"]
    P3b --> BC
    P3a -. delegatecall .-> I3["Implementation"]
    P3b -. delegatecall .-> I3
  end
[/图]

读图要点：

- 透明代理：升级函数在代理里。管理员调用代理时不转发，避免和实现合约函数冲突。

- UUPS：升级函数在实现合约里。如果新实现忘了包含 upgradeTo，合约就再也不能升级。

- 信标代理：一次升级影响所有代理。适合大量相同合约（例如每个用户一个金库）。

- 局限：三种模式都依赖 delegatecall，都有存储冲突风险。

 | 

 | 模式
 | 升级权限在哪
 | 主要风险

 | 透明代理
 | 代理的 admin 槽
 | admin 私钥

 | UUPS
 | 实现合约的 _authorizeUpgrade
 | 新实现遗漏升级函数；实现合约未初始化

 | 信标
 | 信标合约的 owner
 | 一次升级影响全部实例

 | 钻石（EIP-2535）
 | diamondCut 的权限
 | 多个 facet 共享存储，冲突面最大

## 3. 三类代理漏洞

### 3.1 存储冲突

类型 A：代理自己的变量和实现的变量撞槽。

// ❌ 朴素代理：把 implementation 放在 slot 0
contract NaiveProxy {
    address implementation;   // slot 0
    fallback() external payable { /* delegatecall implementation */ }
}
contract Impl {
    address owner;            // slot 0 —— 写 owner 就是写 implementation
}

修复：使用 EIP-1967 定义的固定伪随机槽位存放实现地址和管理员地址。

类型 B：升级前后的布局不一致。

 | 

 | V1
 | V2（❌ 在前面插入 uint256 feeBps）
 | V2（✅ 末尾追加）

 | slot 0: owner
 | slot 0: feeBps ← 读到的是旧 owner 地址，被当作一个巨大的整数
 | slot 0: owner

 | slot 1: totalDeposits
 | slot 1: owner ← 读到的是旧 totalDeposits 的低 20 字节
 | slot 1: totalDeposits

 | slot 2: balances
 | slot 2: totalDeposits ← 读到映射占位槽，恒为 0
 | slot 2: balances

 | slot 3: initialized
 | slot 3: balances ← 映射基址改变，所有余额"消失"
 | slot 3: initialized + paused（打包）

💡 注意：如果插入的是一个 bool，它会和后面的 address owner 打包进同一个槽，错位方式完全不同（owner 的字节被平移 1 字节）。不要靠肉眼数槽位，用 forge inspect 或 solc 的 storageLayout 输出确认。

修复规则：

- 只在末尾追加变量。

- 不删除、不重排、不改类型。

- 父合约预留 uint256[50] __gap;，或使用 ERC-7201 命名空间存储（OpenZeppelin 5.x）。

- 用工具比对新旧布局（例如 OpenZeppelin Upgrades 插件的 validateUpgrade、forge inspect ... storage-layout）。

去 storage-proxy-lab.html 选择"在前面插入变量"，观察哪个槽被错误解释。

### 3.2 初始化缺失

 | 

 | 情况
 | 后果
 | 修复

 | 部署代理后没有在同一笔交易里调用 initialize
 | 攻击者抢跑调用，成为 owner
 | 部署与初始化原子化（构造函数传入初始化 calldata）

 | initialize 可以重复调用
 | 任何人重置 owner
 | initializer 修饰器

 | 实现合约本身没有初始化
 | 攻击者成为实现合约的 owner；如果实现有 delegatecall 或自毁逻辑，可以破坏所有代理
 | 实现合约构造函数调用 _disableInitializers()

 | V2 新增的初始化逻辑用了 initializer
 | 已初始化过，V2 初始化永远不能执行
 | 使用 reinitializer(2)

💡 注意：2021 年 9 月，OpenZeppelin 披露其 UUPS 实现（4.1.0–4.3.1）存在问题：未初始化的实现合约可被任何人接管，并通过升级函数中的 delegatecall 执行 selfdestruct，使所有指向它的代理失效。修复版本为 4.3.2（OpenZeppelin 安全公告）。这和 2017 年 Parity 第二次事故是同一类问题。

### 3.3 选择器冲突

代理自己的函数和实现的函数如果有相同的 4 字节选择器，调用会被代理截获，不会转发。透明代理通过"管理员不转发、其他人只转发"来避免这个问题。钻石代理需要在 diamondCut 时检查冲突。

## 4. 案例：Nomad Bridge（2022 年 8 月）

- Nomad 在一次升级中调用初始化函数，把"可信消息根"设成了 0x00（公开复盘）。

- 合约逻辑中，未经证明的消息默认对应的根也是 0x00。于是任何消息都被视为"已证明"。

- 第一个攻击者成功后，其他人只需复制他的交易、替换收款地址，就能提款。数百个地址参与哄抢，损失约 1.9 亿美元。

- 教训：

- 升级时的初始化参数和代码一样需要审计。

- "零值"不能有业务含义。默认值和合法值必须可区分。

- 升级后要跑回归测试，覆盖"未授权消息必须被拒绝"这一条。

### 4.1 对照案例：Compound 提案 62（2021 年 9 月）

升级后的奖励逻辑有误，部分用户可超额领取 COMP（最坏情况约 28 万枚，约 8,000 万美元）。协议没有可以停止 COMP 分发的紧急开关，任何修复都要走约 7 天的治理流程（The Block 报道）。教训：时间锁挡住恶意升级，也挡住了紧急修复。暂停权和升级权要分开设计。见 C00 4.8 节。

## 5. 链视角：谁能升级"链本身"

可升级的不只是 DeFi 合约。

 | 

 | 链
 | 可升级的关键组件
 | 由谁升级（截至 2026 年公开资料）

 | BNB Chain
 | 系统合约（跨链、质押、治理）和共识规则
 | 硬分叉。2022 年 Token Hub 事故后，Moran 硬分叉修复了验证缺陷并把中继者改为白名单（C01）

 | TRON
 | 网络参数和 TVM 功能开关（如 EIP 兼容操作码）
 | 超级代表投票通过提案（C02）

 | Mantle
 | L1 上的桥、输出预言机、门户合约
 | L2BEAT 页面：MantleSecurityMultisig（6/14）可无延迟升级；MantleEngineeringMultisig（3/7）可暂停提款（C03）

⚠️ 警告：在 L2 上部署的协议，其安全上限是 L2 本身的升级权限。如果 L2 的桥可以被无延迟升级，协议再安全，资产也可能在 L1 端被转走。

## 6. 安全升级流程

- 编写新实现。只追加变量。

- 用工具比对存储布局，输出差异报告。

- 在主网分叉环境中执行升级，跑全部回归测试和不变量测试。

- 审计新实现和升级交易本身（包括初始化参数）。

- 通过时间锁排队。公开升级内容。

- 在延迟期内，监控和社区复核。

- 执行升级。立刻跑部署后验证脚本（读关键变量、做小额端到端操作）。

- 保留回滚方案：如果新实现有问题，能否升级回旧实现？旧实现与新布局是否兼容？

## 7. 审计检查点

-  代理使用 EIP-1967 槽位；没有自定义变量放在低位槽。

-  新旧实现存储布局已用工具比对。

-  实现合约构造函数调用 _disableInitializers()。

-  代理部署与初始化在同一笔交易完成。

-  UUPS 新实现包含升级函数，且权限正确。

-  升级权限经过多签和时间锁。

-  初始化参数中没有"零值具有业务含义"的情况。

-  对部署所在 L2 的升级信任假设做了披露。
