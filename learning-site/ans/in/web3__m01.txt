## 1. 一句话理解

区块链 = 用哈希串起来的区块 + 让陌生人对“下一个区块”达成一致的共识规则。

打个比方想象一本多人共享的流水账，每一页的页脚写着“上一页内容的指纹”。如果有人偷偷改了第 5 页，第 5 页的指纹就变了，第 6 页页脚的记录就对不上，后面每一页都对不上。

要让篡改不被发现，他必须重写第 5 页之后的所有页，而且要比全网所有诚实记账人写得更快。这就是 PoW 的安全来源。

## 2. 三个密码学积木

### 2.1 哈希函数

哈希函数（Hash Function）把任意长度的输入变成固定长度的输出。比特币和以太坊都依赖它的三个性质：

 |  | 性质 | 含义 | 在区块链中的作用
 | 确定性 | 同样的输入永远得到同样的输出 | 任何节点都能独立验证区块
 | 雪崩效应 | 输入改 1 位，输出约一半位改变 | 改动无法“微调”隐藏
 | 单向性 | 从输出无法反推输入 | PoW 只能靠暴力尝试 nonce

### 2.2 默克尔树

默克尔树（Merkle Tree）把一个区块里的所有交易两两哈希，最后得到一个根哈希（Merkle Root）。区块头只存这个根。

读图要点

- 数据流要证明 Tx3 在区块里，只需提供 H(Tx4) 和 H(1+2) 两个哈希（虚线框）。验证者自己算出根，和区块头对比。
- 关键轻节点（例如手机钱包）只下载区块头，靠默克尔证明验证交易。这叫 SPV。
- 局限默克尔证明只能证明“交易存在”，不能证明“交易不存在”。证明不存在需要排序树或其他结构。

### 2.3 数字签名

比特币和以太坊使用椭圆曲线签名 ECDSA（曲线 secp256k1）。私钥签名，公钥验证。任何人都能验证签名，但只有私钥持有人能生成签名。以太坊的地址是公钥 Keccak-256 哈希的后 20 字节。

## 3. 共识：谁来写下一个区块

 |  | 维度 | 工作量证明 PoW（比特币） | 权益证明 PoS（以太坊）
 | 谁出块 | 最先算出合格哈希的矿工 | 被随机选中的验证者（质押 32 ETH）
 | 攻击成本 | 控制 > 50% 算力 | 控制 > 1/3 质押可阻止最终性；> 2/3 可最终确定错误链
 | 惩罚 | 浪费电费 | 罚没（Slashing）质押的 ETH
 | 最终性 | 概率性：确认数越多越安全 | 经济最终性：约 2 个 epoch（约 12.8 分钟）
 | 出块间隔 | 约 10 分钟 | 12 秒（一个 slot）

PoS 的最终性在 M05 有交互实验。本章先看 PoW 的核心：挖矿就是不停改 nonce，直到区块哈希满足难度要求。

## 4. 两种账本模型：UTXO 与账户

UTXO 模型 vs 账户模型点击图放大 ⤢
图加载中…
读图要点

- 数据流UTXO：每笔交易消费旧“硬币”，产出新“硬币”。余额 = 你所有未花费输出之和。
- 数据流账户：链上直接存余额。每个账户有 nonce，nonce 每笔交易加 1。
- 出错点账户模型的 nonce 必须连续。如果 nonce 7 卡住，nonce 8、9 都会卡住。这是钱包后端最常见的故障。见 M03。
- 局限UTXO 天然并行、隐私更好；账户模型更适合智能合约。

## 5. 交易生命周期和链重组

一笔以太坊交易的状态点击图放大 ⤢
图加载中…
读图要点

- 关键“已打包”不是终点。链重组（Reorg）会把交易退回内存池，甚至让它消失。
- 出错点如果后端在“已打包”时就给用户入账，重组后就会出现“链上没收到，账本已入账”。
- 风险攻击者利用重组做双花：先在交易所充值并提走其他币，再用私下挖的更长链抹掉充值交易。

为什么交易所要等 N 个确认？因为攻击者重写 N 个区块的成功率随 N 指数下降。下面的实验用中本聪白皮书第 11 节的公式计算这个概率。

## 6. Go 后端：区块索引器

几乎所有 Web3 后端（钱包、交易所、浏览器、数据平台）都需要一个索引器（Indexer）：它扫描区块，把关心的事件写进数据库。Go 是这个领域的主流语言：go-ethereum（Geth）本身就是 Go 写的，ethclient 可以直接复用。

图加载中…
读图要点

- 数据流数据从 RPC 进入，经过“父哈希校验”这一道门。只有链连续时才解析和入库。
- 出错点最常见的三个故障：RPC 节点落后或返回不一致数据；漏块（扫描跳号）；重组未回退。
- 关键入库 ≠ 通知业务。只有确认数达到阈值，Confirmer 才发出 deposit.confirmed 事件。
- 局限单 RPC 节点是单点。生产环境至少接入 2 家节点服务，并交叉校验区块哈希。

核心循环的 Go 代码（简化版，省略错误重试）：

GOfunc (ix *Indexer) Run(ctx context.Context) error {
    next := ix.store.LastHeight() + 1
    for {
        head, err := ix.client.BlockNumber(ctx)
        if err != nil { return err }
        if next > head { time.Sleep(2 * time.Second); continue }

        blk, err := ix.client.BlockByNumber(ctx, big.NewInt(int64(next)))
        if err != nil { return err }

        // 1. 检查父哈希。不一致说明发生了重组。
        if prev := ix.store.HashAt(next - 1); prev != (common.Hash{}) && blk.ParentHash() != prev {
            next = ix.rollback(ctx, next-1) // 回退到共同祖先，返回下一个要扫的高度
            continue
        }

        // 2. 在一个数据库事务里写入区块和事件，保证幂等。
        if err := ix.store.SaveBlock(ctx, blk, ix.parseTransfers(blk)); err != nil { return err }

        // 3. 把 head - N 之前的事件标记为已确认，并发出消息。
        ix.confirmUpTo(ctx, head-ix.confirmations)
        next++
    }
}

深入一点幂等（Idempotency）：同一个区块被处理两次，结果必须和处理一次一样。做法：用 (tx_hash, log_index) 做唯一键；入账时用 INSERT ... ON CONFLICT DO NOTHING。

回退：从当前高度往回找，直到库里的区块哈希等于链上同高度的区块哈希。删除（或标记作废）之后的所有记录。如果被删的记录已经通知过业务，要发出“撤销”事件。

## 7. 故障与边界

 |  | 故障 | 现象 | 根因 | 防护
 | 重组未处理 | 用户余额多出来，链上没有 | 只看区块高度，不比对父哈希 | 父哈希校验 + 确认数阈值
 | 漏块 | 某些充值永远不到账 | 并发扫块时跳过了失败的高度 | 按高度顺序推进；定时全量对账
 | RPC 数据不一致 | 同一高度两次请求结果不同 | 负载均衡后面的节点进度不同 | 固定节点会话；交叉校验
 | 重复入账 | 一笔充值入账两次 | 重启后重新扫描，缺少唯一键 | (tx_hash, log_index) 唯一约束
 | 事件解码错误 | 金额差 10^12 倍 | 代币精度（decimals）按 18 处理，但 USDT 是 6 | 从合约读 decimals 并缓存

## 术语表
 |  | 术语 | 英文 | 定义
 | 哈希函数 | Hash Function | 把任意输入映射为固定长度输出的单向函数
 | 默克尔树 | Merkle Tree | 两两哈希构成的树，根哈希代表全部叶子
 | 工作量证明 | PoW, Proof of Work | 通过消耗算力竞争出块权的共识
 | 权益证明 | PoS, Proof of Stake | 通过质押资产获得出块和投票权的共识
 | UTXO | Unspent Transaction Output | 未花费的交易输出，比特币的记账单位
 | Nonce（账户） | Account Nonce | 账户已发送交易的计数，保证交易顺序和不可重放
 | 链重组 | Reorg | 节点切换到另一条更长或更重的链，部分区块被孤立
 | 确认数 | Confirmations | 交易所在区块之后又产生的区块数 + 1
 | 索引器 | Indexer | 扫描链上数据并写入可查询数据库的服务
 | 幂等 | Idempotency | 同一操作执行多次，结果与执行一次相同
