## 1. 一句话理解

EVM 是一台单线程的栈式计算机。每个合约有自己的代码和存储；合约之间靠"消息调用"通信；每次调用都可能把控制权交给别人。

以太坊虚拟机（EVM, Ethereum Virtual Machine）：执行合约字节码的虚拟机。BNB Chain 和 Mantle 直接使用 EVM；TRON 使用兼容 EVM 的 TVM（差异见 C02）。

🎯 打个比方：EVM 像一个只有一个窗口的政务大厅。

- 每个合约是一个科室。科室有自己的档案柜（storage）和办事规程（code）。

- 科室 A 要找科室 B 办事，就派人带着材料（calldata）去 B 的窗口（call）。B 处理完再回来。

- delegatecall 是另一种方式：A 把 B 的规程手册借过来，在 A 自己的档案柜上按 B 的规程操作。如果 B 的手册写着"把第 0 号抽屉清空"，被清空的是 A 的第 0 号抽屉。

比喻的局限：真实的大厅里，你离开窗口后就不能插队回来。EVM 里，科室 B 办事中途可以反过来再找 A，此时 A 的上一件事还没办完。这就是重入。

### 2.3 三种调用方式

[图]
sequenceDiagram
  autonumber
  participant U as 用户 EOA

  A->>B: delegatecall B.bar()

[/图]

读图要点：

- call：执行 B 的代码，修改 B 的存储。最常见。

- delegatecall：执行 B 的代码，修改 A 的存储，msg.sender 和 msg.value 保持不变。代理合约（Proxy）和库合约依赖它。

- staticcall：只读调用。view 函数被外部调用时使用。

- 局限：低级 call 失败时不会自动回滚调用者，只返回 false。忘记检查返回值是 06 章 的主题。

去 storage-proxy-lab.html 的"call vs delegatecall"小节，逐步观察四个变量的变化。

## 3. 存储布局：漏洞的藏身处

### 3.1 槽位规则

存储（Storage）：每个合约持有的一个巨大键值表，键和值都是 32 字节。键叫"槽位"（slot）。

图 · Layout 合约的槽位分配新增图解

[图]
flowchart TB
  O["owner：20 字节"] --> S0["slot 0<br/>owner + paused"]
  P["paused：1 字节"] --> S0
  F["fee：12 字节"] -->|"20+1+12 = 33 > 32<br/>放不下"| S1["slot 1：fee"]
  T["total：uint256"] --> S2["slot 2：total"]
  B["bal：mapping"] --> S3["slot 3：本身为空"]
  S3 -->|"keccak256(abi.encode(k, p))"| H["bal 元素在哈希位置"]
  C["constant / immutable"] -->|"不占槽"| N["写进代码"]
[/图]

读图要点：

- 数据流：状态变量按声明顺序从 slot 0 开始依次分配。
- 关键：能否打包只看当前槽剩余空间放不放得下。
- 局限：mapping 的槽位本身是空的，元素散落在哈希算出的位置。
- 风险：变量顺序一变，后面所有槽位都会错位，这是升级漏洞的根源。

- 状态变量按声明顺序从 slot 0 开始分配。

- 如果相邻变量合计不超过 32 字节，编译器把它们打包进同一个槽。

- mapping(k => v) 本身占一个槽 p（内容为空）。元素 m[k] 位于 keccak256(abi.encode(k, p))。

- 动态数组占一个槽 p，存长度。元素 a[i] 位于 keccak256(p) + i。

- 常量（constant）和不可变量（immutable）不占存储槽。

contract Layout {
    address owner;        // slot 0：20 字节
    bool    paused;       // slot 0：1 字节，与 owner 打包
    uint96  fee;          // slot 1：12 字节，slot 0 已放不下（20+1+12 = 33 > 32）
    uint256 total;        // slot 2
    mapping(address => uint256) bal; // slot 3（内容在哈希位置）
}

💡 注意：fee 放不进 slot 0，所以它从 slot 1 开始，total 在 slot 2。打包规则按"剩余空间能否放下"判断。如果把 fee 改成 uint88（11 字节），三个变量正好 32 字节，全部挤进 slot 0。

## 5. Gas、回滚与错误处理

- 每条指令消耗 gas。gas 用完，当前调用帧回滚。

- require(cond, "msg") 和自定义错误 revert Err() 回滚当前调用，并向上冒泡。

- 低级 call 失败不冒泡，只返回 (false, returndata)。

- try/catch 只能捕获外部调用的失败，不能捕获本合约内部的失败。

- 外部调用最多转发 63/64 的剩余 gas（EIP-150）。被调用方耗尽 gas 时，调用方还有 1/64 可以收尾。

图 · 不同失败方式如何传播新增图解

[图]
flowchart TB
  E["调用中出错"] --> Q{"哪种失败？"}
  Q -->|"require / revert"| R1["回滚当前调用"]
  R1 --> R1b["向上冒泡给调用方"]
  Q -->|"低级 call 失败"| R2["不冒泡"]
  R2 --> R2b["只返回 false 和 returndata"]
  R2b --> K["调用方必须自己检查"]
  Q -->|"gas 用完"| R3["当前调用帧回滚"]
  R3 --> R3b["调用方还剩 1/64 gas 收尾"]
  Q -->|"想用 try/catch"| T["只能捕获外部调用失败"]
[/图]

读图要点：

- 数据流：require 和自定义错误会一路向上冒泡，整条调用链一起回滚。
- 出错点：低级 call 失败时外层照常往下执行，除非你检查返回值。
- 局限：try/catch 抓不到本合约内部的失败。
- 关键：EIP-150 只转发 63/64 的 gas，所以调用方总能留一点 gas 收尾。

⚠️ 警告：transfer() 和 send() 只转发 2300 gas。它们曾被当作防重入手段。gas 价格调整（例如 EIP-1884、EIP-2929）后，这种写法会让接收方是合约钱包时转账失败。现在的推荐做法是：用 call 转账，并用 CEI 或重入锁防重入（03 章）。

## 6. 编译器与版本

 | 

 | 版本区间
 | 关键变化
 | 安全含义

 | < 0.8.0
 | 算术默认不检查溢出
 | 必须使用 SafeMath

 | ≥ 0.8.0
 | 算术默认检查，溢出回滚
 | unchecked 块内仍会回绕

 | ≥ 0.8.24
 | 支持 transient 存储（EIP-1153 的 TSTORE/TLOAD）
 | 可以实现低成本重入锁；跨链部署要确认目标链支持（TRON 需相应硬分叉开关，见 C02）

💡 注意：编译器本身也会有 bug。2023 年 7 月，Vyper 0.2.15、0.2.16、0.3.0 的 @nonreentrant 锁实现错误，导致多个 Curve 池被重入，损失约 7,000 万美元（项目方与安全公司公开复盘）。锁定编译器版本，并关注编译器的已知 bug 列表。
