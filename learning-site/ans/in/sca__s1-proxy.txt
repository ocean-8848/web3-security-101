# 代理与可升级合约：换引擎不换车壳

学习目标画出透明代理、UUPS、信标、钻石、最小代理五种模式；识别存储冲突、未初始化实现、选择器冲突三类升级漏洞。

前置章节1.2（delegatecall）、1.3（ERC-1167、ERC-1967）

交互实验存储布局冲突检查器

## 1. 一句话理解

代理合约保存状态和资金，并把所有调用 delegatecall 给实现合约。升级 = 把实现合约地址换掉。

🎯 打个比方：代理合约是一辆车的车壳和油箱（地址、余额、存储）。实现合约是发动机（代码）。升级就是换发动机。风险在于：新发动机的油管接口位置如果和旧的不一样（存储布局不同），油就会灌进错误的管子里。

## 2. 代理的工作原理

[图]
sequenceDiagram
  participant U as 用户
  participant P as Proxy（存储 + 资金）
  participant I as Implementation V1
  participant I2 as Implementation V2
  U->>P: deposit(100)
  P->>P: fallback()：读取实现地址（ERC-1967 槽）
  P->>I: delegatecall(deposit(100))
  I-->>P: 在 Proxy 的存储上执行，写 balances
  Note over P,I2: 管理员调用 upgradeTo(V2)
  U->>P: deposit(100)
  P->>I2: delegatecall(deposit(100))
  I2-->>P: 仍然在同一块存储上执行
[/图]

读图要点

- 状态永远在 Proxy 里。V1 和 V2 必须对"哪个变量在哪个槽"达成一致。

- 实现合约的 constructor 只修改实现合约自己的存储，代理看不到。所以代理模式用 initialize() 代替构造函数。

- 风险点：升级权限是整个系统的"总钥匙"。谁能升级，谁就能拿走全部资金。

## 3. 五种代理模式

 |  | 模式 | 升级逻辑在哪 | 优点 | 典型风险

 | 透明代理 Transparent | Proxy（由 ProxyAdmin 合约管理） | 管理员调用与用户调用分开，无选择器冲突 | 每次调用多一次管理员判断，Gas 稍高；ProxyAdmin 私钥风险

 | UUPS（ERC-1822） | 实现合约（upgradeToAndCall） | 代理更轻，Gas 低 | 新版本忘记继承升级函数 → 永远不能再升级；_authorizeUpgrade 没加权限 → 任何人可升级；实现合约未初始化 → 被人接管（2021 年 OpenZeppelin UUPS 漏洞：攻击者可初始化实现合约并 delegatecall 到 selfdestruct）

 | 信标 Beacon | Beacon 合约保存实现地址 | 一次升级，所有代理同时生效 | Beacon 被控 = 所有代理被控

 | 钻石 Diamond（ERC-2535） | 按函数选择器路由到多个 facet | 突破 24KB 合约大小限制，模块化 | facet 之间存储冲突；选择器管理复杂，审计难度高

 | 最小代理 Clone（ERC-1167） | 不可升级，只是便宜地复制 | 部署成本极低 | 克隆没有在同一交易里初始化 → 被抢先初始化

## 4. 三类升级漏洞

### 4.1 存储冲突

Solidity 按声明顺序从 slot 0 开始分配状态变量。小于 32 字节的变量会打包进同一个槽。V2 只能在末尾追加变量，不能插入、删除、改类型、改顺序。

图 · 插入变量导致槽位错位新增图解

[图]
flowchart LR
  subgraph V1["V1 布局"]
    a1["slot 0：变量 a"]
    b1["slot 1：变量 b"]
  end
  subgraph BAD["V2 在中间插入"]
    a2["slot 0：变量 a"]
    c2["slot 1：新变量 c<br/>读到 b 的旧值"]
    b2["slot 2：变量 b<br/>读到空值"]
  end
  subgraph GOOD["V2 只在末尾追加"]
    a3["slot 0：变量 a"]
    b3["slot 1：变量 b"]
    c3["slot 2：新变量 c"]
  end
  V1 -->|"插入"| BAD
  V1 -->|"追加"| GOOD
[/图]

读图要点
- 关键：状态一直留在代理里，升级只换代码，不搬数据。
- 出错点：在中间插入变量，后面所有变量都会读到错误槽位的数据。
- 数据流：V2 只能在末尾追加，可用 __gap 或 ERC-7201 命名空间预留空间。
- 局限：删除、改类型、改顺序同样会错位，升级前用工具比较两版布局。

工程实践：

- 基础合约预留 uint256[50] private __gap;，新增变量时减少 gap 长度。

- 使用 ERC-7201 命名空间存储：@custom:storage-location erc7201:example.main，每个模块的结构体放在独立的哈希槽（OpenZeppelin 5.x 采用）。

- 用 forge inspect Contract storageLayout 或 OpenZeppelin Upgrades 插件比较两个版本的布局。

### 4.2 初始化漏洞

contract VaultV1 is Initializable, UUPSUpgradeable, OwnableUpgradeable {
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() { _disableInitializers(); }   // ✅ 锁死实现合约本身

    function initialize(address admin) external initializer { // ✅ 只能调用一次
        __Ownable_init(admin);
        __UUPSUpgradeable_init();
    }

    function _authorizeUpgrade(address) internal override onlyOwner {} // ✅ 升级必须有权限
}

图 · 抢先初始化攻击新增图解

[图]
sequenceDiagram
  participant D as 部署者
  participant P as 代理
  participant A as 攻击者
  D->>P: 交易 1 部署代理
  A->>P: 抢先调用 initialize()
  P-->>A: 攻击者成为 owner
  D->>P: 交易 2 调用 initialize()
  P-->>D: 失败 已经初始化过
  Note over D,P: 修复 部署与 initialize 放在同一交易
  Note over P,A: 实现合约本身用 _disableInitializers() 锁死
[/图]

读图要点
- 出错点：部署和初始化分成两笔交易，中间就留出了抢跑窗口。
- 风险：攻击者成为 owner 后，可以控制升级，拿走全部资金。
- 关键：initializer 只能调一次，谁先调谁就是 owner。

- 部署代理和调用 initialize 不在同一笔交易 → 攻击者抢先初始化，成为 owner。

- 继承链里的父合约 __X_init 没调用 → 某些变量保持默认值。

- V2 新增 reinitializer(2) 函数，但没有权限控制。

### 4.3 函数选择器冲突

函数选择器 = 函数签名 Keccak-256 的前 4 字节。不同签名可能产生相同选择器。例如 burn(uint256) 和 collate_propagate_storage(bytes16) 的选择器都是 0x42966c68（3.1 章 LAB 可验证）。如果代理有一个管理函数与实现合约的业务函数选择器相同，用户调用会被代理"截胡"。透明代理通过"管理员只能调管理函数"解决这个问题；编译器会拒绝同一合约内的冲突，但不能检查代理与实现之间的冲突。

## 5. 审计检查清单

- 谁能升级？是多签 + 时间锁，还是单个 EOA？

- 实现合约是否调用了 _disableInitializers()？

- 代理部署与初始化是否原子（同一交易）？

- V1 → V2 存储布局是否只追加？父合约顺序是否改变？

- UUPS 新版本是否保留升级函数和权限检查？

- 实现合约里是否有 selfdestruct 或任意 delegatecall？

- 实现合约是否使用了 immutable？升级后这些值会随实现变化。
