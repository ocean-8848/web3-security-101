
# A06 运营与密钥安全：代码之外的战场

学习目标：读完本章，你能——

- 说出近年最大损失的四个链下根因:私钥与签名、前端与供应链、部署流水线、社会工程。

- 评估一套密钥管理方案(多签 / MPC / HSM)的真实安全,而不只是看阈值。

- 把五起链下事故(Bybit、WazirX、Radiant、DMM、BadgerDAO、Ledger)映射到可检查的评估项。

前置章节：A03 交易所合约与钱包、08 签名安全交互实验：incident-explorer.html

## 1. 一句话理解

合约审计覆盖的是"代码会不会出错"。但近年最大的损失,几乎都不在代码里:私钥被骗走、前端被调包、部署流水线被污染、员工被钓鱼。评估不覆盖链下,等于只锁了保险柜,没锁保险柜所在的房间。

🎯 打个比方：合约是保险柜,运营安全是保险柜所在的整栋楼。

- 保险柜(合约)用最好的钢材(审计过)。

- 但保安被收买(私钥泄露)、门禁系统被改(前端注入)、送货通道被人掉包(供应链)、保洁被冒充(社会工程),保险柜再硬也没用。

比喻的局限:楼里的问题可以装监控、派人巡逻。链上资产一旦被转走,没有保险公司理赔,没有警察追回(多数情况下)。

## 3. 私钥与签名评估

### 3.1 密钥管理方案对比

 | 

 | 方案
 | 原理
 | 优点
 | 要评估的风险

 | 单签 EOA
 | 一把私钥
 | 简单
 | 单点;绝不用于金库

 | 多签合约(Safe)
 | M-of-N 链上合约
 | 成熟、透明
 | 签名流程(见下);module / guard 扩展点;升级

 | MPC
 | 私钥分片,多方协同签名
 | 无完整私钥落地;链上看是单签
 | 分片的分发与存储;实现方的可信度;签名审批流程

 | HSM
 | 硬件内保管并签名
 | 私钥不出硬件
 | 访问控制;谁能让 HSM 签名;物理安全

💡 注意:MPC 和 HSM 解决的是"私钥不以完整形态落地",没有解决"谁来授权签名、签的是什么"。Bybit、WazirX、Radiant 的问题都不是私钥被直接偷走,而是合法的签名人被骗着授权了恶意交易。所以签名流程评估(A03 第 4 节)对任何方案都适用。

### 3.2 评估清单

-  签名人独立性:不同的人、组织、地点、设备?多少把钥匙实际由同一方控制?

-  签名终端:专机专用?隔离?能否收文件、装软件、上网?(Radiant:开发者终端中木马)

-  交易展示与独立解码:签名人看到的和签的是否一致?是否用独立工具解码核对?(Bybit、WazirX)

-  高危操作审批:升级、换签名人、delegatecall、transferOwnership 是否额外审批 + 带外确认?

-  时间锁与限额:大额转出时间锁?单位时间提币上限与告警?

-  密钥轮换与撤销:离职 / 换岗后的密钥与权限是否及时撤销?(Ledger:前员工 npm 权限未撤销)

## 4. 前端与供应链评估

合约再安全,用户是通过前端交互的。前端被攻破,用户直接授权给攻击者。

### 4.1 评估清单

-  前端托管:谁能改线上代码?CDN / Cloudflare / 托管平台的访问控制与密钥?(BadgerDAO:Cloudflare 账户的 API key 被用于注入脚本)

-  依赖锁定:npm / 第三方库是否锁定到具体版本?是否通过第三方 CDN 镜像加载?(Ledger Connect Kit:1.1.5–1.1.7 被投毒)

-  子资源完整性:关键外部脚本是否用 SRI(Subresource Integrity)校验?

-  DNS 与域名:域名注册商账户的保护?DNS 记录的变更审批?(Curve 等曾遭 DNS 劫持)

-  钱包交互透明:前端请求用户签名 / 授权时,是否清晰展示对象、金额、是否无限授权?

-  监控:前端代码完整性监控?异常授权激增告警?

### 4.2 案例:两种供应链攻击

 | 

 | 事故
 | 入口
 | 恶意行为
 | 评估项

 | BadgerDAO(2021-12,约 1.2 亿美元)
 | Cloudflare 账户 API key 被获取
 | 注入脚本,诱导用户给攻击者无限授权;500 个钱包中招
 | 前端托管访问控制;无限授权展示

 | Ledger Connect Kit(2023-12,约 60 万美元)
 | 前员工 npm 账户被钓鱼,权限未撤销
 | 发布恶意版本,运行 Drainer 转走资产
 | 依赖锁定;离职权限撤销;SRI

## 5. 部署与运维评估

-  部署用脚本,脚本经评审;部署与初始化原子化(见 09)。

-  部署后验证:源码验证、关键参数读取核对、权限移交确认。

-  CI / CD 密钥:部署私钥、API key 不进代码库;用密钥管理服务;最小权限。

-  升级流程:经时间锁;公开;部署后跑验证脚本;保留回滚方案。

-  变更管理:任何链上变更有审批、有记录、可追溯。

## 6. 社会工程评估

技术防御再强,人仍是最软的一环。近年多起大案的入口都是社会工程:

 | 

 | 事故
 | 手法

 | DMM Bitcoin(2024,约 3.05 亿美元)
 | 冒充招聘者在 LinkedIn 接触钱包服务商 Ginco 员工,诱其运行"入职测试"代码,终端被控,进而操纵交易请求

 | Radiant(2024,约 5,000 万美元)
 | 冒充前承包商在 Telegram 发送伪装成报告的恶意文件,开发者终端中木马,并转发给同事扩散

评估要点:

-  团队是否有反社会工程的培训与意识,尤其是开发和签名人员?

-  是否有"不在签名 / 部署终端上打开外部文件、链接、运行外部代码"的硬性规定?

-  招聘、承包、合作流程中的身份核验?

-  高危操作是否要求多人、带外确认,使单个人被攻破不足以造成损失?

⚠️ 警告:对合作 / 上币项目做尽调时(见 A05),对方的运营安全薄弱会通过深度合作传导给交易所。合作越深(共享金库、共同部署),越要把对方的运营安全纳入评估。

## 7. 运营安全在评估中的位置

 | 

 | 评估对象
 | 运营安全的权重

 | 交易所自有合约与钱包(A03)
 | 最高:签名流程与密钥管理是第一重点

 | 自研 DeFi 协议(A04)
 | 高:部署、升级权限、前端、监控

 | 上币 / 合作尽调(A05)
 | 中高:通过问卷了解;深度合作时提升

运营安全的许多项超出"合约安全评估"的传统边界,但损失就发生在这里。评估报告即使不能亲自验证所有链下环节,也要明确列出需要企业安全团队跟进的项,而不是当作"不在范围内"略过。

 | 

 | 术语

## 9. 思考题

- 一个团队用 MPC 管理私钥,说"没有完整私钥,所以很安全"。参照 Bybit 和 Radiant,指出这个说法的盲区。

- 你的前端通过第三方 CDN 加载一个钱包连接库。列出至少 3 个降低供应链风险的措施。

- 为什么说"假招聘"对加密团队特别有效?评估团队运营安全时,你会问哪些问题来发现这类风险?
