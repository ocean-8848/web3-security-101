## 章节正文

# 12 审计、测试与开发流程：把安全写进流水线

学习目标：读完本章，你能——

- 画出合约从设计到上线后监控的 8 个安全关口。

- 用 Foundry 写出一个模糊测试和一个不变量测试。

- 为部署到 BNB Chain、TRON、Mantle 的合约分别准备链特定的测试项。

前置章节：01–11 章交互实验：chain-porting-lab.html、incident-explorer.html

## 1. 一句话理解

审计不是安全的起点，也不是终点。审计是流水线上的一个关口；它之前要有设计和测试，它之后要有监控和应急。

🎯 打个比方：合约开发像造一架飞机。

- 设计阶段：画图纸，并写出"任何情况下机翼不能断"（不变量）。

- 制造阶段：每个零件出厂前都测（单元测试），并把零件放进风洞里用各种极端风向吹（模糊测试）。

- 适航认证：外部机构检查（审计）。认证不检查每一颗螺丝，只抽查关键系统。

- 投入运营：飞行中有黑匣子和地面雷达（监控），出了问题有应急程序（暂停、响应）。

比喻的局限：飞机出厂后可以召回维修。不可升级的合约出厂后就不能改了，所以前面的关口必须更严。

## 2. 八个安全关口

[图]

  A["① 规格与威胁模型"] --> B["② 安全编码规范"]
  B --> C["③ 静态分析"]
  C --> D["④ 单元 + 模糊 + 不变量测试"]
  D --> E["⑤ 形式化验证（关键模块）"]
  E --> F["⑥ 外部审计 / 竞赛"]
  F --> G["⑦ 安全部署与权限移交"]
  G --> H["⑧ 监控、漏洞赏金、应急响应"]
  H -. "发现问题" .-> A
[/图]

读图要点：

- 越靠左的关口，修复成本越低。规格阶段发现的问题，只需要改文档。

- ③④⑤ 是自动化关口，每次提交代码都应运行。

- ⑥ 审计发现的问题，应该反向补充到 ④ 的测试中，防止回归。

- 局限：所有关口都依赖"你想到了要检查什么"。经济攻击和跨协议组合风险，常常需要专门的经济审计。

## 3. 各关口要做什么

### 3.1 规格与威胁模型

- 写出每个函数的前置条件、后置条件。

- 写出系统不变量（01 章 4.2 节）。

- 列出外部依赖：代币、预言机、DEX、跨链桥、目标链特性。

- 列出特权角色和每个角色的最大破坏力。

### 3.2 静态分析

 | 

 | 工具
 | 类型
 | 能发现什么

 | Slither
 | Solidity 静态分析
 | 重入模式、未检查返回值、未初始化变量、可见性问题

 | Aderyn 等
 | Solidity 静态分析
 | 常见模式检查，输出 Markdown 报告

 | Solidity SMTChecker
 | 编译器内置形式化检查
 | 断言违背、溢出（需要启用）

 | forge inspect <合约> storage-layout
 | 布局导出
 | 升级前后存储布局对比

💡 注意：静态分析的误报率高。不要追求"零告警"，要追求"每个告警都有结论"。

### 3.3 测试三层

单元测试：验证"我想到的情况"。

[图]
flowchart TB

    U1["验证「我想到的情况」"]
  end
  subgraph L2["模糊测试"]

  end
  L1 --> L2
  L2 --> L3
  L3 --> W["只检查你写下的不变量"]

读图要点：

- 数据流：从固定场景到随机输入，再到随机调用序列，覆盖面逐层扩大。
- 关键：不变量测试靠 Handler 封装 deposit、withdraw、transfer 并随机调用。
- 局限：没写进测试的不变量，模糊工具也不会发现。

模糊测试（Fuzzing）：让工具生成大量随机输入，验证性质在所有输入下成立。

// Foundry 模糊测试：存款后立即取款，用户不能获利
function testFuzz_DepositRedeemNoProfit(uint96 assets) public {
    vm.assume(assets > 0);
    deal(address(usdc), alice, assets);
    vm.startPrank(alice);
    usdc.approve(address(vault), assets);
    uint256 shares = vault.deposit(assets, alice);
    uint256 back   = vault.redeem(shares, alice, alice);
    vm.stopPrank();
    assertLe(back, assets, "round-trip must not profit");
}

不变量测试（Invariant Testing）：让工具生成随机的调用序列，每一步之后检查不变量。

// Foundry 不变量测试：银行永远有足够的 ETH 偿付所有存款
contract BankInvariant is Test {
    Bank bank; Handler handler;
    function setUp() public {
        bank = new Bank();
        handler = new Handler(bank);      // Handler 封装 deposit / withdraw / transfer，随机调用
        targetContract(address(handler));
    }
    function invariant_solvent() public view {
        assertGe(address(bank).balance, handler.sumOfBalances());
    }
}

⚠️ 警告：不变量测试只检查你写下的不变量。Euler 事故（10 章）的不变量"每个账户健康因子 ≥ 1，或可被清算且清算后协议不亏损"——如果没写进测试，模糊工具也不会发现。

### 3.4 形式化验证

形式化验证（Formal Verification）：用数学方法证明代码在所有输入和状态下满足规格。工具包括 Certora Prover、Halmos（符号执行）、K Framework 等。

适用场景：核心数学库、清算逻辑、代币会计、桥的证明验证。代价是规格编写成本高，需要专门人才。

### 3.5 外部审计

 | 

 | 做法
 | 说明

 | 冻结代码
 | 审计期间不改代码；审计对象是某个提交哈希

 | 提供文档
 | 规格、威胁模型、已知风险、测试覆盖率

 | 多家审计
 | 关键协议请 2 家以上，侧重不同

 | 审计竞赛
 | Code4rena、Sherlock、Cantina 等平台；覆盖面广

 | 修复复审
 | 修复本身可能引入新漏洞，必须复审

 | 编译器版本
 | 记录并审查编译器版本的已知 bug（Vyper 2023 事故）

 | 审计范围外的代码
 | 明确标出；部署前不得修改审计范围内代码

💡 注意：PancakeBunny 事故后，其审计方公开表示：被利用的是审计之后新上线、未经审计的合约版本（REKT 文章引述）。"审计过"只对审计时的那个版本成立。

### 3.6 安全部署

- 用脚本部署，不手动操作。脚本本身要评审。

- 部署和初始化在同一笔交易完成（09 章）。

- 部署后在浏览器验证源码（Etherscan 类浏览器、BscScan、Mantlescan、Tronscan）。

- 部署后运行验证脚本：读取所有关键参数，与预期对比。

- 把权限从部署账户移交给多签和时间锁。撤销部署账户的所有角色。

### 3.7 监控与应急

 | 

 | 监控项
 | 告警条件（示例）

 | 合约 TVL 变化
 | 10 分钟内下降 > 10%

 | 闪电贷 + 本协议交互
 | 同一交易出现大额闪电贷与本协议调用

 | 特权调用
 | 任何 owner / admin 函数被调用

 | 预言机
 | 价格偏离其他来源 > 5%；超过心跳未更新

 | 升级
 | 实现地址变化；时间锁队列新增操作

 | 跨链
 | 两侧锁定量与铸造量不一致

图 · 发现异常后的应急流程新增图解

[图]
flowchart TB
  A["监控告警<br/>TVL 骤降、特权调用、预言机偏离等"] --> B["值班人员确认"]
  B --> C["触发暂停<br/>守护者权限，无延迟"]

  F --> G["联系交易所、稳定币发行方冻结"]
  G --> H["发布公告和复盘"]
[/图]

读图要点：

- 关键：暂停必须是无延迟的守护者权限，否则来不及。
- 数据流：先止损（暂停、救援），再追回（冻结），最后复盘。
- 局限：应急能力要事先设计进合约，事发后才加已经晚了。

应急流程：

- 发现异常 → 值班人员确认。

- 触发暂停（守护者权限，无延迟）。

- 组建作战室：开发、审计方、安全响应团队（例如 SEAL 911 一类社区应急组织）。

- 评估是否可以白帽救援（抢先转移剩余资金）。

- 联系交易所、稳定币发行方冻结被盗资金。

- 发布公告和复盘。

💡 注意：mETH 协议在 Bybit 事故中追回 cmETH，靠的是三样东西：协议本身有提款延迟、团队有暂停权限、外部安全社区快速牵线（The Block 报道）。应急能力需要事先设计进合约。

## 4. 链特定测试项

"在以太坊上测过"不代表"在目标链上能跑"。部署前在目标链的测试网或主网分叉上跑一遍完整测试。

 | 

 | 链
 | 必测项
 | 工具提示

 | BNB Chain
 | 代币精度（BSC-USD 为 18 位）；基于区块数的时间计算（出块间隔已缩短到 0.75 秒）；分叉代码的改动点
 | Foundry/Hardhat 直接支持；主网分叉测试

 | TRON
 | USDT 推送转账返回值；能量与 80 ms CPU 时间上限；CHAINID、CREATE2 地址前缀；目标操作码的硬分叉开关是否已开启；TransferContract 绕过 fallback
 | TronBox、TRON IDE；在 Nile / Shasta 测试网实测，不要只用本地 EVM

 | Mantle
 | msg.value 和 address(this).balance 是 MNT；ETH 是 ERC-20（BVM_ETH）；L1 数据费随 tokenRatio 变化；排序器宕机场景；跨链消息延迟
 | Foundry 主网分叉；L1↔L2 消息用官方 SDK 测试

去 chain-porting-lab.html，选择目标链和你的代码假设，生成一份迁移风险清单。
