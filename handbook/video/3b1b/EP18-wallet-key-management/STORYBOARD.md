## 1. 概要

- **一句话核心观点**：谁能让私钥签一笔交易，谁就拥有这笔资产；密钥方案的强度取决于最弱的一环，而多签只数"签名够不够"，不检查"签的是什么"。
- **支撑结构**：私钥 = 资产 → 五种存放方案 → 攻击者能控制的七个环节（最弱一环）→ 生命周期每一步的真实事故 → 多签 / MPC 的前提是独立 → 签名那一刻：哈希与独立解码 → 热钱包：HSM 之前的风控 → 回到 WazirX。
- **关键术语**：私钥、助记词、硬件钱包、多签、MPC 门限签名、HSM、靶号地址、safeTxHash（画面称"哈希"）、operation（0 = CALL，1 = DELEGATECALL）、热 / 温 / 冷钱包、风控引擎。
- **目标观众**：看过 EP01、知道"攻击者能控制什么"这个问题的人；不需要写过合约。
- **时长**：7 分 15 秒（435.3 秒，9 个场景，52 个镜头）。

## 3. 叙事结构

1. **钩子**（hook）：WazirX 4-of-6 Safe 多签冷钱包损失约 2.3 亿美元；没有私钥被导出的公开说法，签名人按流程签名。问题"多签为什么没有拦住？"钉在左上角。
2. **铺垫**（key）：私钥是 256 位随机数；链上只认签名，谁能让它签名谁拥有资产；助记词是种子。比喻：保险柜钥匙，可无限复制；比喻不成立处：私钥复制不留痕迹。
3. **逐步构建**：
   - schemes：五种存放方案，各画出机制（手机里、芯片里只盖章、几把钥匙 + 合约、分片合成签名、HSM 按指令盖章）。
   - weak：攻击者能控制的七个环节；强度 = 最弱的一环；大额事故不是数学破解。
   - life：生命周期五步，每步有事故。具体数字一步步算：2³² = 4,294,967,296 ≈ 43 亿。Wintermute（转走余额 ≠ 撤销权限）、Slope（助记词进日志）、Trust Wallet 扩展（恶意版本）。
   - indep：多签 / MPC 的前提是独立。示例 3-of-5 共用一个前端 → 实际 1 把锁；Multichain 全部 MPC 节点在 CEO 个人云账户。
4. **关键洞见**（sign）：多签只保证足够多的人同意了某个哈希；前端被篡改时哈希背后的交易已被替换；防线是用独立工具重算哈希、核对 operation；局限：共用工具成为新单点。
5. **补充**（hot）：三层钱包；HSM 不判断交易内容，防线在 HSM 之前的风控引擎。
6. **回顾**（answer）：回到 WazirX 的签名结构、界面与实际签名不一致、合约升级、争议未决；答案"多签数的是签名够不够，不检查签的是什么"；成立条件：每个签名人在自己的设备上独立解码、在硬件屏幕核对 to / operation / data。预告第 19 集。

## 5. 材料的观点与解读者的判断

- **材料的观点**（第 18 章原文）：私钥就是资产；方案强度取决于最容易被攻破的环节（一台设备、一行日志、一个签名人的眼睛）；五种方案的比较；第 2 节攻击者能控制的七样东西；生命周期每步都有真实事故；多签只保证足够多的人同意了某个哈希；`operation = 1` 意味着执行外部代码、例行转账不应出现；共用独立工具即新单点；HSM 不判断交易内容，策略检查放在 HSM 之前并按待签原始字节判断；热钱包失守损失有上限；各案例的数字与争议说法。
- **解读者的判断**（视频的取舍，不是原文）：
  - 钩子的问题"多签为什么没有拦住？"取自 README 第 4 节；结尾的答句"多签数的是签名够不够，不检查签的是什么"是对原文"多签只保证足够多的人同意了某个哈希"的口语化改写。"钥匙安全，不等于签名安全"是解读者的归纳。
  - "2³² = 4,294,967,296"由原文"32 位，约 43 亿种"推出；对照行"2²⁵⁶ ≈ 1.2 × 10⁷⁷"由原文"256 位随机数"计算，原文没有写这个数。"挨个试"的进度条是示意，原文只说"私钥可以被 GPU 反推"，没有给出时间。
  - 十六进制私钥串、哈希 `0x7a3f…c21e`、三层钱包的柱宽、多签"2 / 3"都是示意。
  - "3-of-5、五人共用一个前端 → 实际 1 把锁"取自原文第 9 节思考题 1 与比喻"3 把锁就退化成 1 把"；"实际阈值是 1"是解读者给出的答案。
  - 生命周期只讲了 5 步（原文表格把"备份与恢复""轮换与销毁"各算一步）；Wintermute 归到"生成 + 轮换"，Multichain 放进"独立性"一场而不是"备份"，与原文 3.2 图的归类略有不同。
  - Trust Wallet 被归在"存储"这一步，依据原文 3.2 图（"恶意版本"挂在"存储"下）。原文还说与 Sha1-Hulud npm 事件"高度确信"有关，视频未提。
  - Atomic Wallet、Ledger Recover、Bybit、Radiant 未讲；第 4.3 节审批流程和第 7 节用户侧防护只以"独立解码 + 硬件屏幕核对"代表。

## 6. 成立条件、例外和风险

- 金额是事发时美元估值约数。Multichain 的约 1.26 亿美元各报道在 1.25–1.3 亿之间，且"外部攻击 / 内部转移"没有官方定性，视频说了"定性至今有争议"。
- WazirX：签名结构（WazirX 5 把、Liminal 1 把，执行需 3 个 WazirX + Liminal）和"恶意合约提前 8 天部署"出自 Halborn，原文转引。界面问题出在哪一方有争议（WazirX 指 Liminal 界面；Liminal 称受害方 3 台机器被注入恶意载荷），未见最终独立报告；视频没有归咎任何一方。美韩归因朝鲜、新加坡法院批准重组方案未讲。
- "多签数的是签名够不够"成立的条件：签名人只看前端或设备显示的哈希。如果每个签名人在自己的设备上独立解码、重算哈希并核对 to / operation / data，被替换的内容会被发现——但前提是解码工具本身也独立（原文 3.3 节局限）。
- 硬件钱包屏幕能否解析交易决定盲签风险；屏幕只显示哈希时，原文建议不签。
- 风控引擎能拦住的前提是它按待签的原始字节判断，且自身不与签名服务一起失陷（原文 4.2、29 章）。视频没有展开 29 章的参考架构。
