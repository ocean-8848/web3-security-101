## 场景 1：开场

**画面标题**：代码几乎一样， 但两件事不同（逐步动画）

**[1.0]** 大家好，链专题最后一集，Mantle。它是建在以太坊上的二层网络。一句话理解，Mantle 的合约代码和以太坊几乎一样，但有两件事不同。

**[1.1]** 第一，原生币是 MNT 不是 ETH，msg.value 收到的是 MNT。而且你从以太坊带来的 ETH，在上面是 ERC-20 的形式，不能用 call value 发送。

**[1.2]** 第二，你的资产安全不只取决于以太坊，还取决于 L2 的排序器、证明系统和升级多签。提款甚至可以被暂停，所以依赖提款一定能及时完成的协议会出错。这两件事，是 L2 和 L1 最根本的区别。

## 场景 2：以太坊旁的卫星城

**画面标题**：Mantle 像以太坊城旁的一座卫星城（逐步动画）

**[2.0]** 打个比方。Mantle 像以太坊城旁边的一座卫星城。卫星城有自己的交通调度中心，也就是排序器，调度很快，但只有一个调度员。

**[2.1]** 卫星城每隔一段时间，把账本送回以太坊城公证，提交状态根和证明。

**[2.2]** 卫星城的通用货币是 MNT。你从以太坊城带来的 ETH，在这里被换成一种 ETH 兑换券，也就是 ERC-20 形式的 ETH。

**[2.3]** 卫星城的城市规划，可以由十四人委员会中的六人签字修改，而且立即生效，没有延迟。这是一个很重要的信任假设。

**[2.4]** 比喻的局限是，卫星城出问题时，居民可以通过以太坊的紧急通道，把交易强制送进卫星城，这叫强制包含，但可能要等十二小时。下面具体看差异。

## 场景 3：链的安全模型

**画面标题**：资产安全的上限，是这几个组件（逐步动画）

**[3.0]** 先看 Mantle 的安全模型，资料来自 L2BEAT。L2 这一侧，用户交易先经过一个中心化排序器，它是唯一能出块的运营者，然后在 op-geth 分叉的 EVM 上执行，原生 gas 代币是 MNT。

**[3.1]** 以太坊这一侧有几个关键合约。交易数据发布到以太坊的 blob。输出预言机由白名单提议者提交状态根。SP1 验证器网关做有效性证明。还有桥和门户合约，持有 L1 上的跨链资产。L2BEAT 把 Mantle 归类为 ZK Rollup，用 OP Succinct 证明，但工程多签可以把它切换到乐观模式。

**[3.2]** 最关键的是升级权限。一个六选十四的安全多签，可以无延迟升级这些持有资产的 L1 合约。L2BEAT 把无升级延迟、无退出窗口标为关键风险，并将 Mantle 评为 Stage 0。还有一个三选七的工程多签，可以暂停提款、切换乐观模式。所以你在 Mantle 上的资产安全上限，其实就是这几个组件和这两个多签。

## 场景 4：与以太坊的八项差异

**画面标题**：原生币与 ETH 形态，是最常见的移植错（逐步动画）

**[4.0]** 把差异列成表。原生币是 MNT，所以 msg.value、balance、payable 函数的单位全是 MNT。ETH 是 ERC-20 形式，审计报告里叫 BVM_ETH，所以以为能用 call value 发 ETH、或者做 WETH 包装的代码都会出错。回调入口也变了，转 MNT 触发 receive，转 ETH 不触发，所以重入分析要按实际资产重做。交易费分两部分，L2 执行费加 L1 数据费，用 tokenRatio 换算，所以 L2 上可能出现 L1 上不会有的 out-of-gas。

**[4.1]** 交易顺序由单一排序器决定，MEV 和审查风险集中在运营者。排序器宕机时，价格停止更新、清算停止，要经 L1 强制提交最长十二小时，所以借贷和永续合约的清算和预言机逻辑必须考虑这种情况。

**[4.2]** 还有两项容易漏。L1 到 L2 的消息，OP Stack 会对 L1 发送者做地址别名，所以在 L2 上用 msg.sender 等于 L1 合约地址来鉴权会失败，要通过跨域信使获取原始发送者。最后，提款需要状态根被提交和终结，而且可被工程多签暂停，所以依赖提款一定能及时完成的协议会出错。前两项，原生币和 ETH 形态，是最常见的移植错。

## 场景 5：mETH 追回：防御成功

**画面标题**：三个条件缺一不可，追回约 4,300 万美元（逐步动画）

**[5.0]** 第一个案例，是个正面例子，mETH 协议追回 cmETH。mETH 是 Mantle 生态的流动性再质押协议，cmETH 的赎回有八小时延迟。攻击者用 Bybit 被盗的资金发起 cmETH 赎回，第一个条件起作用了，提款有八小时延迟，攻击者的赎回被卡在延迟里。

**[5.1]** 第二个条件，团队有暂停和资产恢复权限，于是暂停合约，把一万五千个 cmETH 从攻击者地址转到恢复地址。

**[5.2]** 第三个条件，外部安全社区 SEAL 在数小时内发现并联系到了团队。这三个条件缺一不可，最终追回约四千三百万美元。

**[5.3]** 一个鲜明的对照是，同一起事件中，Bybit 被盗的大部分原生 ETH 无法追回。区别就在于，原生 ETH 没有延迟，而 cmETH 有。延迟把攻击从一瞬间，拉长成了一个可以响应的窗口。

**[5.4]** 但这个案例也有另一面。团队能把攻击者地址上的代币转走，这意味着团队也有能力转走任何一个用户的代币。这是一个中心化权限，必须向用户披露。延迟和暂停是可信中心化的工具，它保护了资金，也要求用户信任持有权限的人。设计时要回答，谁持有权限，有没有时间锁，被滥用时用户能否察觉。

## 场景 6：客户端层的漏洞

**画面标题**：L2 的执行客户端，本身就是"合约"的一部分（逐步动画）

**[6.0]** 第二个案例，客户端层的漏洞。这提醒我们，L2 的执行客户端本身，就是合约的一部分，它决定了 EVM 规则怎样在这条链上运行。OpenZeppelin 二零二四年四月对 Mantle op-geth 修改部分的审计，报告了三个严重问题，都已修复。

**[6.1]** 第一个最吓人，BVM_ETH 无限铸造。ETH 转账缺少溢出检查，一个负的大整数被当成正数写入，结果只存入一百个 ETH，可以获得两百个。第二个，交易成本计算遗漏了 Value 字段，一个复制粘贴错误使交易池接受付不起的交易，可以被垃圾交易填满造成 DoS。第三个，代付余额检查，对多笔代付交易逐笔检查余额，而不是检查总额，也能填满交易池。

**[6.2]** 教训很深。在 L2 上，合约的可信计算基础，也就是 TCB，包括 L2 客户端、证明系统和桥合约，而你的合约审计根本覆盖不到这些。而且原生币不是 ETH 这个设计，迫使客户端增加了大量新代码，比如 ETH 作为 ERC-20 的转账逻辑和 tokenRatio 换算，新代码就是新攻击面。所以在 L2 上开发，要把这些底层组件也纳入风险评估。

## 场景 7：延迟+暂停设计模式

**画面标题**：延迟期内资产仍在协议控制下（逐步动画）

**[7.0]** 从 mETH 案例，可以提炼一个可复用的设计模式，把延迟加暂停做对。用户发起赎回后，进入请求状态。正常情况下，延迟期满就变成可领取，用户领取后结束。

**[7.1]** 关键在于，延迟期内如果守护者暂停或标记可疑，就进入冻结状态。复核通过可以恢复成请求，继续走正常流程。只有在治理加时间锁批准后，资产才转入恢复地址。注意，延迟期内资产仍在协议控制下，暂停只是阻止状态推进，并不转移资产。

**[7.2]** 有两条原则。恢复这条路径是最敏感的权限，它应该需要比暂停更高的门槛，更多签名、时间锁、公开公告。还有，延迟会降低资本效率，业界常见的折中是，小额即时赎回加大额排队赎回，或者按全局速率限制赎回。这个模式，其实就是第十集讲的把延迟当成安全参数来设计。

## 场景 8：三条链对比

**画面标题**：BNB Chain · TRON · Mantle（逐步动画）

**[8.0]** 把三条链放在一起对比。类型上，BNB Chain 是独立 L1，用 PoSA 共识。TRON 也是独立 L1，用 DPoS。Mantle 是以太坊的 L2。虚拟机上，BNB 是标准 EVM，TRON 是 EVM 变体 TVM，Mantle 是 op-geth 分叉的 EVM。

**[8.1]** 原生币，BNB、TRX、MNT，其中 Mantle 上 ETH 是 ERC-20。最大的移植陷阱各不相同，BNB 是代币精度、区块数计时和分叉改动，TRON 是 USDT 返回值、资源模型和操作码开关，Mantle 是 msg.value 单位、ETH 形态和 L2 信任假设。

**[8.2]** 应急能力也不同，BNB 的验证者可以协调停链，TRON 靠超级代表提案，Mantle 的多签可以暂停提款。这张表告诉你一件事，通用的漏洞模式是相同的，但每条链的参数和信任假设不同，所以每迁移到一条新链，都要按它的差异重新做一遍检查。手册里的链迁移检查器，可以根据目标链和你的代码假设，生成一份迁移风险清单。
