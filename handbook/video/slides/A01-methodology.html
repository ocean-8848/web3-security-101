一句话理解 · 打个比方

安全评估像建筑验收

拿图纸
施工记录、设计图
→ 资料收集
定验收范围
结构、消防、电梯
→ 范围说明书
重点查易出事处
不查每块砖
→ 威胁建模
问题分轻重
必须整改 / 建议整改
→ 风险评级
签字
交付 / 附条件 / 不交付
→ 门禁结论
比喻不准的地方：大楼验收后很少改动。合约会升级、改参数、接新资产，所以要有变更触发重评。
  1. 打个比方，安全评估像建筑验收。验收员不会重新设计大楼。他先拿到图纸和施工记录，再确定这次验什么，比如结构、消防、电梯。
  2. 他也不会检查每一块砖。他知道哪些地方最容易出事，重点看那里。对应到评估，就是威胁建模。
  3. 发现的问题，他分成两类。必须整改才能入住的，和建议整改的。这就是风险评级。
  4. 最后他签字。可以交付，附条件交付，或者不能交付。这就是评估的门禁结论。
  5. 比喻不准的地方在于，大楼验收后很少改动。合约上线后会升级，会改参数，会接入新资产。所以评估必须有一条规则，任何改变风险的变更，都触发重新评估。
流程 · 七个阶段

每个阶段都有退出条件

  1. 来看完整的流程，一共七个阶段。第一步是受理和定范围。申请方提出评估，我们写出范围说明书，双方书面确认。
  2. 第二步是资料收集，按资料清单要架构图、规格、权限清单和部署脚本。资料齐了，代码冻结，才进入下一步。
  3. 第三步是威胁建模。列出资产、入口、信任边界和关键不变量。第四步是审查与测试，这是工作量最大的一步。
  4. 第五步，给每条发现定级，写成报告。第六步，项目方修复，我们复核。严重和高危必须全部关闭，或者有业务负责人签字接受风险。
  5. 第七步，给出门禁结论，同时提出上线后的监控需求。
  6. 注意两条回头的虚线。审查中发现范围外的高风险，比如依赖的外部协议有问题，要回到第一步调整范围，而不是悄悄扩大工作量，或者视而不见。
  7. 另一条是上线之后。升级、参数变更、接入新资产，都会触发新一轮评估。所以第七步不是终点。
每个阶段交什么

不满足退出条件，就不进入下一阶段

阶段输出退出条件
① 受理与定范围范围说明书：对象、提交哈希、链、排除项申请方书面确认
② 资料收集架构、规格、权限、部署脚本、既往审计资料齐全 · 代码冻结
③ 威胁建模资产、入口、信任边界、不变量、特权清单组内评审通过
④ 审查与测试审查记录、测试代码、扫描结论每个高风险项都有结论

  1. 把每个阶段的产出列成表。第一阶段产出范围说明书，退出条件是申请方书面确认。口头说好不算数。
  2. 第二阶段的退出条件有两个。必需资料齐全，而且代码冻结。代码还在改，评估的就不是上线的版本。
  3. 第三阶段的退出条件是组内评审通过。威胁模型画错了，后面的审查就会查错地方。
  4. 第四阶段的退出条件很具体。威胁模型里每一个高风险项，都要有明确结论，有问题，或者没问题，并写明理由。
  5. 第五和第六阶段，每条发现都要有定级、证据和修复建议。严重和高危，要么修复，要么有人签字接受。
  6. 最后是门禁签字。下面我们看，同样是这七步，三类对象做起来差别有多大。
三类对象 · 时长为示例

控制力不同，深度和交付物就不同

A 交易所自有合约与钱包B DeFi 协议C 上币与合作尽调
核心问题我们的资产会不会丢协议会不会被掏空风险能否接受
对代码控制力完全可控自研可控 · 接入不可控不可控
评估深度代码 + 运营 + 密钥 + 流程代码 + 经济 + 依赖权限 + 链上数据 + 问卷
典型时长2–6 周1–4 周1–5 个工作日
交付物完整报告 + 门禁 + 监控规则完整报告或接入评估评分卡 + 结论 + 上线条件
  1. 你要负责三类对象。先看核心问题。A 类是交易所自己的合约和钱包，问题是我们的资产会不会丢。B 类是 DeFi 协议，问题是会不会被掏空，接入后会不会被连累。C 类是上币和合作项目，问题是风险能不能接受。
  2. 三者最大的区别是控制力。自己的合约完全可控，有问题就改。上币项目完全不可控，你没有权力让对方改代码。
  3. 控制力决定深度。A 类最深，要看代码、运营、密钥和流程。B 类看代码、经济模型和外部依赖。C 类看权限、链上数据，再加一份运营安全问卷。
  4. 时长也差很多。示例里，A 类两到六周，B 类一到四周，C 类只有一到五个工作日。
  5. 交付物也不同。A 类是完整报告，加门禁，加监控规则。C 类是一张评分卡，一个结论，和一组上线条件。
C 类尽调 · 注意

不是"代码安不安全"，而是"风险能不能接受"

✗ 错误的目标

五天内审完对方全部代码
要求对方修改代码后再上线
结论写"代码安全"

✓ 正确的目标

把时间花在能直接造成用户损失的权限和机制上
增发、暂停、升级、黑名单、锁仓
结论写"风险可接受 / 附条件 / 不可接受"
没有源码怎么办？仍可查：部署者历史、权限地址类型、持仓集中度、能否卖出。结论写明"未经源码审查"。
  1. C 类尽调有个常见误区。有人想在五天内审完对方全部代码，还要求对方改完再上线，最后在结论里写代码安全。这三件事都做不到。
  2. 正确的目标是，把有限的时间花在能直接造成用户损失的权限和机制上。比如谁能增发，谁能暂停，谁能升级，谁能拉黑名单，锁仓是不是真的。结论写的是风险能不能接受。
  3. 如果对方只给了合约地址，没有源码呢？仍然有事可做。可以查部署者的历史，权限地址是个人钱包还是多签，持仓是否集中，代币能不能卖出。但结论里必须写明，未经源码审查。
定范围 · 最容易出错的一步

范围说明书必须写清八项

1评估对象
仓库 + 提交哈希，不是分支名
2部署目标
链、网络、已部署地址
3包含与排除的文件
4外部依赖
哪些视为可信，哪些要评估
5链下组件
签名、后端、前端、密钥
6已知问题与既往审计
7交付物与截止时间
8结论用途
内部上线、对外公告、监管报备
  1. 七个阶段里，最容易出错的是第一步，定范围。范围说明书要写清八项。第一项是评估对象。注意，要写提交哈希，不能只写分支名。分支上的代码随时会变。第二项是部署到哪条链、哪个网络。
  2. 第三项，包含和排除哪些文件。第四项，外部依赖里，哪些视为可信，比如成熟的标准库，哪些需要评估。
  3. 第五项，链下组件在不在范围内，比如签名服务、后端、前端和密钥管理。开场讲的 Radiant，问题就出在签名环节。第六项，已知问题和以前的审计报告。
  4. 第七项，交付物和截止时间。第八项，结论用于什么，是内部上线决策，还是对外公告，或者监管报备。用途不同，措辞和证据要求就不同。
早期信号 · 应对

五个信号，在第一周就要喊停

信号风险应对
只给分支名，代码还在改评估的不是上线的版本冻结提交哈希；改动走差异评估
"只看合约，不看部署脚本"初始化、权限移交出错部署脚本默认纳入范围
"外部协议很成熟，不用看"依赖风险直接传导至少评估集成点
没有规格文档分不清 bug 还是设计先写出关键不变量

  1. 范围不清有五个早期信号。第一，申请方只给分支名，代码还在改。应对是冻结一个提交哈希，之后的改动单独做差异评估。
  2. 第二，对方说只看合约，不看部署脚本。可是初始化参数和权限移交，恰恰是部署脚本做的。Nomad 的问题就出在初始化值上。所以部署脚本默认纳入范围。
  3. 第三，对方说外部协议很成熟，不用看。成熟不等于和你的集成方式没问题。至少要评估集成点，比如价格、回调、暂停和升级。
  4. 第四，没有规格文档。那就无法判断一个行为是 bug 还是设计。应对是先让对方写出关键不变量，否则不开工。
  5. 第五，上线日期已经对外公布。时间压力会让人降低标准。应对是把门禁条件提前写进范围说明书，谁也不能临时放宽。
真实案例 · 2021-04 · 据公开复盘 · 数字为示例

Uranium：手续费精度改了，校验没跟着改

balanceAdj = balance × 10000 − 手续费require( adj0 × adj1 ≥ k × 1000² )// 左边放大了 10000²，右边只放大 1000²
  1. 来看一个真实案例，以下据公开复盘，数字为示例。Uranium 是一个分叉自 Uniswap V2 的交易所。V2 每次交换后要检查一个不变量，两种代币余额的乘积不能变小。
  2. Uranium 想把手续费精度从千分之一改成万分之一，于是把调整余额时乘的数，从1000改成了10000。
  3. 但是校验那一行，右边仍然乘以1000的平方。左边放大了10000的平方，右边只放大了1000的平方，差了100倍。
  4. 算一下。假设池子里两种代币各100个，乘积是10000。正确的校验要求交换后乘积仍然不小于10000。
  5. 错误的校验只要求乘积不小于100。这意味着两边余额可以同时降到10个左右，池子里九成的资金都能被取走。
  6. 这次改动只有一个常数。教训是，任何改动，哪怕一行，都要走差异评估，而且要回到不变量去验证。
第四阶段 · 两人评估组示例

六项工作，各有工具和产出

工作方法 · 工具产出
架构与权限审查逐个核对修饰器与角色授予 · 链上读取特权清单与最大破坏力
手工代码审查按威胁模型逐个入口走读 · 两人交叉发现草稿
静态分析Slither、Aderyn 自动扫描，逐条下结论扫描结论表
测试补强为关键不变量写模糊测试 · Foundry、Echidna测试代码与结果
部署与配置核查对照部署脚本与链上实际状态配置差异表
链差异核查按目标链清单逐项检查链风险清单
  1. 第四阶段的工作，以两个人的评估组为例，可以分成六项。第一项是架构与权限审查。逐个核对每个函数的修饰器和角色授予，产出一张特权清单。每个特权角色，写出它最坏能造成什么破坏。
  2. 第二项是手工代码审查。按威胁模型，一个入口一个入口地走读，两个人交叉审。
  3. 第三项是静态分析。工具会报很多条，每一条都要给出结论，是真问题还是误报，不能直接贴进报告。
  4. 第四项是测试补强。为关键不变量写模糊测试，让工具用大量随机输入去寻找违反条件的情况。
  5. 第五项是部署与配置核查。对照部署脚本，读取链上实际状态，看参数、权限和实现地址对不对得上。
  6. 第六项是链差异核查。同一份代码部署到 BNB Chain、TRON 或 Mantle，行为可能不同。按目标链的清单逐项检查。
工作量估算 · 示例

按有效代码行粗估，再加三成

复杂度每人每天（行）例子
低400–600标准代币、简单金库
中200–400借贷市场、质押奖励
高100–200集中流动性、跨链消息
  1. 评估要多长时间？业界常用有效代码行来粗估。有效代码行，就是去掉注释和空行之后的源码行数。再按复杂度给一个速度。示例里，低复杂度每人每天四百到六百行，中等两百到四百行，高复杂度一百到两百行。
  2. 来算一个示例。一个质押奖励合约，有效代码3600行，属于中等复杂度，按每人每天300行算。
  3. 3600除以300，是12个人天。评估组有两个人，就是6天。
  4. 再加三成用于写报告和复核。6天乘以1.3，约等于7.8天，取8个工作日。
  5. 如果上线日期只留了5天怎么办？不要压缩审查。在第一阶段就缩小范围，或者推迟上线。压缩审查等于降低标准，而且没有人知道降低了多少。
第七阶段 · 门禁结论

结论只有三种，每种都要写明依据

通过
无未关闭的严重和高危
中危有修复计划
附条件通过
限额上线、只开白名单资产
30 天内完成某项修复
部署指定监控
不通过
有未关闭的严重或高危
且没有可接受的缓解
每份结论都写明：依据的版本 · 未覆盖的范围 · 剩余风险
自评的最大风险是熟悉带来的盲区：不评自己写的代码 · 组内交叉审 · 关键模块请外部审计复核
  1. 最后是结论。只有三种。第一种是通过，没有未关闭的严重和高危，中危有修复计划。
  2. 第二种是附条件通过。可以上线，但必须满足列明的条件。比如限额上线，只开放白名单资产，30天内完成某项修复，或者部署指定的监控。
  3. 第三种是不通过。存在未关闭的严重或高危，又没有可以接受的缓解措施。
  4. 不管哪种结论，都要写明三件事。依据的是哪个版本，哪些范围没有覆盖，还剩哪些风险。没写未覆盖范围，那里出了事，就会被认为是评估失职。
  5. 还有一点。自己做评估，最大的风险是熟悉带来的盲区。所以评估人员不评自己写的代码，组内交叉审查，关键模块再请外部审计复核。
小结

记住三件事

  • 评估的交付物是一个签了字的结论，找 bug 只是手段。
  • 七个阶段各有退出条件；范围写死提交哈希，任何改动走差异评估。
  • 三类对象控制力不同；结论写明版本、未覆盖范围、剩余风险。
