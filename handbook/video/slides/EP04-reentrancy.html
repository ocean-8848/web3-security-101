编译器生成的锁是错的
  1. 大家好，欢迎来到主线第4集，重入攻击。一句话理解，合约在更新自己的账本之前，把控制权交给了外部地址。外部地址趁账本还是旧的，再次调用合约。
  2. 看三起事故，以下据公开报道。2016年，The DAO 被重入，约6000万美元。以太坊社区为此做了硬分叉，反对者继续维护原链，就是今天的以太坊经典。
  3. 六年后的2022年，借贷协议 Fei Rari 被跨函数重入，约8000万美元。
  4. 2023年，Curve 的几个池子被重入，约7000万美元。源码里写了重入锁，但编译器生成的锁是错的。重入在以太坊早期就被发现了，可至今仍在复发。

  1. 打个比方。你去银行取100元，柜员先把现金递给你，然后才去改账本。

威胁模型 · 攻击者控制了什么

函数中途交出控制权 + 状态还没更新

会交出控制权的操作为什么
向地址 call 转原生币接收方是合约时，执行它的 receive / fallback
调用代币的 transfer代币合约由攻击者部署时，代码任意
ERC-777 转账触发接收方的钩子
NFT 的 safeTransferFrom、safeMint触发接收方的 onERC721Received
闪电贷回调设计上就是把控制权交给借款人
调用用户提供的任意地址路由器、钩子、预言机
  1. 重入只需要两个前提。第一，合约在函数中途发起外部调用，被调用方受攻击者控制。第二，外部调用发生时，合约的状态还没有更新到最终值。哪些操作会交出控制权？最常见的是向一个地址转原生币，接收方如果是合约，就会执行它的接收函数。
  2. 调用代币的转账函数。如果代币合约是攻击者部署的，里面的代码可以是任何东西。ERC-777 代币转账时，会触发接收方的钩子函数。
  3. NFT 的安全转账和安全铸造，会回调接收方。闪电贷回调，设计上就是把控制权交给借款人。最后，任何调用用户提供的地址的操作，比如路由器、钩子和预言机。审计时第一件事，就是把这六类位置全部列出来。
漏洞机制 · 数字为示例

每一层都读到了旧余额

// ❌ 先转账，后记账function withdraw() external { uint amt = balances[msg.sender]; require(amt > 0); msg.sender.call{value: amt}(""); // ① 交出控制权 balances[msg.sender] = 0; // ② 太晚了}
  1. 先看最基本的单函数重入。这个提款函数，先读出余额，检查大于零，然后转账，最后才把余额清零。示例里，银行合约有10个 ETH，攻击者的余额记录是1个。
  2. 攻击者调用提款。第一层读到余额1，转出1个 ETH。转账触发了攻击者合约的接收函数，控制权交了出去。
  3. 在接收函数里，攻击者再次调用提款。第二层读到的余额，还是1，因为清零那一行还没执行。于是又转出1个。如此反复，每一层都读到旧余额。
  4. 一直到第10层，银行余额耗尽，递归停止。然后各层依次返回，执行清零。可是钱已经全部转走了。存了1个，取走10个。
防御 · 首选

检查 → 生效 → 交互

// ✅ CEIfunction withdraw() external { uint amt = balances[msg.sender]; // Checks require(amt > 0); balances[msg.sender] = 0; // Effects msg.sender.call{value: amt}(""); // Interactions require(ok);}
  1. 修复方法首选 CEI，就是检查、生效、交互三个单词的首字母。先做所有检查，读余额，确认大于零。
  2. 然后修改状态，把余额清零。
  3. 最后才做外部交互，转账。
  4. 同样的攻击再来一次。第一层清零后转账，攻击者在回调里再次调用提款。第二层读到的余额是零，检查失败，整个调用回滚。攻击直接失败，而且不需要任何额外的开销。
漏洞机制 · 数字为示例

不回到 withdraw，而是进入另一个函数

  1. 只给提款函数加锁，够不够？看跨函数重入。合约里还有一个内部转账函数，没有加锁，和提款函数共享同一个余额表。
  2. 攻击者余额1个 ETH，调用提款。转账触发回调，此时余额记录还是1。
  3. 在回调里，攻击者不再调用提款，而是调用内部转账，把这1个 ETH 的余额，转给自己的同伙。转账函数检查余额是1，通过。
  4. 回调结束，提款函数继续执行，把攻击者的余额清零。结果是，1个 ETH 被提走了，同时同伙的账上又多了1个。存了1个，拿走2个。
  5. 所以，所有读写同一状态的函数，要么都加同一把锁，要么都遵循 CEI。据公开复盘，Fei Rari 就是这样，借款函数先发送 ETH 后记账，攻击者在回调里调用了一个没有被锁覆盖的退出市场函数，取回了全部抵押品。
漏洞机制

锁挡不住的两种重入

  1. 还有两种重入，普通的锁挡不住。第一种是跨合约重入。协议由多个合约组成，比如金库合约和份额代币合约，它们共享状态。合约 A 的锁，挡不住对合约 B 的调用。B 在此刻读到的，是 A 尚未更新的状态。
  2. 第二种是只读重入。攻击者在回调里不修改目标合约，而是让第三方协议去读目标合约的一个只读函数。看这张图。攻击者从一个 AMM 池子移除流动性。池子先转出代币，后更新总量。
  3. 在转出代币时，池子回调攻击者。此刻储备已经减少，总量还没减少，池子报出的价格是扭曲的。
  4. 攻击者在回调里调用一个借贷协议。借贷协议读取池子的价格函数，拿到扭曲的价格，按错误的价格放贷或清算。
  5. 池子自己的状态最终是对的，出错的是在中间时刻读数据的第三方。池子的只读函数通常没有加锁，所以挡不住。防御方在第三方，读取外部价格前，检查对方的重入锁状态，或者改用不受单笔交易影响的价格源。
防御 · 对比

CEI 是首选，锁是第二道防线

方案优点局限
CEI零开销，从根本上消除中间状态复杂函数难以把交互都放最后
nonReentrant 存储锁简单，覆盖整个函数只保护加了锁的；不防只读；跨合约要共享锁
瞬态存储锁gas 更低目标链必须支持 EIP-1153
拉取式支付合约只记账，用户自己来取体验多一步
纵深防御：CEI 默认 · 共享状态的入口共用一把锁 · 不让 view 暴露中间态 · 不变量测试"余额 ≥ 用户余额之和"
  1. 四种防御方案对比一下。CEI 零开销，从根本上消除了中间状态，局限是复杂函数里，很难把所有交互都放在最后。重入锁简单，覆盖整个函数。但它只保护加了锁的函数，不防只读重入，跨合约时要共享同一把锁。
  2. 瞬态存储锁更省 gas，但目标链必须支持对应的操作，部署前要确认。拉取式支付，是合约只记账，由用户自己来取，代价是体验多一步。
  3. 实践中用纵深防御。把 CEI 当默认写法，所有修改共享状态的入口共用一把锁，不让只读函数暴露中间状态，再用不变量测试验证，合约余额在任何调用序列后都不小于用户余额之和。
真实案例 · 2023-07 · 据公开复盘

源码写了锁，编译器生成的锁是错的

源码

字节码

Vyper 0.2.15 / 0.2.16 / 0.3.0
不同函数用了不同的锁槽
→ 跨函数重入照样发生
教训：审计范围要包括编译器版本；关键协议要做字节码层面的测试。使用原生 ETH 的池子受影响，损失约 7,000 万$。
  1. 来看开场提到的 Curve 事故，以下据公开复盘。合约用 Vyper 语言写的，每个函数都标了重入锁。读源码的审计，看不出任何问题。
  2. 但 Vyper 的0.2.15、0.2.16和0.3.0三个版本，生成锁的代码有错，不同的函数用了不同的锁槽位。也就是说，每个函数有自己的锁，彼此不互斥，跨函数重入照样发生。
  3. 使用原生 ETH 的几个池子受到影响，损失约7000万美元。教训是，源码正确不等于字节码正确。审计范围要包括编译器版本，关键协议要做字节码层面的测试。

检查点

支持带钩子的代币吗？
不支持就显式拒绝
任意代币入口 = 任意代码入口
  1. 再看一个反复出现的模式。BNB Chain 上很多项目分叉自以太坊协议。原协议只接受白名单代币，分叉项目放开成任意代币都能上架，却没给存款函数加锁。攻击者上架一个自己部署的代币，在它的转账函数里回调存款，同一笔资产被记账两次。
  2. 以太坊上的 Penpie，2024年9月，据公开复盘损失约2700万美元。攻击者无需许可就能创建一个市场，使用自己的恶意代币。Penpie 的批量领取奖励函数没有重入锁，攻击者在回调里存入资产，把存款变成了奖励。
  3. 所以，允许任意代币，就等于允许任意回调。上架流程本身是安全边界。协议如果不支持带钩子的代币，就要显式拒绝。
链差异 · 详见链专题

同一份代码，回调入口不一样

链转原生币会触发 receive 吗
以太坊转 ETH → 触发
TRON系统交易转 TRX → 不触发；合约调用附带 callValue → 触发
MantleETH 是 ERC-20 形式 → 不触发；转原生币 MNT → 触发
  1. 同一份代码，在不同的链上，回调入口不一样。以太坊上，向合约转 ETH，一定会触发它的接收函数。
  2. TRON 上，用系统交易直接转 TRX，不会执行接收合约的回退函数。但通过合约调用附带转账，就会执行。
  3. Mantle 上，ETH 是以 ERC-20 代币的形式存在的，转 ETH 不触发接收函数。转原生币 MNT，才会触发。所以把以太坊上的重入分析搬到别的链，要重新列一遍回调入口。
审计清单

七个检查点

① 列出所有外部调用，包括代币、NFT、回调、低级 call
② 每个外部调用之前，相关状态都已是最终值？
③ 读写同一状态的入口，共享同一把锁？
④ 有 view 函数在交互期间返回中间状态，并被别人当价格用？
⑤ 支持带钩子的代币吗？不支持是否显式拒绝？
⑥ 编译器版本有已知的锁 bug 吗？
⑦ 部署链上，原生币转账会触发回退函数吗？
  1. 最后是审计检查点，一共七个。第一，列出所有外部调用，包括代币转账、NFT 安全转账、回调和低级调用。第二，每个外部调用之前，相关状态是否都已经更新到最终值。
  2. 第三，所有读写同一状态的入口，是否共享同一把锁。第四，有没有只读函数在交互期间返回中间状态，并被其他协议当作价格使用。
  3. 第五，协议支不支持带钩子的代币，不支持的话是否显式拒绝。第六，编译器版本有没有已知的重入锁 bug。
  4. 第七，在部署的链上，原生币转账会不会触发回退函数。
练一练 · 暂停视频想一想

NFT 的 mint 先调用 _safeMint，再 totalMinted++

function mint() external { require(totalMinted < MAX); _safeMint(msg.sender, id); // 回调 totalMinted++;}
能多铸。
_safeMint 会回调接收方合约；回调里再次调用 mint，此时 totalMinted 还没加 1，供应上限检查读到的是旧值。

修复：先 totalMinted++，再 _safeMint；或加锁。
  1. 来练一练。一个 NFT 合约的铸造函数，先检查已铸数量小于上限，然后调用安全铸造，最后把已铸数量加一。攻击者能多铸造吗？
  2. 能。安全铸造会回调接收方合约。在回调里再次调用铸造函数，此时已铸数量还没加一，上限检查读到的是旧值。修复方法是先把数量加一，再做安全铸造，或者加一把锁。看到了吗？没有转一分钱的 ETH，重入照样发生，因为回调本身就是交出控制权。
小结

记住三件事

  • 重入 = 交出控制权时状态还没更新；先列出所有交出控制权的位置。
  • CEI 是首选；锁要覆盖所有共享状态的入口；只读重入要在读方防。
  • 源码正确 ≠ 字节码正确；允许任意代币 = 允许任意回调。
