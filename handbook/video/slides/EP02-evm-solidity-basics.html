  1. 大家好，欢迎来到主线第2集，EVM 与 Solidity 安全基础。理解合约运行的这台机器，才能理解漏洞从哪里来。
  2. 先用一句话描述它。EVM 是一台单线程的栈式计算机。每个合约有自己的代码和自己的存储。
  3. 合约之间靠消息调用通信。每次你调用别人，都可能把控制权交给对方，而对方可以在你的事情办完之前，反过来调用你。本集讲四件事，调用上下文，三种调用，存储布局，以及八个最容易误解的语言特性。
一句话理解 · 打个比方

EVM 像一个只有一个窗口的政务大厅

每个合约是一个科室
档案柜 + 办事规程
→ storage + code
call：派人去 B 办事
B 在 B 的档案柜上办
→ 改 B 的存储
delegatecall：借 B 的手册
在 A 自己的档案柜上，按 B 的规程办
→ 改 A 的存储
比喻不准的地方：大厅里离开窗口就不能插队回来；EVM 里 B 办到一半可以反过来再找 A，而 A 的上一件事还没办完 —— 这就是重入。
  1. 打个比方，EVM 像一个只有一个窗口的政务大厅。每个合约是一个科室，有自己的档案柜，也就是存储，和自己的办事规程，也就是代码。
  2. 科室 A 要找科室 B 办事，就派人带着材料去 B 的窗口，这是 call。B 在自己的档案柜上办完，再回来。
  3. delegatecall 是另一种方式。A 把 B 的规程手册借过来，在 A 自己的档案柜上，按 B 的规程操作。如果 B 的手册写着把第0号抽屉清空，被清空的是 A 的第0号抽屉。
  4. 比喻不准的地方在于，真实的大厅里，你离开窗口后就不能插队回来。EVM 里，科室 B 办事办到一半，可以反过来再找 A，而 A 的上一件事还没办完。这就是下一集要讲的重入。
账户

外部账户和合约账户

账户有无代码能否主动发起交易控制者
外部账户 EOA无 （EIP-7702 委托后可以有）能私钥
合约账户有不能，只能被调用代码
EIP-7702（2025 年 5 月 Pectra 升级）后，extcodesize == 0 和 msg.sender == tx.origin 都不能再证明"调用者是普通用户"。
  1. 以太坊上有两类账户。外部账户由私钥控制，没有代码，能主动发起交易。合约账户有代码，由代码控制，不能主动发起交易，只能被调用。
  2. 这里有一个新变化。2025年5月，以太坊的 Pectra 升级引入了 EIP-7702，允许外部账户委托执行一段合约代码。所以，过去常用的两种判断，地址没有代码，或者消息发送者等于交易发起人，都不能再证明调用者是一个普通用户。
调用上下文 · 用户 → A → B → C

C 看到的四个值

  1. 调用上下文里有四个变量。看一条调用链，用户发起交易调用合约 A，A 调用 B，B 再调用 C。我们站在 C 的位置看。
  2. 第一个，交易发起人，tx.origin，是发起整笔交易的外部账户，也就是用户。不管调用链多长，它都不变。
  3. 第二个，消息发送者，msg.sender，是直接调用当前函数的地址。对 C 来说，是 B。
  4. 第三个，msg.value，本次调用附带的原生币数量，是 B 转给 C 的数量。第四个，address(this)，当前执行代码的合约地址，就是 C 自己。
警告 · 机制示意

owner 被骗去调用一个恶意合约之后

  1. 为什么不能用交易发起人做权限判断？看一个机制示意。一个钱包合约这样写，要求交易发起人等于 owner，才能转出资金。
  2. 某天，owner 被诱导去调用一个看起来无害的合约，比如领取一个空投。
  3. 这个合约在内部转身调用了钱包的转账函数。此时，钱包看到的交易发起人，仍然是 owner，检查通过，资金被转走。
  4. 如果钱包检查的是消息发送者，看到的就是那个恶意合约，检查失败。所以权限判断用 msg.sender，不用 tx.origin。第4集还会详细讲。
call · delegatecall · staticcall

执行谁的代码？改谁的存储？

  1. 合约之间有三种调用方式。第一种是 call，最常见。执行 B 的代码，修改 B 的存储。B 看到的消息发送者是 A，当前地址是 B。
  2. 第二种是 delegatecall。执行 B 的代码，但修改的是 A 的存储。而且消息发送者和附带的币都保持不变，B 的代码看到的消息发送者，仍然是用户，当前地址是 A。代理合约和库合约都依赖它。
  3. 第三种是 staticcall，只读调用。任何写存储或者发事件的操作都会回滚。外部调用 view 函数时，用的就是它。
  4. 还有一点很重要。低级 call 失败时，不会自动回滚调用方，只返回一个 false。忘了检查这个返回值，是第6集的主题。手册里的存储与代理实验，可以一步步观察这四个变量的变化。
练一练 · 思考题

A 用 delegatecall 调用库 L，L 里写着 owner = msg.sender

// 库合约 Laddress owner; // slot 0function init() { owner = msg.sender; }
  1. 来做一道题。合约 A 用 delegatecall 调用库合约 L 的初始化函数。L 里只有一句，owner 等于消息发送者。owner 在 L 的布局里是第0个槽位。执行之后，哪个合约的哪个槽位被改了？消息发送者是谁？可以先暂停想一想。
  2. 答案是，被改的是 A 的第0个槽位，不是 L 的。因为 delegatecall 用的是调用方 A 的存储。
  3. 消息发送者是谁？是调用 A 的那个人，因为 delegatecall 保持消息发送者不变。
  4. 如果 A 的第0个槽位原本放的不是 owner，而是别的东西，比如实现地址，那它就被一个人的地址覆盖了。这正是代理合约存储冲突的原理。如果 L 的初始化函数谁都能调，那么谁调用，谁就成了 A 的 owner。
存储布局

一个巨大的键值表，每格 32 字节

1按声明顺序
从 slot 0 开始
2相邻打包
合计不超过 32 字节就挤进同一槽
3映射
本身占槽 p
m[k] 在 keccak256(k, p)
4动态数组
槽 p 存长度
a[i] 在 keccak256(p) + i
5常量与不可变量
不占存储槽
  1. 存储是每个合约持有的一个巨大键值表，键和值都是32字节，键叫槽位。规则有五条。第一，状态变量按声明顺序，从第0个槽位开始分配。第二，相邻变量合计不超过32字节，编译器会把它们打包进同一个槽。
  2. 第三，映射本身占一个槽位 p，里面是空的。元素放在 k 和 p 一起做哈希得到的位置。第四，动态数组占一个槽位 p，存的是长度，元素从 p 的哈希值开始依次往后放。
  3. 第五，常量和不可变量不占存储槽，它们直接写在代码里。下面用一个例子看打包。
打包 · 按"剩余空间能否放下"判断

20 + 1 + 12 = 33，放不下

  1. 看一个例子。第一个变量是地址 owner，20字节，放进第0个槽位。第二个是布尔值 paused，1字节，和 owner 一起，第0个槽位用了21字节。
  2. 第三个是 fee，类型是96位整数，12字节。21加12是33，超过了32，放不下。所以 fee 从第1个槽位开始。后面的 total 在第2个槽位，映射 bal 占第3个槽位。
  3. 如果把 fee 改成88位整数，11字节，20加1加11正好32，三个变量全部挤进第0个槽位。total 变成第1个，映射变成第2个。
  4. 看出问题了吗？只改了一个类型，后面所有变量的位置都变了。如果这是一个已经上线的可升级合约，新代码会按新位置去读旧数据，余额可能被当成地址。这就是第9集存储冲突的根源。
布局 · 安全

四个场景，和一个"随机"槽位

场景风险
代理与实现的变量顺序不一致实现写 owner，实际改写了代理的实现地址
升级时在中间插入新变量后面的变量全部错位
private 变量存放密码或种子任何人都能直接读出

EIP-1967 实现地址槽 = keccak256("eip1967.proxy.implementation") − 1 = 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
  1. 存储布局为什么是安全问题？四个场景。代理和实现的变量顺序不一致，实现合约以为自己在写 owner，实际改写了代理的实现地址。升级时在中间插入新变量，后面的变量全部错位。
  2. 用 private 变量存放密码或种子，上一集讲过，任何人都能直接读出。用 delegatecall 调用不受信任的合约，对方的代码可以改写你的任何槽位。
  3. 怎样避免代理和实现冲突？EIP-1967 为代理定义了固定的槽位，用一个字符串的哈希减一得到。这个位置几乎不可能和普通变量重合。看到这串以3608开头的数字，就知道这是一个标准代理的实现地址槽。
语言特性 · 误解 vs 事实

前四个：可见性、转账、自毁、余额

1private误解：别人看不到事实：只限制其他合约调用，存储完全公开
2receive / fallback误解：转账只是改余额事实：向合约转原生币会执行它的代码 → 重入入口
3selfdestruct误解：可以删除合约事实：Cancun 后只有同交易内创建的合约才被删除；其余只转走余额
4合约余额误解：只能通过我的函数增加事实：任何人可强制转入 → 用余额记账会被"捐赠"操纵
  1. 接下来是 Solidity 最容易误解的八个特性。第一，private。误解是别人看不到。事实是它只限制其他合约调用，存储完全公开，所以不能存秘密。
  2. 第二，接收函数和回退函数。误解是转账只是改一下余额。事实是向合约转原生币，会执行对方的代码。这就是重入的入口。
  3. 第三，自毁。误解是可以删除合约。2024年 Cancun 升级以后，只有在同一笔交易里创建的合约才会被真正删除，其他情况只是把余额转走。
  4. 第四，合约余额。误解是余额只能通过我的函数增加。事实是任何人都可以强制转入。所以用合约余额来记账，会被捐赠操纵。思考题来了，一个合约要求余额必须等于存款总额，攻击者只要强制转入1个最小单位，这个检查就永久失败了。
语言特性 · 误解 vs 事实

后四个：算术、时间、区块、选择器

5检查型算术误解：0.8 以后不会出错事实：unchecked、类型转换、除法截断都不报错
6block.timestamp误解：精确时间事实：出块者可小幅调整；L2 由排序器决定
7block.number误解：每块固定时间事实：出块间隔会变
8函数选择器误解：函数名唯一事实：只有 4 字节，不同签名可能碰撞 · Poly Network
  1. 第五，检查型算术。误解是0.8版本以后算术不会出错。事实是溢出会回滚，但 unchecked 块、类型转换和除法截断都不会报错。第六，区块时间戳。误解是精确时间。事实是出块者可以小幅调整，二层网络上由排序器决定，不能做随机数，也不能做秒级判断。
  2. 第七，区块号。误解是每个区块的时间固定。算一个示例。一个合约要锁仓7天，按3秒一个块计算，写死了201600个块。
  3. 后来出块间隔缩短到0.75秒，这正是 BNB Chain 发生过的变化。同样是201600个块，现在只要42个小时，也就是1.75天，锁仓期缩短了四分之三。
  4. 第八，函数选择器。误解是函数名唯一。事实是选择器只有4个字节，不同的函数签名可能算出同一个选择器。2021年 Poly Network 事故的关键一步，就利用了这一点，第11集会讲。
执行规则

哪些失败会冒泡，哪些不会

会冒泡
require、自定义错误 → 回滚当前调用并向上传
gas 用完 → 当前调用帧回滚
不会冒泡
低级 call 失败 → 只返回 false
try / catch 只捕获外部调用的失败
63 / 64 规则
外部调用最多转发 63/64 的剩余 gas
被调用方耗尽时，调用方还有 1/64 收尾
transfer / send 只转 2300 gas
曾被当作防重入；gas 价格调整后，
接收方是合约钱包时会失败
  1. 再看错误处理。require 和自定义错误会回滚当前调用，并且向上冒泡，调用方也跟着回滚。gas 用完，当前调用帧回滚。
  2. 有两种情况不会冒泡。低级 call 失败时只返回 false，调用方继续执行。try catch 只能捕获外部调用的失败，不能捕获本合约内部的失败。
  3. 还有一条63分之64规则。外部调用最多转发剩余 gas 的63分之64，被调用方耗尽 gas 时，调用方还剩64分之1可以收尾。
  4. 最后，transfer 和 send 只转发2300 gas，曾经被当作防重入的手段。后来 gas 价格调整，接收方是合约钱包时，这种转账会直接失败。现在的推荐做法是用 call 转账，再用检查生效交互的顺序或重入锁来防重入。
编译器 · 据公开复盘

编译器本身也会有 bug

版本关键变化安全含义
< 0.8.0算术默认不检查溢出必须用 SafeMath
≥ 0.8.0算术默认检查，溢出回滚unchecked 块内仍会回绕
≥ 0.8.24支持瞬态存储低成本重入锁；跨链要确认目标链支持
2023-07 · Vyper 0.2.15 / 0.2.16 / 0.3.0 的重入锁实现错误 → 多个 Curve 池被重入，约 7,000 万$
  1. 最后是编译器。0.8.0之前的版本，算术默认不检查溢出，必须用 SafeMath 库。0.8.0以后默认检查，但 unchecked 块里仍然会回绕。
  2. 0.8.24以后支持瞬态存储，只在当前交易内有效，交易结束自动清零，可以实现低成本的重入锁。但部署到其他链时，要确认目标链支持这个操作。
  3. 编译器本身也会有 bug。据公开复盘，2023年7月，另一种合约语言 Vyper 的三个版本，重入锁的实现有错误，导致多个 Curve 池被重入，损失约7000万美元。所以编译器版本要锁定，并关注它的已知 bug 列表。
小结

记住三件事

  • 权限用 msg.sender；delegatecall 执行别人的代码、改自己的存储。
  • 存储按槽位打包；改一个类型、插一个变量，后面全部错位。
  • private 不保密、余额可被强制转入、区块时间会变、低级 call 失败不冒泡。
