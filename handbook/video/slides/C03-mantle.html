  1. 大家好，链专题最后一集，Mantle。它是建在以太坊上的二层网络。一句话理解，Mantle 的合约代码和以太坊几乎一样，但有两件事不同。
  2. 第一，原生币是 MNT 不是 ETH，msg.value 收到的是 MNT。而且你从以太坊带来的 ETH，在上面是 ERC-20 的形式，不能用 call value 发送。
  3. 第二，你的资产安全不只取决于以太坊，还取决于 L2 的排序器、证明系统和升级多签。提款甚至可以被暂停，所以依赖提款一定能及时完成的协议会出错。这两件事，是 L2 和 L1 最根本的区别。

安全模型 · 资料来自 L2BEAT（截至 2026）

资产安全的上限，是这几个组件

  1. 先看 Mantle 的安全模型，资料来自 L2BEAT。L2 这一侧，用户交易先经过一个中心化排序器，它是唯一能出块的运营者，然后在 op-geth 分叉的 EVM 上执行，原生 gas 代币是 MNT。
  2. 以太坊这一侧有几个关键合约。交易数据发布到以太坊的 blob。输出预言机由白名单提议者提交状态根。SP1 验证器网关做有效性证明。还有桥和门户合约，持有 L1 上的跨链资产。L2BEAT 把 Mantle 归类为 ZK Rollup，用 OP Succinct 证明，但工程多签可以把它切换到乐观模式。
  3. 最关键的是升级权限。一个六选十四的安全多签，可以无延迟升级这些持有资产的 L1 合约。L2BEAT 把无升级延迟、无退出窗口标为关键风险，并将 Mantle 评为 Stage 0。还有一个三选七的工程多签，可以暂停提款、切换乐观模式。所以你在 Mantle 上的资产安全上限，其实就是这几个组件和这两个多签。
差异总表 · 移植最常见的错在前两项

原生币与 ETH 形态，是最常见的移植错

差异Mantle会让什么出错
原生币MNTmsg.value/balance/payable 单位是 MNT
ETH 的形态ERC-20（BVM_ETH）以为能 call{value:} 发 ETH、WETH 包装
回调入口转 MNT 触发 receive，转 ETH 不触发重入分析、接收通知逻辑
交易费L2 执行费 + L1 数据费（tokenRatio 换算）L2 上可能出现 L1 没有的 out-of-gas
交易顺序单一排序器MEV/审查集中在运营者
排序器宕机清算/喂价停，强制提交最长 12 小时借贷、永续的清算与预言机
L1→L2 消息对 L1 发送者做地址别名msg.sender==L1地址 鉴权会失败
提款需状态根提交/终结，可被暂停依赖"提款一定及时"的协议
  1. 把差异列成表。原生币是 MNT，所以 msg.value、balance、payable 函数的单位全是 MNT。ETH 是 ERC-20 形式，审计报告里叫 BVM_ETH，所以以为能用 call value 发 ETH、或者做 WETH 包装的代码都会出错。回调入口也变了，转 MNT 触发 receive，转 ETH 不触发，所以重入分析要按实际资产重做。交易费分两部分，L2 执行费加 L1 数据费，用 tokenRatio 换算，所以 L2 上可能出现 L1 上不会有的 out-of-gas。
  2. 交易顺序由单一排序器决定，MEV 和审查风险集中在运营者。排序器宕机时，价格停止更新、清算停止，要经 L1 强制提交最长十二小时，所以借贷和永续合约的清算和预言机逻辑必须考虑这种情况。
  3. 还有两项容易漏。L1 到 L2 的消息，OP Stack 会对 L1 发送者做地址别名，所以在 L2 上用 msg.sender 等于 L1 合约地址来鉴权会失败，要通过跨域信使获取原始发送者。最后，提款需要状态根被提交和终结，而且可被工程多签暂停，所以依赖提款一定能及时完成的协议会出错。前两项，原生币和 ETH 形态，是最常见的移植错。
案例一 · EP10 延迟 + 暂停救回资产

三个条件缺一不可，追回约 4,300 万美元

① 提款延迟
cmETH 赎回有 8 小时延迟
攻击者赎回被卡住
② 暂停 + 恢复权
团队暂停合约
把 15,000 cmETH 转到恢复地址
③ 外部社区
SEAL 数小时内联系到团队
发现并通知
对照：同一起事件中，Bybit 被盗的大部分原生 ETH 无法追回——原生 ETH 没有延迟，cmETH 有。
另一面：团队能转走攻击者地址的代币，意味着也能转走任何用户的代币。这是必须向用户披露的中心化权限。
  1. 第一个案例，是个正面例子，mETH 协议追回 cmETH。mETH 是 Mantle 生态的流动性再质押协议，cmETH 的赎回有八小时延迟。攻击者用 Bybit 被盗的资金发起 cmETH 赎回，第一个条件起作用了，提款有八小时延迟，攻击者的赎回被卡在延迟里。
  2. 第二个条件，团队有暂停和资产恢复权限，于是暂停合约，把一万五千个 cmETH 从攻击者地址转到恢复地址。
  3. 第三个条件，外部安全社区 SEAL 在数小时内发现并联系到了团队。这三个条件缺一不可，最终追回约四千三百万美元。
  4. 一个鲜明的对照是，同一起事件中，Bybit 被盗的大部分原生 ETH 无法追回。区别就在于，原生 ETH 没有延迟，而 cmETH 有。延迟把攻击从一瞬间，拉长成了一个可以响应的窗口。
  5. 但这个案例也有另一面。团队能把攻击者地址上的代币转走，这意味着团队也有能力转走任何一个用户的代币。这是一个中心化权限，必须向用户披露。延迟和暂停是可信中心化的工具，它保护了资金，也要求用户信任持有权限的人。设计时要回答，谁持有权限，有没有时间锁，被滥用时用户能否察觉。
案例二 · L2 的可信计算基础（TCB）

L2 的执行客户端，本身就是"合约"的一部分

op-geth 审计发现（已修复）机制如果未修复
BVM_ETH 无限铸造ETH 转账缺溢出检查，负 big.Int 被当正数存 100 ETH 可得 200 ETH
交易成本遗漏 Value复制粘贴错误，接受付不起的交易交易池被垃圾交易填满（DoS）
代付余额检查逐笔检查而非检查总额无法支付的交易填满交易池
教训：在 L2 上，合约的可信计算基础（TCB）包括 L2 客户端、证明系统和桥合约——合约审计覆盖不到这些。"原生币不是 ETH"迫使客户端增加大量新代码，新代码=新攻击面。
  1. 第二个案例，客户端层的漏洞。这提醒我们，L2 的执行客户端本身，就是合约的一部分，它决定了 EVM 规则怎样在这条链上运行。OpenZeppelin 二零二四年四月对 Mantle op-geth 修改部分的审计，报告了三个严重问题，都已修复。
  2. 第一个最吓人，BVM_ETH 无限铸造。ETH 转账缺少溢出检查，一个负的大整数被当成正数写入，结果只存入一百个 ETH，可以获得两百个。第二个，交易成本计算遗漏了 Value 字段，一个复制粘贴错误使交易池接受付不起的交易，可以被垃圾交易填满造成 DoS。第三个，代付余额检查，对多笔代付交易逐笔检查余额，而不是检查总额，也能填满交易池。
  3. 教训很深。在 L2 上，合约的可信计算基础，也就是 TCB，包括 L2 客户端、证明系统和桥合约，而你的合约审计根本覆盖不到这些。而且原生币不是 ETH 这个设计，迫使客户端增加了大量新代码，比如 ETH 作为 ERC-20 的转账逻辑和 tokenRatio 换算，新代码就是新攻击面。所以在 L2 上开发，要把这些底层组件也纳入风险评估。
设计模式 · 从 mETH 提炼可复用设计

延迟期内资产仍在协议控制下

  1. 从 mETH 案例，可以提炼一个可复用的设计模式，把延迟加暂停做对。用户发起赎回后，进入请求状态。正常情况下，延迟期满就变成可领取，用户领取后结束。
  2. 关键在于，延迟期内如果守护者暂停或标记可疑，就进入冻结状态。复核通过可以恢复成请求，继续走正常流程。只有在治理加时间锁批准后，资产才转入恢复地址。注意，延迟期内资产仍在协议控制下，暂停只是阻止状态推进，并不转移资产。
  3. 有两条原则。恢复这条路径是最敏感的权限，它应该需要比暂停更高的门槛，更多签名、时间锁、公开公告。还有，延迟会降低资本效率，业界常见的折中是，小额即时赎回加大额排队赎回，或者按全局速率限制赎回。这个模式，其实就是第十集讲的把延迟当成安全参数来设计。
