一句话理解 · 打个比方

合约开发像造一架飞机

画图纸
写出"机翼不能断"
→ 规格 + 不变量
零件进风洞吹
各种极端风向
→ 模糊测试
适航认证抽查
不查每颗螺丝
→ 审计
黑匣子 + 地面雷达
出问题有应急程序
→ 监控 + 应急
比喻不准的地方：飞机出厂后可以召回维修。不可升级的合约出厂后就不能改了，所以前面的关口必须更严。
  1. 打个比方。合约开发像造一架飞机。设计阶段，画图纸，并写出任何情况下机翼不能断，这是不变量。制造阶段，每个零件出厂前都测，并把零件放进风洞里用各种极端风向吹，这是模糊测试。
  2. 适航认证，外部机构检查，这是审计。认证不检查每一颗螺丝，只抽查关键系统。
  3. 投入运营，飞行中有黑匣子和地面雷达，这是监控，出了问题有应急程序。
  4. 比喻不准的地方在于，飞机出厂后可以召回维修。不可升级的合约出厂后就不能改了，所以前面的关口必须更严。
流程 · 越靠左修复越便宜

从设计到上线后监控

  1. 合约安全有八个关口。第一，规格与威胁模型。第二，安全编码规范。第三，静态分析。第四，单元、模糊、不变量测试。越靠左的关口，修复成本越低。规格阶段发现的问题，只需要改文档。
  2. 第五，关键模块的形式化验证。第六，外部审计或竞赛。第三到第五是自动化关口，每次提交代码都应该运行。
  3. 第七，安全部署与权限移交。第八，上线后的监控、漏洞赏金和应急响应。
  4. 两条关键原则。审计发现的问题，要反向补充到第四步的测试里，防止回归。还有，发现问题后回流到第一步。所有关口都依赖你想到了要检查什么，经济攻击常常需要专门的经济审计。
关口一 · 修复成本最低的地方

动手写代码之前，先写下四样东西

1
前置 / 后置条件
每个函数调用前必须满足什么，调用后必须变成什么
2
系统不变量
例：银行余额 ≥ 存款总和
3
外部依赖
代币、预言机、DEX、跨链桥、目标链特性
4
特权角色
每个角色的最大破坏力
这里写下的不变量，会直接变成关口四里测试的断言。
  1. 先展开第一个关口，规格与威胁模型。它要写下四样东西。第一，每个函数的前置条件和后置条件，也就是调用前必须满足什么，调用后必须变成什么。第二，系统不变量，比如银行余额永远不少于存款总和，第1集讲过。
  2. 第三，列出外部依赖，代币、预言机、DEX、跨链桥，还有目标链的特性。第四，列出所有特权角色，以及每个角色最大能造成多大破坏。这一步写下的不变量，后面会直接变成测试里的断言。
关口三 · 每次提交都跑

不追求零告警，追求每个告警都有结论

工具类型能发现什么
Slither静态分析重入模式、未检查返回值、未初始化变量、可见性
Aderyn 等静态分析常见模式检查，输出 Markdown 报告
SMTChecker编译器内置断言违背、溢出（需启用）
forge inspect storage-layout布局导出升级前后存储布局对比
  1. 静态分析是第三个关口，每次提交都应该跑。常用工具 Slither，发现重入模式、未检查返回值、未初始化变量和可见性问题。还有 Aderyn 这类，做常见模式检查，输出报告。
  2. 编译器内置的 SMTChecker，能发现断言违背和溢出，需要启用。forge inspect 的存储布局导出，用于升级前后对比，第9集讲过。
  3. 一个重要原则，静态分析的误报率高。不要追求零告警，要追求每个告警都有结论，是真问题还是误报，并写明理由。
关口四 · 单元 → 模糊 → 不变量

从"我想到的"到"工具替我找"

  1. 测试分三层。第一层，单元测试，验证我想到的情况。比如存100应该得多少份额，我写死预期值去验证。它只覆盖我想到的场景。
  2. 第二层，模糊测试。让工具生成大量随机输入，验证一个性质在所有输入下都成立。比如，存款后立即取款，用户不能获利。工具会用成千上万个随机金额去试。
  3. 第三层，不变量测试。让工具生成随机的调用序列，每一步之后检查不变量。比如，银行永远有足够的 ETH 偿付所有存款。工具随机地组合存款、取款、转账，寻找打破这条不变量的序列。这正是评估篇第8集讲的方法。
  4. 但要记住一条警告。不变量测试只检查你写下的不变量。Euler 那条健康因子的不变量，如果没写进测试，模糊工具也不会发现。你写性质，工具找序列，但性质要你写对。
关口五 · 关键模块

不是多试一些输入，而是证明所有输入都成立

工具

Certora Prover
Halmos（符号执行）
K Framework

适用场景

核心数学库
清算逻辑
代币会计
桥的证明验证
代价：规格编写成本高，需要专门人才 → 只对关键模块做。
  1. 第五个关口，形式化验证。模糊测试是用大量输入去试，形式化验证是用数学方法证明，代码在所有输入和所有状态下都满足规格。常见工具有 Certora Prover，做符号执行的 Halmos，还有 K Framework。
  2. 它适合用在最关键的地方，核心数学库、清算逻辑、代币会计，以及跨链桥的证明验证。代价是规格编写成本高，需要专门的人才。所以一般只对关键模块做，不是整个项目都做。
关口六

"审计过"只对审计时的那个版本成立

做法说明
冻结代码审计对象是某个提交哈希，审计期间不改
提供文档规格、威胁模型、已知风险、测试覆盖率
多家审计关键协议请 2 家以上，侧重不同
修复复审修复本身可能引入新漏洞，必须复审
编译器版本记录并审查已知 bug（Vyper 2023）
范围外代码明确标出；部署前不得修改范围内代码
  1. 外部审计有几条做法。冻结代码，审计对象是某个提交哈希，审计期间不改。提供文档，规格、威胁模型、已知风险和测试覆盖率都给审计方。
  2. 多家审计，关键协议请两家以上，侧重不同。修复复审，修复本身可能引入新漏洞，必须复审。
  3. 编译器版本，记录并审查它的已知 bug，这是 Vyper 事故的教训。范围外的代码明确标出，部署前不得修改范围内的代码。这部分在评估篇第7集讲得更细。核心是，审计过只对审计时的那个版本成立。
关口七、八

应急能力要事先设计进合约

⑦ 安全部署

脚本部署，脚本评审
部署与初始化同一笔交易
浏览器验证源码 + 读参数核对
权限移交多签时间锁，撤销部署账户角色

⑧ 监控与应急

TVL 骤降、闪电贷交互、特权调用、价格偏离、升级、跨链对账 → 告警
发现 → 确认 → 暂停 → 作战室 → 白帽救援 / 联系冻结 → 公告复盘
mETH 在 Bybit 事故中追回，靠三样：协议有提款延迟 + 团队有暂停权 + 外部安全社区快速牵线 —— 都是事先设计的。
  1. 第七个关口，安全部署。用脚本部署，脚本本身要评审。部署和初始化在同一笔交易完成。部署后在浏览器验证源码，读取所有关键参数和预期对比。最后把权限移交给多签和时间锁，撤销部署账户的所有角色。
  2. 第八个关口，监控与应急。监控合约 TVL 骤降、闪电贷与本协议的交互、特权调用、价格偏离、升级、跨链对账，触发告警。应急流程是，发现异常，值班确认，触发暂停，组建作战室，评估白帽救援或联系交易所冻结，最后公告和复盘。
  3. 一个正面例子。mETH 协议在 Bybit 事故中追回资产，靠的是三样东西，协议本身有提款延迟，团队有暂停权限，外部安全社区快速牵线。这三样，都是事先设计进去的。应急能力不能等出事了才有。评估篇第9集专门讲应急。
关口八 · 告警条件示例

每条告警都要有人值班响应

监控项告警条件（示例）
合约 TVL 变化10 分钟内下降 > 10%
闪电贷 + 本协议交互同一交易出现大额闪电贷与本协议调用
特权调用任何 owner / admin 函数被调用
预言机价格偏离其他来源 > 5%；超过心跳未更新
升级实现地址变化；时间锁队列新增操作
跨链两侧锁定量与铸造量不一致
  1. 监控具体怎么设告警？给几个示例阈值。合约 TVL，10分钟内下降超过10%。闪电贷，同一笔交易里出现大额闪电贷和本协议的调用。特权调用，任何管理员函数被调用，都要告警。
  2. 预言机，价格偏离其他来源超过5%，或者超过心跳时间没有更新。升级，实现地址变化，或者时间锁队列新增操作。跨链，两侧锁定量和铸造量不一致。阈值要按协议调整，关键是每条告警都有人值班响应。
链差异 · "在以太坊上测过"≠"目标链能跑"

部署前在目标链的测试网或分叉上跑一遍

链必测项
BNB Chain代币精度（BSC-USD 18 位）；基于区块数的时间计算；分叉代码的改动点
TRONUSDT 推送返回值；能量与 80ms 时限；CHAINID、地址前缀；硬分叉开关；TransferContract 绕过 fallback
Mantlemsg.value 是 MNT；ETH 是 ERC-20；L1 数据费；排序器宕机；跨链消息延迟
工具提示：BNB Chain 用 Foundry / Hardhat 主网分叉 · TRON 用 TronBox、TRON IDE，在 Nile / Shasta 测试网实测 · Mantle 用 Foundry 主网分叉，L1↔L2 消息用官方 SDK 测试
  1. 链特定测试，在以太坊上测过，不代表在目标链上能跑。部署前，要在目标链的测试网或者主网分叉上，跑一遍完整测试。BNB Chain 上必测，代币精度，BSC-USD 是18位，基于区块数的时间计算，因为出块间隔变了，还有分叉代码的改动点。
  2. TRON 上必测，USDT 推送转账的返回值，能量和80毫秒的时限，链 ID 和地址前缀，目标操作码的硬分叉开关是否开启，以及直接转账绕过回退函数。而且要在 TRON 的测试网实测，不要只用本地 EVM。
  3. Mantle 上必测，收到的原生币是 MNT，ETH 是 ERC-20 形式，一层数据费，排序器宕机场景，以及跨链消息延迟。手册里的链迁移检查器，可以根据目标链和你的代码假设，生成一份迁移风险清单。链专题会逐一展开。
一页速查表 · 把全系列浓缩成清单

十类，每类一个关键问题

  1. 最后是一页审计速查表，把整个主线浓缩成一张清单。重入，外部调用前状态是否已更新，共享状态是否共享锁。权限，每个状态修改函数谁能调用，初始化是否受保护。算术，舍入方向对协议有利，精度从合约读取。外部调用，返回值检查，无代码地址，非标准代币。
  2. 预言机，价格一笔交易内可变吗，时效和上下限检查。MEV 和签名，有最小输出和截止时间吗，EIP-712 加 nonce。升级，存储布局，实现合约已锁死，时间锁。
  3. 经济，偿付不变量，治理快照，清算激励。跨链，消息字段完整，防重放，限额。最后是链差异，目标链和以太坊有哪些行为差异。这张表，就是前面十一集的提炼。把它贴在显示器旁边。
练一练 · 暂停视频想一想

两家审计已通过，上线前一周要把手续费从 0.3% 改成 0.25%

只改一个数字，可以直接上线吗？
参考
不能。改完就是新版本，审计结论不再覆盖它。
① 找审计方复审这次改动
② 把不变量补进测试：每次兑换后 k 不减少
③ 搜遍所有用到费率的地方
Uranium Finance：只改了一处常数，漏改另一处，k 检查失效，约 5,000 万$。
  1. 来练一练。你的协议通过了两家审计。上线前一周，产品要求把手续费从0.3%改成0.25%。只是改一个数字，可以直接上线吗？
  2. 参考答案。不能直接上线。改完之后就是一个新版本，审计结论不再覆盖它。要做三件事。第一，找审计方对这次改动做复审。第二，把相关不变量补进测试，比如每次兑换后乘积 k 不减少，让模糊测试去跑。第三，搜遍代码里所有用到这个费率的地方。Uranium Finance 就是改手续费时，只改了一处常数，漏改了另一处，k 检查失效，据公开报道损失约5000万美元。
小结

记住三件事

  • 审计只是一个关口；越靠左修复越便宜，发现回流到设计和测试。
  • 测试三层：单元、模糊、不变量；工具找序列，但性质要你写对。
  • "审计过"只对那个版本成立；应急能力要事先设计进合约。
