  1. 大家好，欢迎来到主线第4集，访问控制与权限。合约的每个状态修改函数，都必须回答一个问题，谁可以调用我？如果答案是任何人，就必须证明任何人调用都安全。
  2. 看三起事故，以下据公开报道。2017年，Parity 多签钱包依赖的库合约没有初始化，被一个用户接管后自毁，约51万个 ETH 被永久冻结。
  3. 2022年，Ronin 跨链桥，其中一份签名权，来自一个早就不需要、却没有撤销的授权。
  4. 同年，BNB Chain 的 Token Hub，只要付100个 BNB 的押金就能注册成跨链中继者，攻击者因此凭空铸造了200万个 BNB。三起事故，都是谁能做什么没有想清楚。

→ 缺少权限检查

不看刷卡的是谁

第一个喊"我是经理"的人

→ 未初始化

比喻不准的地方：写字楼可以换锁。合约如果不能升级，锁一旦装错就永远是错的。
  1. 打个比方，合约像一栋写字楼。公开函数是大堂的门，谁都能进。onlyOwner 函数是机房的门，要刷卡。漏洞一，机房门忘了装刷卡器，就是缺少权限检查。
  2. 漏洞二，刷卡器只检查刷卡的人是不是从总裁办公室出来的，不检查刷卡的到底是谁。这就是用 tx.origin 鉴权。
  3. 漏洞三，大楼刚建好时，第一个走进物业办公室、宣布我是经理的人，就成了经理。这是未初始化。
  4. 漏洞四，总裁的门卡一直放在前台抽屉里，这是私钥管理。
  5. 比喻不准的地方在于，写字楼的锁可以换。合约如果没有升级能力，锁一旦装错，就永远是错的。
威胁模型

不只是"外部攻击者"

攻击者身份能力典型攻击
任意外部地址调用所有公开函数调用未保护的 mint、setOwner、initialize
恶意合约在 owner 交互时插入调用利用 tx.origin 冒充 owner
被钓鱼的特权用户签下自己看不懂的交易前端篡改、盲签
拿到私钥的攻击者完全等同于特权角色验证者私钥泄露
内部人员合法持有特权跑路、恶意升级
  1. 权限问题的攻击者有五种身份。第一种，任意外部地址，可以调用所有公开函数。典型攻击是调用没有保护的增发、改 owner 或初始化函数。
  2. 第二种，恶意合约，在 owner 和它交互时插入调用，利用 tx.origin 冒充 owner。第三种，被钓鱼的特权用户，签下了自己看不懂的交易。
  3. 第四种，拿到私钥的攻击者，完全等同于特权角色。第五种，内部人员，合法持有特权，却跑路或者恶意升级。后三种，代码写得再对也防不住，要靠权限设计。
六种常见缺陷 · 1–2

机房门没装刷卡器

① 缺少权限检查

function mint(to, amt) external { _mint(to, amt); // 任何人都能增发}

修复

function mint(to, amt) external onlyRole(MINTER_ROLE) { _mint(to, amt);}
0.5 之前函数默认 public：旧合约忘写可见性 = 把内部函数暴露给所有人。
② tx.origin 鉴权 → 改用 msg.sender（机制见 EP02）
  1. 第一种缺陷，缺少权限检查。这个增发函数是外部可调用的，没有任何修饰器，任何人都能增发。
  2. 修复很简单，加上角色检查，只有拥有增发角色的地址才能调用。
  3. 注意一个历史问题。Solidity 0.5之前，函数默认可见性是 public。旧合约如果忘了写可见性，就等于把内部函数暴露给了所有人。审计老代码时要特别留意。
  4. 第二种缺陷，用 tx.origin 鉴权，第2集讲过机制。修复是改用 msg.sender。
六种常见缺陷 · 3

第一个喊"我是经理"的人，就成了经理

漏洞

function initialize(owner_) external { owner = owner_;}// 谁都能调，还能重复调

修复

function initialize(owner_) external initializer { ... }constructor() { _disableInitializers(); // 锁死实现}
两处都要锁：代理调用的初始化只能执行一次；实现合约本身也要在构造函数里锁死。
  1. 第三种缺陷，未保护的初始化函数。可升级合约和克隆合约，用初始化函数代替构造函数。如果它谁都能调用，或者可以重复调用，任何人都能把自己设为 owner。
  2. 修复有两处。第一，初始化函数加上 initializer 修饰器，保证只能执行一次。第二，在实现合约的构造函数里，调用禁用初始化，把实现合约本身锁死。
  3. 为什么实现合约本身也要锁？因为实现合约也是一个独立部署的合约，任何人都可以直接调用它。下面这起事故，就是两处都没锁好。
真实案例 · 2017 · 据公开复盘

同一个库，两次出事

  1. 来看 Parity 多签钱包，以下据公开复盘。每个钱包是一个很薄的合约，遇到不认识的调用，就用 delegatecall 转给一个共享的库合约。
  2. 2017年7月。库里的钱包初始化函数没有保护。攻击者通过钱包调用了它，delegatecall 改写的是钱包自己的存储，攻击者成了钱包的 owner，转走约15.3万个 ETH。
  3. 修复后，部署了一个新的库合约。但这个库合约本身没有初始化。
  4. 2017年11月，一个用户直接调用了这个库的初始化函数，成了库的 owner，然后调用了库的自毁函数。
  5. 库合约消失了。所有依赖它的钱包失去了代码逻辑，资金还在，却再也调不动，约51万个 ETH 被永久冻结。教训是，实现合约本身也必须初始化，或者在构造函数里锁死。
六种常见缺陷 · 4–6

任意调用、单步转移、签名写错

④ 任意外部调用

execute(target, data)
合约持有授权时，data = transferFrom(受害者, 攻击者)
换成 delegatecall → 直接改写存储

⑤ 单步所有权转移

输错地址 → 权限永久丢失
两步式：新 owner 必须主动 accept

⑥ 签名鉴权写错

无效签名 → ecrecover 返回 address(0)
签名者变量未设置（也是 0）→ 检查通过
  1. 第四种缺陷，任意外部调用。一个执行函数，让用户指定目标地址和调用数据。如果这个合约持有别人给它的代币授权，攻击者就把调用数据构造成，从受害者转账给攻击者。如果这里用的是 delegatecall，攻击者的代码会直接改写本合约的存储。
  2. 第五种，单步所有权转移。owner 一步把权限转给新地址，输错一个字符，权限就永久丢失。修复是两步式，新 owner 必须主动调用接受函数。
  3. 第六种，签名鉴权写错。用签名代替消息发送者来鉴权时，ecrecover 对无效签名会返回零地址。如果被比较的签名者变量从没设置过，它默认也是零，检查就通过了。第8集会详细讲签名。
防御 · 特权角色设计 · 延迟为示例

暂停要快，升级要慢

角色能做什么建议持有者建议延迟
UPGRADER升级实现合约多签 + 时间锁≥ 48 小时
PARAM_ADMIN调整费率、抵押率多签 + 时间锁24 小时
PAUSER紧急暂停小型多签或监控机器人无延迟
MINTER增发只授予特定合约—
  1. 防御的核心是最小权限，把一个万能的 owner，拆成多个角色，每个角色只做一件事。升级角色负责升级实现合约，由多签加时间锁持有，示例延迟48小时以上。
  2. 参数管理员负责调整费率和抵押率，同样是多签加时间锁，示例延迟24小时。
  3. 暂停角色负责紧急暂停，由小型多签或者监控机器人持有，没有延迟。增发角色只授予特定的合约，不给任何人。
  4. 为什么暂停要快、升级要慢？暂停只能止损，不能转走资金。升级可以做任何事。所以权力越大，延迟越长。
防御 · 示例

时间锁给用户一个"退出窗口"

  1. 多签加时间锁是这样工作的。提案者是一个5选3的多签，它不能直接修改目标合约，只能把操作提交到时间锁合约排队。
  2. 示例延迟48小时。这48小时里，排队的操作是公开的，监控和社区都能看到。
  3. 如果发现是恶意操作，守护者可以取消。注意权限是不对称的，守护者只能取消，不能发起。
  4. 用户如果不同意，可以在这48小时里撤出资金。延迟到期后，操作才被执行。
  5. 这套设计的局限是，如果多签的签名人被同时钓鱼，比如所有人都看到了同一个被篡改的界面，多签就防不住。它只能防单个私钥被盗。时间锁的价值，正在于给发现留出时间。
L2 信任假设 · 据 L2BEAT 公开页面

不是代码漏洞，而是信任假设

  1. 二层网络的桥合约，持有用户全部的跨链资产。谁能升级桥合约，谁就能决定这些资产的去向。看 Mantle，以下据 L2BEAT 截至2026年的公开页面。
  2. Mantle 有一个安全多签，14个签名人，阈值是6。它可以没有延迟地升级一层网络上的桥和输出预言机合约。
  3. 算一下信任假设。6个签名就能升级，那么只要有6个人合谋或者同时被攻破，资产就不安全。反过来说，用户相信的是，14个人里至少有9个不会这样。
  4. L2BEAT 把没有升级延迟、没有退出窗口，标为关键风险。这不是代码漏洞，而是信任假设。评估时，要把它写进剩余风险。链专题 C03 会详细讲。
账户层权限 · 据 TRON 官方文档与安全公司公开资料

在 TRON 上，"一个地址 = 一把私钥"不成立

Owner
最高权限，可修改其他权限，增删签名人
Active
日常操作：转账、质押、调合约；可限定操作类型
Witness
超级代表出块相关
每个权限：一组地址 + 各自权重 + 阈值。权重之和达到阈值，操作才执行。
  1. 前面讲的都是合约层的权限。还有一种账户层的权限，以 TRON 为例。以太坊的外部账户只有一把私钥。TRON 账户原生支持多重权限，有 Owner、Active 和 Witness 三类。Owner 是最高权限，可以修改其他权限。Active 负责日常操作。
  2. 每个权限有一组地址，每个地址有权重，权限有阈值，权重之和达到阈值，操作才执行。
  3. 这带来一种诈骗。受害者在假钱包或钓鱼页泄露了私钥。攻击者不急着转钱，而是把账户的 Owner 和 Active 权限都改成自己的地址。
  4. 受害者仍然能看到余额，但已经转不出去了。转入不需要签名，所以新的 USDT 还在不断转进来。攻击者择机一次全部转走。
  5. 这类骗局常见于场外交易。骗子提供一个有余额却转不出来的账户私钥，诱导对方支付手续费。对开发者的含义是，在 TRON 上收到一个地址，不能假设它由单一私钥控制。
真实案例 · 2022-10 · BNB Chain Token Hub · 据公开复盘

100 BNB 的押金，换来 200 万 BNB

  1. 最后看 BNB Chain 的 Token Hub，以下据公开复盘。跨链消息要由中继者提交。当时，注册中继者只需要支付100个 BNB 的押金。
  2. 攻击者付了押金，成为中继者，再利用证明验证的一个缺陷，伪造了跨链消息。
  3. 凭空铸造了200万个 BNB，按当时价格约5.7亿美元。其中一亿多美元被转出链外，其余被冻结。
  4. 之后的修复硬分叉，把中继者改成了白名单。教训是，只要付押金就能注册，这本身就是一个权限决策。100个 BNB 的门槛，和它能控制的资产规模相比，太低了。
审计清单

八个检查点

① 每个状态修改函数都有权限检查，或"任何人可调"的安全论证
② 没有任何地方用 tx.origin 鉴权
③ 初始化有 initializer；实现构造函数调用 _disableInitializers
④ 不存在用户可控的任意 call / delegatecall 目标
⑤ 所有权转移是两步式
⑥ 角色已拆分；升级与参数修改经过时间锁
⑦ 特权私钥持有者、存放方式、阈值已文档化，有撤销流程
⑧ 部署链的账户模型与以太坊一致吗？
  1. 审计检查点有八个。第一，每个修改状态的函数，都有明确的权限检查，或者有一份任何人调用都安全的论证。第二，没有任何地方用交易发起人鉴权。
  2. 第三，初始化函数有 initializer 修饰，实现合约的构造函数锁死了初始化。第四，不存在用户可以控制的任意调用或委托调用目标。
  3. 第五，所有权转移是两步式。第六，特权角色已经拆分，升级和参数修改经过时间锁。
  4. 第七，特权私钥由谁持有、怎样存放、阈值多少，都已文档化，并有撤销流程。Ronin 就缺了撤销这一步。第八，部署链的账户模型和以太坊是否一致，比如 TRON 的多权限账户。
练一练 · 暂停视频想一想

暂停角色可以暂停提款，没有时间锁。合理吗？

如果暂停私钥被盗，最坏情况是什么？
参考
无延迟是合理的：暂停只能止损，不能转走资金。
最坏情况：攻击者长期冻结提款，造成恐慌或勒索。
缓解：暂停有自动到期；恢复由更高门槛的多签执行；暂停私钥可被快速撤换。
  1. 来练一练。一个协议的暂停角色可以暂停提款，没有时间锁。这个设计合理吗？如果暂停角色的私钥被盗，最坏情况是什么？
  2. 参考答案。没有延迟是合理的，因为暂停只能止损，不能转走资金。最坏情况是，攻击者长期冻结提款，造成恐慌，甚至以此勒索。缓解办法是，让暂停有自动到期时间，恢复由更高门槛的多签执行，并且暂停私钥可以被快速撤换。
小结

记住三件事

  • 每个函数回答"谁可以调用我"；六种缺陷逐一排查。
  • 实现合约本身也要锁死初始化；所有权两步转移。
  • 最小权限 + 多签 + 时间锁；撤销流程和账户模型同样是权限。
