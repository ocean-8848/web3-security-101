一句话理解 · 打个比方

合约是保险柜，运营安全是整栋楼

保安被收买
→ 私钥与签名
门禁系统被改
→ 前端被注入
送货通道被掉包
→ 依赖与供应链
保洁被冒充
→ 社会工程
比喻不准的地方：楼里出事还有保险理赔、警察追回。链上资产被转走，多数情况下追不回来。
  1. 打个比方。合约是保险柜，用最好的钢材做的，也审计过了。运营安全是保险柜所在的整栋楼。保安被收买，对应私钥和签名出问题。门禁系统被改，对应前端被注入。
  2. 送货通道被人掉包，对应依赖库和供应链被投毒。保洁被冒充，对应社会工程。这些情况发生时，保险柜再硬也没用。
  3. 比喻不准的地方在于，楼里出了事，还有保险公司理赔，有警察追回。链上资产一旦被转走，多数情况下追不回来。
攻击面 · 四类链下根因

社会工程常常是入口

  1. 链下根因可以分四类。第一类是私钥与签名，包括多签签名流程被攻破，以及签名终端和基础设施被入侵。
  2. 第二类是前端与供应链。前端被注入恶意脚本，依赖库被投毒，还有域名被劫持。
  3. 第三类是部署与运维，部署和升级的流水线被污染，持续集成的密钥泄露。第四类是社会工程，假招聘、假承包商、钓鱼邮件。
  4. 四类常常组合出现。社会工程是入口，导致私钥、终端或者流水线被攻破。公开报道多指向有国家背景的长期团队。所以评估要按对方会渗透几个月来设防。
私钥与签名 · 方案对比

每种方案，都有要评估的风险

方案原理优点要评估的风险
单签个人地址一把私钥简单单点 · 绝不用于金库
多签合约链上 M-of-N成熟、透明签名流程 · module 扩展点 · 升级
MPC私钥分片，多方协同签名无完整私钥落地分片分布 · 实现方可信度 · 审批流程
HSM硬件内保管并签名私钥不出硬件谁能让它签 · 访问控制 · 物理安全
  1. 先看私钥与签名。常见的密钥方案有四种。单签的个人地址只有一把私钥，简单，但是单点，绝不能用于金库。
  2. 多签合约是链上的 M 选 N，成熟透明。要评估签名流程、module 这样的扩展点，以及合约能否被升级。
  3. MPC 是多方计算，私钥被拆成分片，多方协同签名，完整私钥从不出现。链上看起来是一个普通的单签地址。要评估分片放在哪里，实现方是否可信，以及审批流程。
  4. HSM 是硬件安全模块，私钥在硬件内保管并签名，不出硬件。要评估的是，谁能让它签名，访问控制和物理安全怎样。
关键认识 · 示例

私钥不落地 ≠ 签的东西是对的

  1. MPC 和 HSM 解决的是，私钥不以完整形态落地。它们没有解决两个问题，谁来授权签名，签的到底是什么。
  2. 来看一个示例。一个 MPC 方案，3个分片，任意2片就能签名。分片 A 和 B 放在两台服务器上，分片 C 在一名员工的手机里。看起来，攻击者要攻破两个地方。
  3. 但 A 和 B 两台服务器，都听同一个审批服务的指令。审批服务说签，它们就签。
  4. 攻击者只要攻破这个审批服务，就同时驱动了 A 和 B，满足了2片的门槛。名义上是3选2，实际上是一个单点。
  5. Bybit、WazirX、Radiant 的问题，都不是私钥被直接偷走，而是合法的签名人被骗着授权了恶意交易。所以上一集的签名流程评估，对任何密钥方案都适用。
私钥与签名 · 评估清单

六个问题

签名人独立性
不同的人、组织、地点、设备？实际几方控制？
签名终端
专机专用？能否收文件、装软件、上网？
独立解码
看到的和签的一致吗？用独立工具核对？
高危操作审批
升级、换签名人、delegatecall 额外审批 + 带外确认
时间锁与限额
大额转出有延迟？单位时间有上限和告警？
轮换与撤销
离职、换岗后权限及时撤销？Ledger：前员工权限未撤
  1. 私钥与签名的评估清单有六个问题。签名人是否独立，实际有几方在控制。签名终端是不是专机专用，能不能收文件、装软件、上网。
  2. 签名人看到的和签的是否一致，有没有用独立工具核对。升级、换签名人、委托调用这些高危操作，有没有额外审批和带外确认。
  3. 大额转出有没有时间锁，单位时间的提币有没有上限和告警。最后一项常被忽略，密钥和权限的轮换与撤销。员工离职或换岗后，权限有没有及时撤销。后面会看到，一个没撤销的账号，就足以引发一次供应链攻击。
前端与供应链 · 评估清单

前端被攻破，用户直接授权给攻击者

前端托管
谁能改线上代码？CDN、托管平台的访问控制与密钥？
依赖锁定
npm 库锁定版本？是否从第三方 CDN 动态加载？
子资源完整性 SRI
外部脚本带哈希校验，被篡改就拒绝执行
域名与监控
注册商账户保护 · DNS 变更审批 · 授权激增告警
  1. 合约再安全，用户也是通过前端交互的。前端被攻破，用户就会直接把授权给攻击者。评估清单的前两项，前端托管，谁能修改线上代码，CDN 和托管平台的访问控制怎样。依赖锁定，npm 库有没有锁定到具体版本，是不是从第三方 CDN 动态加载最新版。
  2. 第三项，子资源完整性。页面引用外部脚本时，写上这个脚本内容的哈希值。浏览器下载后先算哈希。
  3. 如果有人在 CDN 上把脚本换掉了，哪怕只改了一个字符，哈希就对不上，浏览器拒绝执行。这样，托管方被入侵，也注入不了恶意代码。
  4. 第四项，域名和监控。域名注册商账户要有强保护，DNS 记录的变更要审批。还要监控异常授权，比如大量用户突然授权给同一个陌生地址。
真实案例 · 据公开报道

一个改了网页，一个改了依赖库

BadgerDAO · 2021-12 · 约 1.2 亿$

托管服务账户的 API 密钥被获取
向前端注入恶意脚本
诱导用户给攻击者无限授权
约 500 个钱包中招，资金被划走
评估项：前端托管访问控制 · 授权展示 · 授权激增告警

Ledger Connect Kit · 2023-12 · 约 60 万$

前员工的 npm 账户被钓鱼
离职后发布权限没有撤销
发布 1.1.5 – 1.1.7 恶意版本
引用它的网站加载了盗币脚本
评估项：依赖锁定 · 离职权限撤销 · SRI
  1. 来看两种供应链攻击，以下据公开报道。先看 BadgerDAO，2021年12月。攻击者获取了前端托管服务账户的 API 密钥。
  2. 他们用这个密钥向前端注入了恶意脚本。用户打开网站，正常操作时，会被诱导给攻击者的地址一个无限授权。
  3. 大约500个钱包中招，损失约1.2亿美元。对应的评估项，是前端托管的访问控制，钱包授权时的清晰展示，以及授权激增的告警。
  4. 再看 Ledger Connect Kit，2023年12月。这是一个很多 DeFi 网站都在用的钱包连接库。一名前员工的 npm 账户被钓鱼。问题是，他离职后，这个账户的发布权限并没有撤销。
  5. 攻击者用它发布了1.1.5到1.1.7三个恶意版本。凡是动态加载最新版的网站，都把盗币脚本带给了自己的用户。
  6. 直接损失约60万美元，不算大，但波及面极广。对应的评估项，依赖锁定版本，离职权限撤销，以及子资源完整性校验。
部署与运维 · 评估清单

流水线也是攻击面

1脚本化
部署用经过评审的脚本；部署与初始化原子化
2部署后验证
源码验证、参数读取核对、权限移交确认
3CI 密钥
部署私钥不进代码库；最小权限
4升级流程
经时间锁 · 公开 · 验证脚本 · 回滚方案
5变更管理
每次链上变更有审批、有记录、可追溯
  1. 第三类根因是部署与运维。第一，部署要用经过评审的脚本，部署和初始化要在同一笔交易里完成，不给别人抢先初始化的机会。
  2. 第二，部署后验证。在浏览器上验证源码，逐项读取关键参数核对，确认权限已经移交给多签。
  3. 第三，持续集成的密钥。部署私钥和 API 密钥绝不能进代码库，要用密钥管理服务，并且给最小权限。
  4. 第四，升级要经过时间锁，公开，部署后跑验证脚本，并保留回滚方案。第五，任何链上变更都要有审批、有记录、可以追溯。
社会工程 · 据公开报道

人仍是最软的一环

DMM Bitcoin · 2024 · 约 3.05 亿$

冒充招聘者，在职业社交平台接触钱包服务商员工
诱其运行一段"入职测试"代码
终端被控 → 操纵交易请求

Radiant · 2024 · 约 5,000 万$

冒充前承包商，在即时通讯里发来"报告"
文件带木马，开发者终端中招
还被转发给同事，扩散到多个签名人
  1. 第四类根因是社会工程。技术防御再强，人仍是最软的一环。先看 DMM Bitcoin，以下据公开报道。攻击者冒充招聘者，在职业社交平台上接触了 DMM 的钱包服务商的一名员工。
  2. 对方被诱导运行了一段所谓入职测试的代码。他的电脑因此被控制，攻击者进而操纵了交易请求，损失约3.05亿美元。
  3. 再看 Radiant。攻击者冒充一名前承包商，在即时通讯软件里发来一份看似正常的报告文件。文件里带着木马，开发者的电脑中招。
  4. 这份文件还被转发给了同事，扩散到多个签名人。注意这个细节。攻击者不需要逐个攻破签名人，只要让他们彼此信任地转发一份文件。
评估要点 · 运营安全在三类对象中的权重

让"一个人被攻破"不足以造成损失

培训与意识
尤其是开发和签名人员
硬性规定
签名、部署终端上不开外部文件、链接、代码
身份核验
招聘、承包、合作流程
多人与带外确认
单个人被攻破不足以造成损失
评估对象运营安全的权重
A 交易所自有合约与钱包最高 · 签名流程与密钥管理是第一重点
B 自研 DeFi 协议高 · 部署、升级权限、前端、监控
C 上币与合作尽调中高 · 通过问卷了解；深度合作时提升
  1. 社会工程的评估要点有四个。团队，尤其是开发和签名人员，有没有反社会工程的培训。有没有硬性规定，签名和部署用的电脑上，不打开任何外部文件、链接，不运行外部代码。
  2. 招聘、承包和合作流程，有没有身份核验。高危操作是否要求多人和带外确认。目标是，单个人被攻破，不足以造成损失。
  3. 运营安全在三类对象里的权重不同。交易所自有合约和钱包最高，签名流程和密钥管理是第一重点。自研协议要看部署、升级权限、前端和监控。上币尽调通过问卷了解，深度合作时要提高权重。很多项超出了合约评估的传统边界，但报告要明确列出需要安全团队跟进的项，而不是写一句不在范围内就略过。

小结

记住三件事

  • 最大的损失在链下：私钥签名、前端供应链、部署运维、社会工程。
  • MPC 和 HSM 让私钥不落地，但没解决谁授权、签的是什么。
  • 锁定依赖、SRI、离职即撤权；让一个人被攻破不足以造成损失。
