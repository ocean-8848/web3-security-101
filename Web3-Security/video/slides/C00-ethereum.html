参照环境 · 协议升级改变了安全假设

五个升级，每个都动了合约安全的地基

升级改变了什么对安全的影响
EIP-150（2016）外部调用最多转发 63/64 gas调用方总能留一点 gas 收尾
EIP-2929（2021）提高 SLOAD 等 gas依赖 2300 gas 的 transfer 可能失败
EIP-1153（2024）瞬态存储 TSTORE/TLOAD低成本重入锁；新的交易内状态语义
EIP-6780（2024）SELFDESTRUCT 只在同交易内创建的合约删码Parity 式自毁库不再能删码；强制转 ETH 仍可行
EIP-7702（2025）EOA 可委托一段合约代码tx.origin==msg.sender 不再代表普通钱包
  1. 先看以太坊作为参照环境的几个关键升级。EIP-150，外部调用最多转发 63/64 的剩余 gas，所以调用方总能保留一点 gas 收尾。EIP-2929 提高了 SLOAD 等操作的 gas，这导致依赖 2300 gas 的 transfer 可能失败，这是第六集讲过的坑。
  2. EIP-1153 引入瞬态存储，可以做低成本的重入锁，但也带来新的交易内状态语义。EIP-6780 改了自毁，SELFDESTRUCT 只在同一交易内创建的合约上删除代码，Parity 式的自毁库合约不再能删码，但强制转入 ETH 仍然可行。
  3. 最重要的是 EIP-7702，EOA 可以签名委托一段合约代码。这意味着 tx.origin 等于 msg.sender 不再代表调用者是普通钱包。记住这几个升级，它们动的是合约安全的地基，后面的案例会反复用到。

案例一 · EP03 跨函数重入的真实版本

把 transfer 改成 call，就改变了重入面

// ❌ borrow 先转出 ETH，后更新借款记录
function borrowFresh(...) internal {
require(comptroller.borrowAllowed(...) == 0);
doTransferOut(borrower, amount); // ① call{value:} 交出控制权
accountBorrows[borrower].principal = newDebt; // ② 太晚
}
被打破的不变量：外部调用返回前，账本应已反映这笔借款。回调中 Comptroller 读到的借款记录还是 0，于是允许退出抵押市场并取回抵押品。
根本原因：Compound 原版用 transfer（只转发 2300 gas）发 ETH，恰好挡住回调；被攻击的 Fuse 版本改用低级 call，却没同步改成 CEI。锁也没覆盖 exitMarket。
修复：改转账方式必须同时改成先记账后交互；所有读写借贷状态的入口共用一把锁。损失约 8,000 万美元。
  1. 第一个案例，Fei Rari。它是基于 Compound 分叉的借贷池。看这段简化示意，borrow 函数先调用 doTransferOut 把 ETH 转给借款人，这一步对 ETH 市场是一个 call，交出了控制权。然后才更新借款记录，太晚了。
  2. 被打破的不变量是，外部调用返回之前，账本应该已经反映了这笔借款。但攻击者在收到 ETH 的回调里，去退出抵押市场，此时 Comptroller 读到的借款记录还是零，于是允许退出并取回全部抵押品。
  3. 根本原因很有意思。Compound 原版用 transfer 发 ETH，只转发 2300 gas，恰好挡住了回调重入。而被攻击的 Fuse 版本改用了低级 call，把足够的 gas 和控制权交给了接收方，状态更新顺序却没同步调整。而且据公开分析，那把重入锁没有覆盖 exitMarket 函数。这正是第三集跨函数重入的真实版本。
  4. 修复就是，修改转账方式必须同时改成先记账后交互，并且让所有读写借贷状态的入口共用一把锁。教训是，改转账方式就是改重入面。损失约八千万美元。
案例二 · EP06 不可升级合约的上线门槛

11,539 ETH 被永久锁死，起因是比较错了变量

// ❌ 缺陷 2：比较对象写错
function claimProjectFunds() external onlyOwner {
require(refundProgress >= totalBids, "..."); // totalBids 是 NFT 总数
// refundProgress 最多等于出价笔数 _bidIndex < totalBids
// → 条件永远不成立，资金永远提不出
payable(owner).transfer(address(this).balance);
}
缺陷 1（DoS 入口）：退款用推送方式，任何一个出价者合约拒收，整笔回滚，所有人都退不了款。
直接原因：totalBids 是 NFT 数量之和，大于出价笔数；refundProgress 最多到出价笔数，条件永远不成立。合约不可升级，无法修复。
修复：退款改拉取式；资金出口条件必须有端到端测试——写一个"退款完成后项目方能提取"的测试，它会立刻失败。
  1. 第二个案例，Akutars，一个荷兰式拍卖的 NFT 项目。它有两个缺陷。先看提款函数，claimProjectFunds 要求 refundProgress 大于等于 totalBids 才能提款。但 totalBids 是 NFT 数量之和，而 refundProgress 最多等于出价的笔数，出价笔数小于 NFT 总数。
  2. 还有第一个缺陷，退款用的是推送方式，任何一个出价者的合约拒收 ETH，整笔退款就回滚，所有人都退不了款，这是一个 DoS 入口。
  3. 直接锁死资金的是第二个缺陷。那个比较条件永远不成立，项目方永远提不出钱。一万一千多个 ETH，当时超过三千四百万美元，被永久锁在合约里。合约不可升级，无法修复。
  4. 修复有两条。退款改成拉取式。更重要的是，资金出口的条件必须有端到端测试，写一个退款完成后项目方能提取的测试，它会立刻失败，上线前就能发现。教训是，不可升级合约没有维修门，就只能一次做对。
案例三 · EP07 单交易操纵 vs 多区块操纵

TWAP 挡得住闪电贷，挡不住有资本的持续操纵

Harvest（单笔交易）

闪电贷压低 Curve 池内 USDC 价
→ 份额价格 = 持仓估值 ÷ 份额
→ 低价存入、恢复后赎回
约 3,380 万美元

Inverse（多区块）

自有资金推高浅池 INV 价
+ 垃圾交易压制套利回拉
→ TWAP 被持续抬高数个区块
约 1,560 万美元
关键区别：TWAP 能挡住单笔交易的闪电贷操纵，但挡不住有资本、能持续数个区块的操纵——尤其是浅池。低流动性代币不作高抵押率抵押品。
  1. 第三组案例，Harvest 和 Inverse，都是价格操纵，但要对比着看。Harvest 是单笔交易操纵。它的金库份额价格，等于持仓估值除以份额总数，而持仓估值依赖 Curve 池内的稳定币价格。攻击者用闪电贷在一笔交易里压低 USDC 价格，以偏低的份额价格存入，价格恢复后再高价赎回。损失约三千三百八十万美元。
  2. Inverse 不一样，它是多区块操纵，而且项目方强调是资本密集型、非闪电贷。攻击者投入大量自有资金在流动性很浅的 INV 池里推高价格，同时发大量垃圾交易压制套利机器人把价格拉回，于是 TWAP 窗口内的价格被持续抬高了好几个区块。然后以 INV 高价抵押借走约一千五百六十万美元。
  3. 关键区别就在这里。很多人以为用了 TWAP 就安全，但 TWAP 只能挡住单笔交易的闪电贷操纵，挡不住有资本、能持续数个区块的操纵，尤其是浅池。所以低流动性的治理代币，不能作为高抵押率的抵押品。这和 BNB 链上的 Venus XVS 是同一个教训。
案例四 · EP06 持有授权就是持有钥匙

"回调来自我刚调用的地址"≠"那是真实的池子"

address pool = readAddress(route); // ❌ 池子地址来自用户输入
lastCalledPool = pool; IUniswapV3Pool(pool).swap(...); // 恶意池回调
// —— 回调里 ——
require(msg.sender == lastCalledPool); // 只证明"是我刚调用的"
(address tokenIn, address from) = decode(data); // from 可为任意授权用户
IERC20(tokenIn).safeTransferFrom(from, msg.sender, amt);
被打破的不变量：只有真实的 Uniswap 池才能触发回调。校验只认"上一次调用的地址"，而那个地址正是攻击者自己部署的假池子。
修复：用工厂地址和代币对计算出合法池子地址再比较（CallbackValidation）。持有用户授权的合约，任何"用户可控地址"都是攻击入口。约 330 万美元，波及 14 条链。
  1. 第四个案例，Sushi 的路由合约 RouteProcessor2，上线仅四天。用户要先给它授权，它才能代用户交换代币。看代码，交换函数里的池子地址来自用户输入的路由，没有校验是不是真实池子。攻击者填入自己部署的假池子，假池子立即回调。
  2. 回调函数里确实有校验，要求 msg.sender 等于 lastCalledPool。但这只证明了回调来自我刚才调用的地址，而那个地址正是攻击者自己的假池子。校验通过后，它解码出的 from 可以是任意一个授权过的用户，于是把别人的代币转给了自己。
  3. 被打破的不变量是，只有真实的 Uniswap 池才能触发回调。正确做法是用工厂地址和代币对，计算出合法的池子地址再比较，这是 Uniswap V3 的 CallbackValidation 思路。核心教训，持有用户授权的合约，等于持有用户钱包的钥匙，它的任何用户可控地址都必须视为攻击入口。约三百三十万美元被盗，风险波及十四条链。用户侧，只授权需要的额度，不用的及时撤销。
案例五 · EP09/10 时间锁的两面性

同一把时间锁，挡住恶意升级，也挡住快速修复

教训：把权限分两类——可快速执行、只能"停"的守护者权限；必须经时间锁、可以"改"的升级权限。升级前在主网分叉跑不变量："每个用户累计领取 ≤ 按份额应得"。
  1. 第五个案例，Compound 提案 62。治理提案升级了 COMP 奖励分发逻辑，但奖励索引的计算有误。
  2. 升级生效后，部分用户可以领取远超应得的 COMP，可领取量约十六万八千 COMP，创始人估计最坏情况约二十八万 COMP，相当于八千万美元。
  3. 问题是，协议没有任何管理员开关或社区工具可以停止 COMP 分发。任何修复都必须走治理流程，到生产环境需要约七天。在这七天窗口期里，被错误发放的 COMP 只能被动等待。
  4. 教训很深刻。时间锁本来是保护用户免受恶意升级的，但当升级本身有 bug 时，同一把时间锁也阻止了快速修复。所以要把权限分成两类，一类是可以快速执行、只能停的守护者权限，一类是必须经过时间锁、可以改的升级权限。而且升级前应该在主网分叉环境里跑奖励分发的不变量测试，每个用户累计领取不超过按份额应得的，上线前就能发现。

EIP-7702 之后新警告：用"是不是 EOA"来防重入、防闪电贷的代码都要重新审视——委托后的 EOA 带代码、会回调、也会在收 ETH 时执行逻辑。链上超 80% 的 7702 委托指向复制粘贴的"清扫合约"。
  1. 第六组，签名界面事故。WazirX 是印度交易所，用的是四选六多签加一个托管服务商。签名人以为在签一笔日常交易，界面显示的也是正常内容，但发送到硬件钱包签名的数据是恶意的，这笔交易把多签升级成了攻击者控制的版本，约两亿三千万美元被盗。
  2. 七个月后，Bybit 几乎是同一种攻击。Safe 钱包的前端被篡改，签名人盲签了一笔 delegatecall，替换了多签的实现合约，损失高达十五亿美元。同一种攻击，七个月内两次命中大型交易所。防御就是第八集讲的，独立解码 calldata，硬件钱包逐字段核对，对升级和 delegatecall 类操作设置额外审批。
  3. 最后提醒一个新风险。EIP-7702 之后，任何用是不是 EOA 来防重入、防闪电贷或限制调用者的代码，都需要重新审视。因为委托后的 EOA 带有代码、会回调，收到 ETH 时也会执行逻辑。链上统计显示，超过百分之八十的 7702 委托指向复制粘贴的清扫合约，根本问题还是私钥泄露，但 7702 让清扫更便宜、更自动化。
在以太坊主网开发 · 一页清单

把十起事故，变成九条检查项

  1. 把这十起事故浓缩成一页检查清单。重入分析要覆盖所有回调来源，原生 ETH、代币钩子、闪电贷回调、用户指定的池子和路由，还有 EIP-7702 委托的 EOA。不要用 tx.origin 等于 msg.sender 或者 code.length 等于零来判断调用者是普通用户。用瞬态存储锁时确认编译器版本，并对锁做跨函数测试。
  2. 价格来源要区分单笔交易可操纵和多区块可操纵，浅池资产不作高抵押率抵押品。回调校验基于计算出的合法地址，不基于上一次调用的地址。资金出口，提款、项目方领取、退款，都要有端到端测试，不可升级合约尤其如此。
  3. 守护者暂停权和升级权要分离，奖励和铸币类功能要有独立的紧急开关。所有交换有 minOut 和 deadline，关键交易考虑私有通道。多签操作有独立的 calldata 解码与核对流程。这九条，就是这十起事故换来的。
小结

记住三件事

  • 以太坊是原件：读懂主网病历，到哪条链都认得出症状。
  • 协议升级会移动安全假设：EIP-7702 之后，"是不是 EOA"不再可靠。
  • 改转账方式=改重入面；同一模式不同外衣，把新事故对应到已知模式。
