  1. 大家好，欢迎来到主线第9集，可升级合约与代理。留给自己的维修门，也是留给攻击者的门。一句话理解，代理合约保存数据和资金，实现合约提供代码。升级，就是换掉代理指向的实现。谁能换实现，谁就拥有全部资金。
  2. 看三个案例，以下据公开报道。2022年，Nomad 桥在升级时，把可信消息根设成了零，损失约1.9亿美元。

  4. 同年，Compound 的一个升级提案出错，部分用户超额领取奖励，而协议没有紧急开关，修复要等约7天。本集讲三种代理、三类漏洞和安全升级流程。
一句话理解 · 打个比方

代理是保险柜，实现是操作手册

按手册操作柜子
delegatecall：用手册，改柜子
升级 = 换一本新手册
新手册改了格子含义
"第 3 格放现金"改成"放钥匙"
→ 存储冲突
"第一个读到这页的是主人"
没人先读过
→ 未初始化，路人成主人
比喻不准的地方：真实换手册需要时间。没有时间锁时，链上换实现只需一笔交易。
  1. 打个比方。代理合约是一个保险柜，实现合约是保险柜的操作手册。柜员每次都按手册操作柜子，这就是 delegatecall，用手册，改柜子。升级，就是换一本新手册。
  2. 如果新手册把第3格放现金，改成了第3格放钥匙，柜员会把现金当钥匙用。这是存储冲突。
  3. 如果新手册第一页写着，第一个读到这页的人是柜子主人，而没人先读过它，路人就能成为主人。这是未初始化。
  4. 比喻不准的地方在于，真实保险柜换手册需要时间。如果没有时间锁，链上换实现只需要一笔交易。
代理模式

升级权限在哪，风险就在哪

模式升级权限在哪主要风险
透明代理代理的 admin 槽admin 私钥
UUPS实现合约的授权升级函数新实现遗漏升级函数；实现合约未初始化
信标代理信标合约的 owner一次升级影响全部实例
钻石 EIP-2535diamondCut 的权限多个 facet 共享存储，冲突面最大
  1. 代理有几种模式。透明代理，升级逻辑在代理里，管理员调用代理时不转发，避免和实现函数冲突。升级权限在代理的管理槽，风险是管理员私钥。
  2. UUPS，升级函数在实现合约里。如果新实现忘了包含升级函数，合约就再也不能升级。还要防实现合约未初始化。信标代理，多个代理共享一个信标，一次升级影响所有代理，适合大量相同的合约。
  3. 还有钻石模式，把逻辑拆成多个切面。升级权限在切面管理函数，多个切面共享存储，冲突面最大。四种模式都依赖 delegatecall，都有存储冲突风险。
漏洞一 · 代理变量和实现变量撞槽

写 owner，就是写 implementation

  1. 第一类存储冲突，代理自己的变量和实现的变量撞在同一个槽。看一个朴素代理，它把实现地址放在第0个槽位。
  2. 实现合约里，owner 也在第0个槽位。因为 delegatecall 用的是代理的存储。
  3. 当实现合约执行设置 owner 的代码，改的是第0个槽，也就是代理的实现地址被改成了一个 owner 地址。
  4. 下一次调用，代理会把这个 owner 地址当作实现合约去 delegatecall，合约彻底坏掉。修复是用 EIP-1967 定义的固定伪随机槽位，存放实现地址，第2集讲过那个以3608开头的位置，几乎不可能和普通变量重合。
漏洞一 · 升级前后布局不一致 · 在前面插入 uint256 feeBps

插入一个变量，后面全部错位

别靠肉眼数槽位：插入一个 bool 会和后面的 owner 打包，错位方式完全不同。用 forge inspect 或 solc 的 storageLayout 确认。
  1. 第二类存储冲突，升级前后布局不一致。看一个例子，V2 想在最前面插入一个手续费变量。V1 的布局是，第0槽 owner，第1槽总存款，第2槽余额映射，第3槽初始化标志。
  2. V2 在最前面插入了手续费，于是第0槽变成手续费，而它读到的，其实是旧的 owner 地址，被当成了一个巨大的整数。
  3. 第1槽本该是手续费后面的 owner，却读到了旧的总存款的低20字节，变成一个错误的地址。
  4. 第2槽读到映射的占位槽，恒为零。第3槽的映射基址变了，所有用户的余额全部消失。一个变量的插入，后面全部错位。
  5. 正确的做法是，只在末尾追加变量，不删除、不重排、不改类型，父合约预留空隙槽位，并用工具比对新旧布局。注意，插入一个布尔值，错位方式又完全不同，所以别靠肉眼数槽位。手册里的存储实验，可以看到哪个槽被错误解释。
漏洞二 · 初始化

四种情况，都和"谁先初始化"有关

情况后果修复
部署后没在同一笔交易里初始化攻击者抢跑调用，成为 owner部署与初始化原子化
初始化可重复调用任何人重置 ownerinitializer 修饰器
实现合约本身没初始化攻击者成为实现 owner；若实现有 delegatecall / 自毁 → 破坏所有代理构造函数 _disableInitializers
V2 新初始化用了 initializer已初始化过，V2 初始化永不执行reinitializer(2)
  1. 第二类漏洞是初始化缺失，四种情况。第一，部署代理后，没有在同一笔交易里初始化，攻击者抢跑调用初始化，成为 owner。修复是部署与初始化原子化。第二，初始化可以重复调用，任何人都能重置 owner，修复是加 initializer 修饰器。
  2. 第三，实现合约本身没初始化。攻击者成为实现合约的 owner，如果实现里有 delegatecall 或自毁逻辑，就能破坏所有指向它的代理。这正是 OpenZeppelin 那个公告，也和2017年 Parity 第二次事故是同一类问题。修复是在实现合约的构造函数里禁用初始化。
  3. 第四，V2 新增的初始化逻辑，如果还用普通的 initializer 修饰器，因为已经初始化过了，V2 的初始化永远不能执行。修复是用可重复初始化的版本，指定版本号。
真实案例 · 2022-08 · 据公开复盘

"零值"有了业务含义

  1. 来看 Nomad，以下据公开复盘。Nomad 在一次升级中，调用初始化函数，把可信消息根设成了零。
  2. 而合约逻辑里，未经证明的消息，默认对应的根也是零。于是，任何消息的根都等于零，都被视为已证明。
  3. 第一个攻击者成功后，其他人只需要复制他的交易，替换收款地址，就能提款。数百个地址参与哄抢，损失约1.9亿美元。
  4. 三条教训。第一，升级时的初始化参数，和代码一样需要审计。第二，零值不能有业务含义，默认值和合法值必须可区分。第三，升级后要跑回归测试，覆盖未授权消息必须被拒绝这一条。
对照案例 · 2021-09 · 据公开报道

时间锁挡住恶意升级，也挡住紧急修复

  1. 再看一个对照案例，Compound 提案62，2021年9月。升级后的奖励逻辑有误，部分用户可以超额领取奖励代币，最坏情况约28万枚，约8000万美元。
  2. 问题是，协议没有一个可以停止奖励分发的紧急开关。任何修复，都要走约7天的治理流程。在这7天里，错误的奖励还在继续发放。
  3. 和 Nomad 对比，一个是升级权太容易被利用，一个是没有紧急开关，修复太慢。教训是，时间锁挡住了恶意升级，但也挡住了紧急修复。所以，暂停权和升级权要分开设计，暂停要快，升级要慢，第4集讲过。
链视角 · 截至 2026 年公开资料

可升级的不只是 DeFi 合约

链可升级的关键组件由谁升级
BNB Chain系统合约、共识规则硬分叉（Moran 修复了 Token Hub）
TRON网络参数、TVM 功能开关超级代表投票通过提案
MantleL1 桥、输出预言机、门户安全多签 6/14 可无延迟升级；工程多签 3/7 可暂停提款
在 L2 上部署的协议，其安全上限是 L2 本身的升级权限。桥能被无延迟升级 → 协议再安全，资产也可能在 L1 端被转走。
  1. 可升级的不只是 DeFi 合约，链本身也可以。BNB Chain 的系统合约和共识规则，通过硬分叉升级，比如 Moran 硬分叉修复了 Token Hub。TRON 的网络参数和功能开关，由超级代表投票通过提案。
  2. Mantle 的一层桥、输出预言机和门户合约，据 L2BEAT，安全多签6选14可以无延迟升级，工程多签3选7可以暂停提款。
  3. 这里有一条重要的警告。在二层网络上部署的协议，它的安全上限，就是二层网络本身的升级权限。如果二层的桥可以被无延迟升级，那么协议写得再安全，资产也可能在一层网络那一端被转走。评估时一定要披露这个信任假设。
安全升级 · 八步

升级交易本身也要审计

  1. 安全升级流程八步。第一，编写新实现，只追加变量。第二，用工具比对存储布局，输出差异报告。第三，在主网分叉环境执行升级，跑全部回归测试和不变量测试。
  2. 第四，审计新实现，以及升级交易本身，包括初始化参数。Nomad 就是升级交易的参数出了错。第五，通过时间锁排队，公开升级内容。
  3. 第六，延迟期内，监控和社区复核。第七，执行升级，立刻跑部署后验证脚本，读关键变量，做小额端到端操作。
  4. 第八，保留回滚方案。如果新实现有问题，能不能升级回旧实现，旧实现和新布局是否兼容。整个流程的核心是，升级交易本身，和代码一样需要审计。
审计清单

八个检查点

① 代理用 EIP-1967 槽位；没有自定义变量放在低位槽
② 新旧实现存储布局已用工具比对
③ 实现合约构造函数调用 _disableInitializers
④ 代理部署与初始化在同一笔交易完成
⑤ UUPS 新实现包含升级函数，且权限正确
⑥ 升级权限经过多签和时间锁
⑦ 初始化参数中没有"零值具有业务含义"
⑧ 对部署所在 L2 的升级信任假设做了披露
  1. 审计检查点八个。第一，代理用 EIP-1967 槽位，没有自定义变量放在低位槽。第二，新旧实现的存储布局已经用工具比对过。
  2. 第三，实现合约的构造函数调用了禁用初始化。第四，代理的部署与初始化在同一笔交易完成。
  3. 第五，UUPS 的新实现包含升级函数，并且权限正确。第六，升级权限经过多签和时间锁。
  4. 第七，初始化参数中，没有零值具有业务含义的情况。第八，对部署所在二层网络的升级信任假设，做了披露。
练一练 · 暂停视频想一想

UUPS 升级到 V2，V2 的授权升级函数被写成空函数

会发生什么？
参考
授权升级函数是 UUPS 检查升级权限的地方。写成空函数 = 没有任何权限检查 → 任何人都能升级这个合约，把实现换成恶意合约，接管全部资金。
修复：授权升级函数必须有权限修饰器；升级流程验证新实现的该函数。
  1. 来练一练。一个 UUPS 合约升级到 V2 后，V2 的授权升级函数被写成了空函数。会发生什么？
  2. 参考答案。授权升级函数，是 UUPS 检查升级权限的地方。写成空函数，等于没有任何权限检查，任何人都能升级这个合约，把实现换成恶意合约，接管全部资金。这比不能升级更危险。修复是，授权升级函数必须有权限修饰器，而且升级流程要验证新实现的这个函数。
小结

记住三件事

  • 谁能换实现谁就有全部资金；用 EIP-1967 槽位，只在末尾加变量。
  • 实现合约锁死初始化；零值不能有业务含义（Nomad）。
  • 升级交易本身要审计；暂停权与升级权分开；L2 升级权是安全上限。
