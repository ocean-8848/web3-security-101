  1. 大家好，欢迎来到评估篇第3集。这一集讲第一类评估对象，交易所自己的合约和钱包。先记住一句话。交易所的链上资产，绝大部分时间安全地躺在冷钱包里。损失却发生在签一笔交易的那几秒。
  2. 看三起事故，以下据公开报道。2025年2月，Bybit 冷钱包被盗，约14.6亿美元。签名人看到的界面被篡改了。
  3. 2024年7月，印度交易所 WazirX 被盗约2.3亿美元。签名人看到的内容，和实际签的数据不一致。
  4. 2024年10月，借贷协议 Radiant 被盗约5000万美元。签名人的电脑被植入木马。三起事故，合约本身都没有新漏洞。所以本集的重心不是合约代码，而是签名流程。
一句话理解 · 打个比方

交易所金库像银行运钞流程

金库的锁
很难撬开
→ 多签阈值
伪造调拨单
押运员按正常流程把钱运出
→ 签名界面被篡改
押运员电脑里有木马
以为签 A，实际签了 B
→ 终端被入侵
比喻不准的地方：运钞单可以打电话复核、可以追回。链上交易一旦达到阈值并广播，没有撤回。
  1. 打个比方，交易所的金库像银行的运钞流程。金库的锁很难撬开，对应多签的阈值。
  2. 但劫匪不撬锁。他们伪造一张调拨单，让押运员按正常流程把钱运出来。对应到链上，就是签名界面被篡改。
  3. 或者，他们在押运员的电脑里装了木马。押运员以为在签 A，实际签了 B。这就是终端被入侵。
  4. 比喻不准的地方在于，银行的运钞单可以打电话复核，出了事还有机会追回。链上交易一旦达到签名阈值并广播，就没有撤回。
攻击面

链上五块，链下四块；损失多在链下

  1. 先画出攻击面。链上有五块。热钱包负责日常提币。冷钱包或者多签，负责大额存储。还有充值地址和归集合约，提币和批量转账合约，以及交易所对外部协议的授权。
  2. 链下有四块。签名服务，可能是多签、MPC 或者硬件安全模块。签名界面，比如多签的网页前端。签名人的电脑。还有部署和升级的流水线。
  3. 看箭头。签名人在电脑上，通过签名界面，驱动签名服务，最终让冷钱包动起来。冷钱包的升级和换签名人，也要经过部署流水线。
  4. 红色的四块全在链下。开场那三起事故，加上另一起 DMM，合计损失超过20亿美元，根因都在这里。所以评估的重点，是谁能让冷钱包动，怎么让它动。

签名验证
合约签名、零地址、签名可塑性 · 见第 08 章
  1. 合约层先看钱包和多签合约，有五个检查点。第一，用的是经过审计的标准实现，比如 Safe，还是自研的。自研必须单独深审。
  2. 第二，实现能不能被替换。谁能升级，有没有时间锁。Bybit 就是这样，一笔 delegatecall 交易把钱包的实现换掉了。
  3. 第三，所有权转移。是不是两步式，能不能被一笔交易直接夺走。Radiant 的签名人，就是盲签了一笔所有权转移。
  4. 第四，扩展点。Safe 的 module 可以绕过签名阈值直接执行交易，等于一把额外的钥匙。guard 也会改变签名逻辑。要列出所有已启用的扩展点，逐个评估。
  5. 第五，签名验证是否正确处理了合约签名、零地址，以及签名可塑性。这些在第8章讲过。
合约层 · 充值入账 · 示例

入账要幂等：同一笔转账，只能记一次

收到的事件按 txHash 去重按 (txHash, logIndex) 去重
0xab… 第 3 条日志 · 500 USDT+500+500
0xab… 第 7 条日志 · 300 USDT漏记+300
0xab… 第 3 条日志 · 重放忽略忽略
按序号去重 · 重组后重放+500 重复忽略
  1. 再看充值。充值入账有一条铁律，幂等。同一笔转账，只能记一次账。来看一个示例。
  2. 一笔批量转账交易里，有两条转账日志。第3条给用户转500 USDT，第7条转300 USDT。如果只按交易哈希去重，第7条会被当成重复，漏记了300。
  3. 正确的键是交易哈希加日志序号。两条都入账，同一条日志重放时被忽略。
  4. 反过来，如果用自增序号之类不稳定的键，链重组后同一事件被重新推送，就会重复入账500。
  5. 还有两点。识别资产要用代币合约地址，不能用符号，因为任何人都能部署一个叫 USDT 的代币。还要校验交易执行结果。TRON 上就出现过执行失败的交易被当成充值的假充值。确认数要按链设置，考虑重组。
合约层 · 授权敞口 · 数字为示例

无限授权：对方出事，你的余额就是敞口

  1. 交易所做市、理财或质押时，会给外部协议授权，让对方能从我们的地址划走代币。这里的风险是授权额度。
  2. 来算一个示例。做市地址里有5000万 USDT，给一个外部协议设置了无限授权。某天这个协议被攻破，攻击者能划走的上限，就是这个地址的全部余额，5000万。
  3. 改成按需授权。每次只授权本次操作需要的数额，比如100万，用完撤销。同样的事故，敞口降到100万以内。
  4. 还要看一点。持有授权的内部合约，是否允许调用任意目标和任意数据？如果允许，攻击者可以借它的手，调用代币的转账函数，把授权给它的钱转走。这在第6章讲过。
重点 · 签名流程评估

多签的安全，不等于 M-of-N

环节要问的问题反面案例
签名人独立性不同的人、组织、地点、设备？实际几方控制？Ronin
终端安全专机专用？能否收文件、装软件、上网？Radiant
交易构造与展示看到的内容和签署的数据是否一致？Bybit、WazirX
独立解码是否用不同于构造方的工具解码核对？硬件钱包盲签
高危操作审批升级、换签名人、delegatecall 额外审批？Radiant
带外确认大额交易通过电话或线下二次核对哈希？多数被盗所缺
时间锁与限额大额转出有延迟？单位时间有上限？—
  1. 评估一个多签托管方案，要看整条签名链路。第一个环节是签名人独立性。N 个签名人，是不是不同的人、不同的组织、不同的地点和设备？实际上有几方在控制？
  2. 第二是终端安全，签名用的电脑是不是专机专用，能不能收文件、装软件、上网。第三是交易的构造和展示，签名人看到的，和实际签的，是不是一回事。
  3. 第四是独立解码。签名人是否用一个不同于构造方的工具，自己解码交易数据并逐字段核对。如果硬件钱包无法解析交易内容，签名人就是在盲签。
  4. 第五，升级、换签名人、delegatecall 这些高危操作，有没有额外的审批。第六是带外确认，大额交易是否通过电话或线下，二次核对交易哈希。
  5. 第七是时间锁和限额，作为最后的兜底。下面先用一个数字例子，看看签名人独立性为什么排第一。
真实案例 · 2022-03 Ronin 跨链桥 · 据公开报道

9 选 5 看起来很稳，实际要攻破几方？

  1. 来看 Ronin 跨链桥，以下据公开报道。2022年3月，Ronin 桥被盗约6.2亿美元。它的验证人是9选5，需要5个签名才能放行提款。看起来，攻击者要攻破5个独立的验证人。
  2. 但这9把钥匙里，有4把由同一家公司运营。攻破这家公司的系统，就同时拿到了4把。
  3. 还差1把。此前为了分担负载，一个合作的组织曾授权这家公司代为签名，这个授权后来没有撤销。于是第5个签名也能从同一家公司的系统里拿到。
  4. 算一下。名义上要攻破5方，实际上只要攻破1方。阈值是5，独立方的数量是1。评估多签时，要问的不是有几把钥匙，而是实际有几个独立的控制方。
理想形态 · 每个签名人独立完成

不依赖构造系统给的摘要

  1. 签名流程的理想形态是这样的。发起人提出转账请求，构造系统生成交易数据和一份人类可读的摘要，发给签名人。
  2. 关键在接下来几步。签名人不看构造系统给的摘要，而是用一个独立的工具，自己解码交易数据。目标地址、金额、调用的函数，以及是不是 delegatecall。
  3. 如果是高危操作，再通过带外渠道，比如电话，和发起人核对交易哈希。
  4. 最后在硬件钱包上，逐字段核对，再签名。每个签名人独立重复这些步骤，达到阈值后广播。
  5. 这条流程防的是构造系统或界面被攻破。如果所有签名人都只看同一个摘要，那么不管阈值多高，整个多签都退化成一个单点。

据公开报道，Bybit 那笔交易表面上是转账，实际 operation = 1，钱包实现被替换，随后资金被转走。
  1. 独立解码具体看什么？以 Safe 多签的交易为例。先看三个基本字段。to 是目标地址，value 是转出多少原生币，data 是调用哪个函数、带什么参数。
  2. 最关键的是 operation 这个字段。0 是普通调用，代码在目标合约里执行。1 是委托调用，也就是 delegatecall。目标合约的代码会在钱包自己的存储里执行，可以改写实现地址、签名人和阈值。日常转账几乎用不到委托调用，看到1，立刻停下。
  3. 还要看 nonce，确认这是第几笔交易，防止有人插队，或者让你签一笔预先准备好的交易。
  4. 据公开报道，Bybit 那笔交易，界面上显示的是一笔正常的转账。实际的 operation 是1，钱包的实现被替换成攻击者的合约，随后资金被转走。
事故 → 评估项

合约没有新漏洞，失守的是"人签了什么"

事故根因环节对应评估项
Bybit · 2025-02签名界面被篡改 → delegatecall 替换实现交易展示 · 独立解码 · 高危审批 · 升级机制
WazirX · 2024-07界面与签名数据不一致 → 多签被升级交易展示 · 独立解码 · 带外确认
Radiant · 2024-10终端被木马入侵 → 盲签所有权转移终端安全 · 独立解码 · 所有权两步式
评估托管方案时，把约 60% 的精力放在签名流程上。
  1. 把三起事故映射到评估项上。Bybit 的根因是签名界面被篡改，导致一笔 delegatecall 替换了钱包实现。对应的评估项，是交易展示、独立解码、高危操作审批，以及钱包的升级机制。
  2. WazirX 的根因是界面和签名数据不一致，多签被升级。对应交易展示、独立解码和带外确认。Radiant 的根因是终端被入侵，签名人盲签了所有权转移。对应终端安全、独立解码，以及所有权转移是否两步式。
  3. 三起的共同点是，合约本身没有新漏洞，失守的是人签了什么。所以评估一个托管方案，建议把大约六成的精力放在签名流程上。
兜底 · 数字为示例

流程挡不住集体被骗，限额能把损失封顶

  1. 流程再严，也挡不住签名人集体被钓鱼，或者被胁迫。所以还要有兜底，就是时间锁和限额。来看一个示例。
  2. 没有限额时，冷钱包里有3亿美元。一旦签名被骗，一笔交易就能全部转走。
  3. 加上限额。示例里，冷钱包每24小时最多转出2000万，超过的部分进入48小时时间锁。同样被骗，第一天最多损失2000万。
  4. 时间锁里的大额转出，会触发告警。只要在48小时内发现并取消，剩下的2亿8000万都保得住。限额的意义，不是防住攻击，而是把最坏结果从全部，变成一个能承受的数字。

小结

记住三件事

  • 交易所资产的重心是签名流程，不是多签阈值。
  • 问"实际有几个独立控制方"；独立解码，看到 operation = 1 立刻停。
  • 入账幂等、按需授权、限额与时间锁兜底。
