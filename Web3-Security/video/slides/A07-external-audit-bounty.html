能当上线依据吗？

审的是哪个提交？上线的是同一个吗？
哪些文件没审？"已确认风险"写了什么？
  1. 大家好，欢迎来到评估篇第7集，外部审计与漏洞赏金。先看一个画面。项目方发来一份审计报告，封面写着，未发现严重问题。这一页，能当作上线依据吗？
  2. 答案是，还不能。你至少要问，审的是哪个提交，上线的是不是同一个，哪些文件没审，报告里的已确认风险写了什么。本集讲怎样选审计、界定范围、读报告，以及怎样设计漏洞赏金。整个立场是，外部审计是自评的补充，不是替代。
一句话理解 · 打个比方

外部审计像会诊：你仍是主治医生

主治医生
最了解病人，对结果负责
→ 你，内部评估
会诊医生
第二双眼睛，发现盲区
→ 外部审计
会诊范围
只看你给的检查结果和时间窗
→ 范围外的责任还在你
比喻不准的地方：医生有行医资质门槛。审计公司水平参差，范围和深度差异很大，报告质量要自己判断。
  1. 打个比方，外部审计像请第二位医生会诊。你是主治医生，最了解病人，也对结果负责。
  2. 请会诊，是因为第二双眼睛能发现你的盲区，而不是因为你不想看了。
  3. 会诊医生只看你给的检查结果，和约定时间内的情况。他看不到的，责任还在你。
  4. 比喻不准的地方在于，医生有行医资质的门槛。审计公司水平参差不齐，范围和深度差异很大，报告质量要你自己判断。
什么时候用哪种

五种方式互补，不互斥

方式适合特点局限
单家审计常规上线固定团队、深度审查受团队经验限制
多家审计核心协议、大额资金不同团队侧重不同成本高，可能重复
审计竞赛需要广覆盖大量审计者并行，按发现付费深度不均，消化报告耗时
形式化验证核心数学、清算、桥验证数学证明覆盖所有输入只证明写下的性质
漏洞赏金上线后持续真实攻击者视角，长期被动，依赖奖金吸引力
  1. 外部检查有五种方式。单家审计适合常规上线，一个固定团队在固定时间里深度审查，局限是覆盖面受这个团队的经验限制。多家审计适合核心协议和大额资金，不同团队侧重不同，代价是成本高。
  2. 审计竞赛是大量审计者并行审查，按发现付费，覆盖面广。但深度不均，你还要花时间消化大量提交。形式化验证用数学证明覆盖所有输入，适合核心数学、清算和桥的验证逻辑。
  3. 注意形式化验证的局限，它只证明你写下的性质。性质写漏了，证明再严谨也没用。最后是漏洞赏金，上线后持续运行，用真实攻击者的视角补充一次性审计，但它是被动的。
典型组合 · 时间为示例

自评在前，赏金在后，审计在中间

  1. 一个核心协议的典型组合是这样的。第一步永远是自评，按前几集的方法，示例里两到三周。
  2. 然后是外部审计，一家或者两家，示例里各两到三周。两家可以并行，也可以串行，串行的好处是第二家能看到第一家修复后的代码。
  3. 对核心数学模块，比如清算和份额计算，再加上形式化验证。
  4. 修复之后要复审。上线后，漏洞赏金长期运行。注意，自评一定在审计之前。不要让审计方从零开始，花一半时间去理解你本该写清楚的东西。

Nomad 类问题出在这里
  1. 你交给审计方的材料，决定了审计的质量。六项要写清。提交哈希，不是分支名，审计期间代码冻结。范围内和范围外的文件，以及哪些外部依赖视为可信。
  2. 规格文档和关键不变量，让审计方知道代码应该是什么样。你的威胁模型和自评发现，也一并给出。不要让审计方从零开始，也不要隐瞒已知问题，否则你花钱请人重复你的工作。
  3. 链下组件，比如前端、签名和部署，默认应该在范围内。部署脚本和初始化参数也必须在范围内，Nomad 那类问题就出在这里。
差异审计 · 示例

"只改了一行"，也要审

  1. 审计结束到上线之间，代码常常还会改。来看一个示例。审计的是提交 a1b2，准备上线的是提交 e9f0。
  2. 两个提交之间有三处改动。一处改了常数，一处调整了函数顺序，还新增了一个管理函数。项目方说，都是小改动。
  3. 这时审计报告的结论，对 e9f0 已经不完全适用了。正确的做法是差异审计，只审这三处改动，以及它们影响的路径。工作量不大，但不能省。
  4. 第1集讲的 Uranium，就是改了一个常数。任何在审计之后、上线之前的改动，哪怕只有一行，都要走差异审计。上线前，再比对一次链上字节码和审计版本。
读报告 · 按顺序

六个步骤

1范围与版本
哪个提交？和上线的一样吗？哪些文件没审？
2方法与工时
人工 + 哪些工具？投入多少人天？
3发现与修复状态
等级、是否已修复、有没有复审
4已确认风险
审计方指出、项目方选择不修
5假设与免责
"假设预言机可信""假设 owner 不作恶"
6范围外提示
"未审计 X" = 你的盲区
  1. 拿到一份报告，按六个步骤读。第一步，范围与版本。审的是哪个提交，和上线的是不是同一个，哪些文件没审。
  2. 第二步，方法与工时。人工审查加了哪些工具，投入多少人天。用第1集的速度估一下，工时太短的报告，覆盖必然有限。
  3. 第三步，每条发现的等级、是否已修复、有没有复审记录。
  4. 第四步，已确认风险。这是最容易被忽略、却最重要的部分，下一页单独讲。
  5. 第五步，假设与免责。报告假设了什么，比如假设预言机可信，假设 owner 不作恶。这些假设，就是你的剩余风险。第六步，范围外提示。报告里写着未审计的部分，就是你的盲区。
重点 · Acknowledged Risk

"已确认"不等于"已解决"

报告里的写法 · 示例项目方回复你要判断的
owner 可随时暂停所有转账"设计如此"owner 是谁？交易所热钱包会被冻吗？
价格来自单一现货池"后续版本改进"上线时池子多深？闪电贷能推动吗？
升级无时间锁"由多签控制"多签几方独立？签名流程如何？
审计方的职责到"指出"为止。接不接受，是你的决定，要按 A02 的流程独立判断。
  1. 已确认风险，是审计方指出了、项目方选择不修的问题。看三个示例。第一，owner 可以随时暂停所有转账，项目方回复设计如此。你要判断的是，owner 是谁，交易所的热钱包会不会被冻结。
  2. 第二，价格来自单一现货池，项目方回复后续版本改进。你要判断，上线时这个池子有多深，闪电贷能不能推动它。
  3. 第三，升级没有时间锁，项目方回复由多签控制。你要判断，这个多签有几方是独立的，签名流程怎样。
  4. 为什么这部分比已修复的发现更需要你亲自判断？因为审计方的职责到指出为止。接不接受这个风险，是你的决定，要按第2集的风险接受流程独立判断。
警惕

五个红旗，"通过审计"可能只是营销

红旗含义
审计版本与上线版本不同结论可能不适用
只有一句"无严重问题"缺少过程，无法判断覆盖
工时极短、范围极大走过场
全部"已修复"，但没有复审记录修复可能引入新问题
不列假设，不列范围外剩余风险不明
  1. 审计报告有五个红旗。第一，审计版本和上线版本不同，结论可能不适用。第二，整份报告只有一句无严重问题，缺少过程，你无法判断它覆盖了什么。
  2. 第三，工时极短而范围极大，比如两个人审三天，范围是两万行代码，基本是走过场。第四，所有发现都写着已修复，但没有复审记录，修复本身可能引入新问题。
  3. 第五，不列假设，不列范围外。剩余风险完全不明。做上币尽调时要特别注意，通过审计是一个常被滥用的营销说法。要核验报告本身，而不是听信已审计三个字。
漏洞赏金 · 上线后的持续防线

七个要素

要素说明
范围哪些合约、前端、基础设施；链上地址明确
严重度分级与内部定级同一口径（A02）
奖金分级严重级常按"可能损失的一定比例"并封顶
排除项已知问题、测试网、需要不现实前提的攻击
提交与响应流程接收渠道、响应时限、修复时限、付款流程
安全港对善意研究者的法律豁免，鼓励上报而非利用
合规付款前的身份与制裁检查
  1. 漏洞赏金是上线后的持续防线。一个赏金计划有七个要素。第一是范围，哪些合约、前端和基础设施在范围内，链上地址要写明确。第二是严重度分级，和内部定级用同一个口径。
  2. 第三是奖金分级，严重级通常按可能损失的一定比例计算，再设一个上限。第四是排除项，比如已知问题、测试网，以及需要不现实前提的攻击。
  3. 第五是提交和响应流程。白帽发现严重漏洞时，每一小时都可能有攻击者在找同一个洞，所以响应时限要写死。第六是安全港，给善意研究者法律豁免，鼓励他们上报而不是利用。第七是付款前的合规检查。
奖金设计 · 数字为示例

和攻击者的收益比一比

  1. 严重漏洞的奖金应该设多高？来算一个示例。协议锁仓1亿美元，一个严重漏洞最多能盗走其中2000万。
  2. 示例规则是，严重级奖金为可能损失的10%，上限200万美元。2000万的10%是200万，正好在上限内。
  3. 和攻击者比一比。攻击者利用这个漏洞，名义收益2000万。但他要洗钱，要承担被追踪、被冻结和法律的风险，实际能落袋的远少于此。白帽上报，拿到200万，合法、安全。
  4. 奖金太低，比如只给5万，有能力的研究者不会花时间看你的协议，发现了也可能被诱惑。奖金太高，预算失控，还会吸引大量低质量提交。原则是，让上报明显比利用更划算。
  5. 最后提醒，漏洞赏金不能替代审计和自评。它是被动的，依赖运气和奖金的吸引力，是最后一道网，不是第一道防线。
职责边界

主责始终在内部

内部没有能力读懂报告时，"外包安全"就变成了"外包责任的错觉"。
  1. 最后把内外协作串起来。内部评估是主责，负责界定范围、冻结版本，再交给外部审计或竞赛，做独立检查。
  2. 报告回来，由你批判性地阅读，判断剩余风险，然后做门禁结论。外部审计是输入，不是决策。
  3. 上线之后，漏洞赏金持续运行。新的发现回流到内部评估，触发修复，必要时重新评估。
  4. 这条链有一个前提，内部有能力读懂和判断审计报告。能力不足时，外包安全就变成了外包责任的错觉。这正是整个评估篇想帮你避免的。

  1. 来练一练。你收到一份审计报告，结论是未发现严重问题。在把它作为上线依据之前，你要核对哪五件事？可以先暂停想一想。
  2. 参考答案。第一，版本，审计的提交、上线的提交和链上字节码三者一致。第二，范围，哪些文件没审，链下组件和部署脚本在不在范围内。
  3. 第三，工时，投入的人天和代码量是否匹配。第四，已确认风险，逐条独立判断，必要时走风险接受流程。
  4. 第五，假设。报告里的每一条假设，都是你的剩余风险，要写进门禁结论。做到这五件事，那一页封面才真正有意义。
小结

记住三件事

  • 外部审计是补充：范围写死提交哈希，审计后的改动走差异审计。
  • 读报告重点看已确认风险、假设、范围外，并独立判断。
  • 赏金让上报比利用更划算；它是最后一道网。
