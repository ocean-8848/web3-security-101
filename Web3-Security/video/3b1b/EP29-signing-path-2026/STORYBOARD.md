## 1. 概要

- **一句话核心观点**：私钥保护回答"谁拿着钥匙"，签名路径回答"谁决定钥匙盖在什么文件上"；近两年的大额事件，攻击者多数控制了后者。防御是：每一层重新检查、关键输入多个来源、响应覆盖链上状态。
- **支撑结构**：MPC 只保证完整私钥不出现，不判断该不该签 → 签名路径七个环节 + 数据源，每个箭头是一次信任传递 → 六起事件打在不同环节，结果相同 → 三个共同点 → 三类防御（账本绑定 + 全类型策略；多数据源 + 部署隔离；链上监控 + 紧急撤销）。
- **关键术语**：签名路径、MPC、账本绑定签名、策略引擎（默认拒绝、读原始待签字节）、EIP-7702 委托（`0xef0100` 前缀、授权元组 `0x05`）、Safe `operation = 1`、Solana 持久 nonce、DVN / RPC 数据源、分链熔断、撤销路径。
- **目标观众**：知道钱包和多签是什么，但没有设计过签名服务的人。
- **时长**：7 分 54 秒（473.9 秒，10 个场景，56 个镜头）。

## 3. 叙事结构

1. **钩子**（hook）：2026-10-29 Binance 多链热钱包约 63.4 亿美元（项目方口径）被转走；项目方称未发现私钥泄露；攻击者进入内部签名服务。问题"不偷私钥，怎样拿到签名？"钉在左上角。
2. **铺垫**（mpc）：MPC 分片、合成签名、完整私钥不出现；它不判断该不该签。公章比方及其不成立处。
3. **逐步构建**：
   - path：换问题 → 签名路径七个环节 + RPC 数据源；每个箭头是信任传递。
   - breaks：六起事件逐个打在路径上；结果相同。
   - common：三个共同点，并各自对应一类防御。
   - ledger：第一类防御 · 账本绑定签名（示例数值一步步比对）。
   - policy：第一类防御 · 策略覆盖全部交易类型，默认拒绝，放在原始字节前；7702 授权元组缺口。
   - sources：第二类防御 · 多个独立数据源（KelpDAO）；部署与开发网络隔离（Binance）。
4. **关键洞见**（revoke）：暂停提现不等于撤销权限。委托存活 3 小时 50 分（逐步计算）；链上监控；零地址授权与 nonce 计算（示例 41 → 42）。
5. **回顾**（answer）：回答钩子：攻击者控制的是"谁决定盖在什么文件上"。三句话防御；成立条件：私钥保护仍必要、架构把单人作恶变成多人共谋、多数事件仍是项目方初步说法。预告第 30 集。

## 5. 材料的观点与解读者的判断

- **材料的观点**（第 29 章原文）：
  - 开场：Binance 约 63.4 亿美元（项目方口径）、称没有发现私钥泄露证据、攻击者访问内部签名服务让它代为签名；MPC 只保证完整私钥不出现，不判断"这笔交易该不该签"。
  - 公章比方及其局限（伪造合同可由法院撤销，链上交易多数无法撤销）。
  - 签名路径 ①–⑦ 与数据源 RPC；"每个箭头都是一次信任传递"；六起事件的断点（3.1 图）；"结果相同：签名系统正常运行"；图把每起事件简化为一个断点。
  - 三个共同点与三类防御（3.3、第 4 节开头）；第 4 节是"本手册的示例架构"，Binance 未公布具体方案。
  - 账本绑定签名的伪代码思路、"攻击者能同时写账本和请求时失效"的警告；策略默认拒绝、全交易类型表、"规则写在提现 API 上只保护一条路径"、7702 授权元组 `0x05` 的先猜再看。
  - LayerZero 关于恶意 RPC 只对 DVN 返回伪造数据、DDoS 迫使切换的说法；"不一致时拒绝签名，不做故障转移"；部署令牌、第二人批准看镜像摘要、开发网络无路由。
  - 暂停提现不等于撤销权限；委托存活约 3 小时 50 分（20:20 至次日 00:10 UTC）；`eth_getCode` 以 `0xef0100` 开头告警；零地址授权撤销与 nonce 规则；MPC 没有一把单独私钥可立刻撤销；撤销路径独立、预批准、每季度演练。
  - 架构不能阻止全部内部人作恶，把单人作恶变成多人共谋；第 18 章的私钥控制仍然必要。

## 6. 成立条件、例外和风险

- **金额与口径**：Binance 约 63.4 亿美元是项目方口径；第三方（TRM、Elliptic）估值 63.6–64.3 亿美元。各案金额为事发时美元估值，状态截至 2026-11-09 可能继续变化。
- **未确认部分**：Binance 报告为初步报告（告警时间、提现暂停时间、内部 AI 工具的利用方式、部署令牌完整权限未确认）；WazirX 双方说法冲突、无最终独立报告；Drift 描述来自项目方自身调查；KelpDAO 责任有争议、已进入诉讼；Bitget 产品名与零日细节未公开。视频在相应画面标了"项目方说法 / 争议"，但没有逐案展开。
- **账本绑定的前提**：攻击者不能同时写账本和请求；账本写入权限与签名调用权限分开，并有实时对账。
- **策略的前提**：策略读取原始待签字节并默认拒绝；规则只挂在某个 API 上时，其他路径不受保护。Solana 持久 nonce 的弃用计划尚无确定主网时间（原文 4.3 注），移除前策略仍要覆盖。
- **架构的局限**：不能阻止全部内部人作恶；只把单人作恶变成多人共谋。私钥生命周期控制（第 18 章）仍然必要。
- **撤销的前提**：先切断日常路径，否则撤销可能被覆盖；撤销以 `eth_getCode` 返回空为准；其他链（Solana nonce 账户、XRP、TRON 权限）要分别复查，视频未展开。
- 视频只讲防御与机制，不含针对真实系统的操作步骤。
