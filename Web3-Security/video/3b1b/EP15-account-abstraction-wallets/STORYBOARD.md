## 1. 概要

- **一句话核心观点**：旧模型里签名的意思是"转这笔钱"；账户抽象之后，签名的意思是"允许这段代码替我做事"。签名的含义变大，签错一次的后果也变大；而写在链上的委托，停掉链下服务撤销不了。
- **支撑结构**：钩子（Binance 热钱包被设置 7702 委托，关服务后仍在）→ 签名含义的变化 → 授权书比方及其局限 → ERC-4337 流程与签名覆盖的哈希 → EIP-7702 授权元组、chain_id = 0、tx.origin 假设 → 大额损失来自"合法委托 + 恶意批量" → Session Key 四个维度与累计额度（一步步算）、Cardex → 意图与 Permit2 → 回答与防御。
- **关键术语**：账户抽象、UserOperation、Bundler、EntryPoint、Paymaster、userOpHash、EIP-7702 授权元组 / 委托、批量执行、Session Key、意图 / Solver、Permit2、Passkey。
- **时长**：6 分 17 秒（376.6 秒，9 个场景，49 个镜头）。

## 3. 叙事结构

1. **钩子**（hook）：2026 年 10 月，攻击者经 Binance 内部签名服务给以太坊热钱包设置 7702 委托，目标是攻击者合约；关闭提现服务后委托仍在，约 3 小时 50 分后才清零。问题"账户变成合约后，花钱的到底是谁？"钉在左上角。
2. **铺垫**（meaning、bank）：签名从"转这笔钱"变成"允许这段代码替我做事"；授权书比方，以及比方不成立的地方（链上委托立即生效、可能多链生效）。
3. **逐步构建**：
   - flow：ERC-4337 流程；签名覆盖 userOpHash，编码决定什么受保护；2023 打包漏洞；新的信任边界。
   - delegate：7702 授权元组 → code 指向委托合约；chain_id = 0；tx.origin 假设失效；网站请求委托默认拒绝。
4. **关键洞见**（batch）：大额损失多来自"合法委托 + 恶意批量调用"，钱包必须逐项解码。
5. **延伸**（session、permit）：Session Key 的四个维度、累计额度一步步算、Cardex 共用密钥但范围限制起了作用；意图的风险字段；Permit2 一次无限授权 + 链下签名。
6. **回顾**（answer）：花钱的是签名授权的那段代码；链上委托撤销不了链下；托管策略拒签 7702、监控 0xef0100；Passkey 保护登录不保护内容。预告第 16 集。

## 5. 材料的观点与解读者的判断

- **材料的观点**（第 15 章原文）：
  - 一句话理解（签名从"转这笔钱"到"允许这段代码替我做事"）与授权书比方及其局限。
  - Binance（5.6 节）：经内部签名服务设置 7702 委托，目标是攻击者合约；关闭提现服务后仍有效，约 3 小时 50 分后清零；教训：签名策略识别 type 4、热钱包拒签、监控 `0xef0100` 前缀。
  - ERC-4337 流程、签名覆盖 userOpHash、2023 年打包漏洞（同一 UserOp 不同哈希，已修复无已知损失）。
  - EIP-7702：2025 年 5 月 Pectra 上线；授权元组 `[chain_id, address, nonce]`；chain_id = 0 全链有效（nonce 匹配）；`tx.origin == msg.sender` 失效；EIP 原文"应用不应该请求用户签署委托"。
  - 7702 钓鱼：2025-05 约 14.6 万美元（合法委托 + 恶意批量）；2025-08 约 100 万、154 万美元两起；"主要风险在合法委托上的恶意批量调用"。
  - Session Key 四个维度、"累计不是单笔"；Cardex：共用 session signer、私钥在前端、约 9,000 个钱包、约 40 万美元、ERC-20 与 NFT 未受影响。
  - 意图示例"1 ETH 换至少 3,000 USDC"及风险字段；Permit2 机制；2024-10 PEPE 持有者约 140 万美元、Permit2 合约未被攻破；钱包应同等级告警。
  - Passkey 保护的是登录，不是签名内容（第 7 节）。
- **解读者的判断**（视频的取舍，不是原文）：
  - 钩子问题与结尾答案"花钱的是签名授权的那段代码；谁能让你签下授权，谁就决定了那是什么代码"是解读者的概括。
  - 钩子画面里"code: → 委托"、清零后回到"（空）"是示意；攻击者如何控制签名服务、"50 个连续 nonce 授权"的说法（原文指向 23、29 章）未进入视频。
  - "例：转 1 ETH 给 Bob"、12 枚金币、7 根付账小柱、三条链"链 A/B/C"、五条链"链 B–E"都是示意。
  - 批量执行解码出的三项（调用应用合约、读取余额、把全部代币转给陌生地址）是示意内容，不是某起事件的真实调用。
  - "每笔 0.1 ETH，签 10 笔 1 ETH、100 笔 10 ETH"是解读者构造的示例算式，用来解释原文"累计不是单笔"（Biconomy 审计发现）。
  - Cardex 画面的用户点数量不代表 9,000。
  - 原文的 Coinbase Smart Wallet、Biconomy 审计、Wintermute 统计、CoW Swap 与 1inch Fusion v1 案例、社交恢复、存储冲突、初始化抢跑、授权元组回放（Glamsterdam）、交易所充提兼容等内容未进视频。

## 6. 成立条件、例外和风险

- 金额是事发时美元估值约数；7702 钓鱼的 14.6 万美元由 GoPlus 归因于 Inferno Drainer，8 月两起来自 ScamSniffer 记录。
- chain_id = 0 的授权只在支持 EIP-7702 且该地址 nonce 匹配的链上有效。
- "钱包默认拒绝"指原文建议的防御，不代表所有钱包都已这样实现。
- Session Key 的范围限制只在实现正确时起作用；Cardex 中范围限制保护了 ERC-20 与 NFT，但共用密钥本身是设计错误。
- Permit2 风险的前提是用户曾把代币无限授权给 Permit2；AllowanceTransfer 带额度和过期时间，视频只讲了"无限授权 + 链下签名"这一种情形。
- 清零委托需要一笔新的授权；托管方应把清零流程写成预案并演练（原文 AAW-9），视频未展开。
- Passkey 抵抗钓鱼网站窃取密码，但同步型 Passkey 的安全性取决于云账户恢复流程（原文 3.3 节）。
