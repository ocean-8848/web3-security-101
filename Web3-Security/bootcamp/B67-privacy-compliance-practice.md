## 2. 第 1 步：去匿名化——聚类会冤枉人

[B66](B66-tracing-privacy-practice.md) 第 2 步的每一跳都是确定的。真实追踪常常要靠启发式规则把地址聚成"实体"。规则会出错。

<details class="predict"><summary>🤔 先猜再看：实验默认打开三条规则，窗口 600 秒、容差 10%。精确率会高于 50% 吗？</summary>

不会。默认设置下精确率只有 12.4%，15 个地址全被并成一个簇。CoinJoin、OTC 商和宽松的时间窗口都制造了错误链接。

</details>

打开[链上去匿名化实验](../interactive/deanonymization-lab.html)，按顺序操作，记录每一行：

| # | 设置 | 预期精确率 | 预期召回率 | a1 所在簇的大小 |
|---|---|---|---|---|
| 1 | 默认（三条规则开，600 秒，10%） | 12.4% | 100.0% | 15 |
| 2 | 勾选两条排除规则 | 54.2% | 100.0% | 4 |
| 3 | 再把窗口调到 300 秒、容差 1% | 100.0% | 100.0% | 4 |
| 4 | 窗口调到 100 秒、容差 1% | 100.0% | 92.3% | 4 |

每一行都点"揭示真相"，读"证据清单"里标为"假"的链接。第 1 行的错误来自 CoinJoin（T3）和 OTC 商。第 2 行剩下的错误来自"时间金额"规则：b2 和 f1 被连到 r1。第 4 行窗口太窄，e1 到 r1 的真实关联也丢了。这是精确率和召回率的取舍。

> 💡 注意：启发式结果写进地址清单时，"置信度"一栏写规则名称和参数，例如"时间金额，300 秒 / 1%"。法院采信链上分析时，也有卧底交易等其他证据印证，见 [24 章 5.4 节](../24-data-privacy.md)。

## 3. 第 2 步：数据最小化——哈希不是匿名

某合约为了"隐私"，只存 `keccak256(email)`。你来验证它是否真的隐藏了邮箱。

1. 模拟链上值和攻击者的候选列表：

```bash
ONCHAIN=$(cast keccak "alice@example.com"); echo "链上值: $ONCHAIN"
printf "bob@example.com\ncarol@example.com\nalice@example.com\ndave@example.com\n" > candidates.txt
while read e; do [ "$(cast keccak "$e")" = "$ONCHAIN" ] && echo "命中: $e"; done < candidates.txt
```

```text
链上值: 0x75a90bbc4dd359da9253ea49138b05a4e37a5a4b4c8e4d66e7d39623523073fa
命中: alice@example.com
```

2. 改用加盐承诺。盐（Salt）是每条记录单独生成的 32 字节随机数，存在可删除的链下系统里：

```bash
SALT=0x$(openssl rand -hex 32)
REC=$(cast from-utf8 "alice@example.com")
COMMIT=$(cast keccak $(cast concat-hex $SALT $REC)); echo "承诺: $COMMIT"
while read e; do [ "$(cast keccak "$e")" = "$COMMIT" ] && echo "命中: $e"; done < candidates.txt
```

输出只有一行 `承诺: 0x746a09b6…`，没有"命中"。没有盐，枚举失败。删除盐以后，承诺无法再关联到这个人。

> 💡 注意：加盐承诺是计算隐藏，不是完美隐藏。盐泄露后可以比对。完整的设计模式和 EDPB 段落号见 [24 章 4.5 节](../24-data-privacy.md)。本节是工程练习，不是法律意见。

## 4. 第 3 步：制裁筛查与 Travel Rule 最小演练

1. 建一份玩具名单和提币请求。名单里的地址是你的练习地址，不是真实制裁地址：

```bash
printf "0xed8ff955d9036ddd4ae360d5d7f5c69dcc12bf96\n0x0c19bfc4df302362f227b0470dd13f2d1ff6e48e\n" > blocklist.txt
printf "req-001 0x789AFFB4Cd021b0f45aD8D0689380F53B2399495 3.9\nreq-002 0x0C19Bfc4dF302362f227b0470dd13f2d1fF6e48e 1.0\n" > withdrawals.txt
grep -Ff blocklist.txt withdrawals.txt;  echo "--- 忽略大小写:"; grep -iFf blocklist.txt withdrawals.txt
```

```text
--- 忽略大小写:
req-002 0x0C19Bfc4dF302362f227b0470dd13f2d1fF6e48e 1.0
```

第一次匹配没有命中。名单是小写，请求是 EIP-55 校验和格式（大小写混合）。筛查前必须统一大小写。这类 bug 会让制裁筛查静默失效（CUS-9）。

2. Travel Rule：服务商之间转账时，要传递发起人和受益人信息（[23 章 4.2 节](../23-custody-exchange-ops.md)）。用下表检查 req-001 的报文。欧盟 TFR 下服务商之间转账不设最低门槛，所以 3.9 ETH 也要填。

| 字段 | 发起人 | 受益人 | 你的报文有吗 |
|---|---|---|---|
| 姓名 | 必填 | 必填 | |
| 账户或钱包地址 | 必填 | 必填 | |
| 地址、证件号或出生日期之一（按辖区） | 按辖区 | — | |
| 对方服务商身份 | — | 必填 | |

> 💡 注意：各辖区的字段要求不同。上表是练习骨架，上线前以法务确认的规则为准。
