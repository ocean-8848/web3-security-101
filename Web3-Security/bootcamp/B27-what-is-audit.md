## 开场：报告说"没有问题"，为什么协议还是被攻击了

示例场景：一个协议公布了审计报告，一周后资金被盗。社区质问审计公司。审计公司指出：被盗的合约是上线前新加的，不在审计范围内。

这个场景告诉我们两件事。审计有范围。审计不是保险。

前面的阶段里，你一个人读代码、写 PoC、写报告。本章讲读代码之外的部分：审计方怎样接项目、定范围、排期，团队怎样评审和定级，修复以后怎样复查和交付。

<details class="predict"><summary>🤔 先猜再看：审计报告里写的"提交哈希"，主要是给谁看的？</summary>

给所有依赖这份报告的人看。它把"审过的代码"钉死在一个版本上。上线代码和这个版本不同，报告对差异部分就没有结论。

</details>

> 🎯 打个比方：审计像体检。体检报告说明这次检查发现了什么。它不是保证你明年不生病，也不包括没做的检查项目。
>
> 比喻的局限：人体的规则不会被对手故意利用。合约的每一个角落都有对手主动寻找弱点。

## 1. 审计是什么，不是什么

审计的定义和最小流程见 [B09 第 1 节](B09-reading-code-mindset.md)。专业审计还要回答：它承诺什么，不承诺什么。

| 审计是 | 审计不是 |
|---|---|
| 限时的、尽力而为的专业审查 | "这个合约安全"的保证 |
| 针对特定提交哈希 | 对后续所有版本有效 |
| 帮助开发者修复问题 | 替代测试、监控和应急预案 |
| 一个安全阶段 | 上线前的唯一一步 |

审计方法论的作用只有一句话：**让你在疲劳、时间紧、代码陌生的情况下，仍然不漏掉重要的地方。**

### 1.1 审计生命周期

```mermaid
flowchart LR
  A["准备<br/>测试·文档·冻结代码"] --> B["受理与范围<br/>提交哈希·行数·报价"]
  B --> K["启动会<br/>信任假设·通信渠道"]
  K --> C["侦察<br/>编译·测试·工具扫描·建模"]
  C --> M["人工审计<br/>多轮多视角"]
  M --> V["验证<br/>写 PoC"]
  V -->|"疑点被否定 / 新线索"| M
  V --> R["内部评审<br/>定级·去重·复核"]
  R --> D["初版报告"]
  D --> E["项目方修复"]
  E --> F["修复复查"]
  F -->|"修复引入新问题"| E
  F --> G["终版报告·公开"]
  G --> H["上线后<br/>监控·赏金·应急"]
  H -.代码变更.-> A
```

**读图要点：**

- 审计从"准备"开始，不从"读代码"开始。范围要锁定提交哈希。
- "人工审计 ↔ 验证"是一个循环。好的审计员会多轮往返，而不是一次读完。
- "修复复查"不可省略。它是独立的一轮审计，修复代码与原代码一样需要逐行检查。
- 虚线表示：代码一变更，安全结论就要重新评估。
- 局限：竞赛审计的流程不同，是多人并行提交，详见 [B53](B53-contests-and-habits.md)。

侦察和人工审计的做法见 [B09](B09-reading-code-mindset.md)，写 PoC 和发现见 [B14](B14-writing-findings.md)。本章第 2–4 节讲审计开始前的准备、范围和排期，第 5–8 节讲内部评审、沟通、修复复查和方法论。

## 2. 审计准备度：Rekt Test

Rekt Test 是 Trail of Bits 的 Dan Guido 牵头的安全团队工作组在 2023 年发布的 12 个是/否问题。它参考了软件团队的 Joel Test。下面是中文转述，原文见 [Trail of Bits 博客](https://blog.trailofbits.com/2023/08/14/can-you-pass-the-rekt-test/)。

| # | 问题 |
|---|---|
| 1 | 所有参与者、角色和权限都写成文档了吗？ |
| 2 | 依赖的外部服务、合约、预言机都有文档吗？ |
| 3 | 有书面并演练过的应急响应计划吗？ |
| 4 | 文档记录了攻击你系统的最佳方式吗？ |
| 5 | 对全部员工做身份核验和背景调查吗？ |
| 6 | 有成员的职责中明确包含安全吗？ |
| 7 | 生产系统要求使用硬件安全密钥吗？ |
| 8 | 密钥管理要求多人和物理步骤吗？ |
| 9 | 定义了关键不变量，并在每次提交时测试吗？ |
| 10 | 使用最好的自动化工具发现安全问题吗？ |
| 11 | 接受外部审计，并有漏洞披露或赏金计划吗？ |
| 12 | 考虑并缓解了系统对用户的滥用途径吗？ |

Rekt Test 的回答要有证据支持。它是自评工具，不是认证。作者也说明它不能防止所有攻击。

没有规格的合约无法判断"对不对"，审计员只能判断"看起来怪不怪"。

### 2.1 受理（Intake）：审计方决定接不接

Rekt Test 是项目方的自评。受理（Intake）是审计方的判断：签约前收集资料，判断这次审计能否按质量完成。受理资料用 [T01 受理清单](../templates/T01-intake-checklist.md) 记录。

| 检查项 | 通过标准 | 不通过时 |
|---|---|---|
| 代码冻结 | 客户给出固定提交哈希 | 推迟开工日期 |
| 能否编译 | 按 README 能在干净环境中 `forge build` | 客户先修复构建 |
| 测试 | `forge test` 能运行，并给出覆盖率 | 报告中记录，工期加入建测试的时间 |
| 文档 | 有架构说明、角色说明、预期不变量 | 增加启动会时长，并记录假设 |
| 已知问题 | 列出已知问题和风险接受项 | 启动会上逐条确认 |
| 部署信息 | 目标链、部署脚本、初始参数、权限持有人 | 把部署审查列为待确认项 |
| 利益冲突 | 团队与客户无持币、投资或竞争关系 | 回避或书面披露 |

> ⚠️ 警告：如果客户要求承诺"审计后不会被攻击"，拒绝这个条款。审计结论只覆盖指定提交、指定范围和指定时间。

## 3. 确定范围

### 3.1 锁定版本

本章的练习对象仍是 LunchPool。如果你在 [B09](B09-reading-code-mindset.md) 建过工作副本，直接在副本里运行 `git rev-parse HEAD`。否则，创建一份带 git 的副本，得到提交哈希：

```bash
cd practice-example-code/range/basics  # 从 web3-security-handbook/ 出发，进入配套工程
# 清掉旧副本，新建空目录
rm -rf /tmp/lunchpool-audit && mkdir /tmp/lunchpool-audit
cp -R src/b05 docs /tmp/lunchpool-audit/  # 复制合约源码和规格文档
cd /tmp/lunchpool-audit  # 进入副本目录
# -q 静默；建仓库并提交一次
git init -q && git add . && git commit -q -m "lunchpool audit target"
git rev-parse HEAD  # 打印这次提交的完整哈希
```

本手册的一次运行得到（示例，你的哈希不同）：

```text
37dba9ccb5d62067054b2d327d04bd9d164db676
```

把这个哈希写进工作说明。之后回到配套工程：

```bash
cd -  # 回到上一个所在目录
```

<details class="predict"><summary>🤔 先猜再看：一次 2 周的审计进行到第 9 天，客户说"只改了一行，顺便看一下"。这一行改了清算奖励的计算。你应该直接把它并入当前审计吗？</summary>

不应该直接并入。范围由提交哈希定义。你先读差异，判断它影响哪些入口和不变量，再和客户书面确认：纳入范围并调整工期，或者放到修复复查。报告要写明最终审计的提交哈希。

</details>

### 3.2 统计代码量

cloc 统计代码行数。安装方法：`brew install cloc`。也可以用 npx 免安装：

```bash
npx -y cloc src/b05  # npx -y：临时下载并运行，不用安装
```

实际输出：

```text
-------------------------------------------------------------------------------
Language                     files          blank        comment           code
-------------------------------------------------------------------------------
Solidity                         1             10              3             62
-------------------------------------------------------------------------------
```

（cloc 2.10，通过 npm 包运行。）

nSLOC 只统计源代码行，不统计注释和空行。下面用 `solidity-code-metrics` 工具（Solidity Metrics 的命令行引擎，版本 0.0.28）：

```bash
# 生成度量报告，存到 metrics.md
npx -y solidity-code-metrics src/b05/LunchPool.sol > metrics.md
grep 'LunchPool.sol' metrics.md | head -1  # 只看 LunchPool 那一行
rm metrics.md  # 删除临时报告
```

实际输出（只显示第一行）：

```text
| 📝 | src/b05/LunchPool.sol | 1 | **** | 75 | 75 | 62 | 3 | 47 | **<abbr title='Payable Functions'>💰</abbr>** |
```

字段依次是：类型、文件、逻辑合约数、接口数、总行数、nLines、**nSLOC（62）**、注释行、**复杂度分（47）**、能力标记。VS Code 用户可以安装 Solidity Metrics 扩展得到同样的图形报告。

### 3.3 估算工期

业界没有统一的速度标准。示例速度见 [A01 第 5.1 节](../assessment/A01-methodology.md) 的表，不是报价依据。本节用那张表练习计算。

计算步骤（示例）：

1. LunchPool 的 nSLOC 是 62，复杂度按"低"（简单金库）。
2. 按 A01 表中"低"的 400 nSLOC/人日，读码需要约 0.16 人日。
3. 按 A01 的规则加 30% 用于报告与复核，约 0.2 人日。
4. 小项目还有启动会、写 PoC 和排版的固定开销。本手册示例按半天计，合计约 0.7 人日。

调整项：外部依赖多，时间增加；测试和文档差，时间增加；新的数学模型，时间增加。

大项目的总工期再按阶段分配。下面是一个 2 周、3,000 行项目的示例：

| 阶段 | 占比 |
|---|---|
| 侦察与建模 | 15% |
| 人工审计四轮 | 50% |
| 验证与 PoC | 15% |
| 报告与内部评审 | 15% |
| 缓冲 | 5% |

### 3.4 范围表（Scoping）

范围表写进合同附件。每一行都能被第三方核对。

| 字段 | 示例 |
|---|---|
| 仓库与提交哈希 | `org/protocol@a1b2c3d`（示例） |
| 范围内文件 | `src/core/*.sol`，共 3,000 行（示例） |
| 范围外但有依赖 | 数学库、预言机适配器、编译器版本 |
| 目标链 | 以太坊主网、Arbitrum |
| 信任假设 | 管理员是 4/7 多签加 48 小时时间锁（示例） |
| 明确排除 | 前端、链下 Keeper、治理代币经济 |

范围外的依赖要显式决策。2025 年 5 月 Cetus 事故的漏洞位于开源数学库，不在其业务合约（[The Block](https://www.theblock.co/post/355795/sui-dex-cetus-open-source-library-flaw-smart-contract-223-million-usd-exploit)）。外部审计的范围设计见 [A07](../assessment/A07-external-audit-bounty.md)，Cetus 的详细机制见 [B51](B51-move-audit.md)（阶段 7）。

## 4. 启动与排期

### 4.1 日历（示例：2 周、2 名审计员）

| 日期 | 动作 | 产出 |
|---|---|---|
| D0 | 启动会；确认范围和通信渠道 | 启动纪要、信任假设 |
| D1 | 编译、跑测试、覆盖率、工具扫描 | 工具基线、噪声清单 |
| D2 | 建模：资产、角色、入口、不变量 | 建模底稿（模板见阶段 5 的 [B35](B35-case-method.md)） |
| D3–D6 | 第 1、2 轮人工审计（四轮视角见 [B09 第 3.3 节](B09-reading-code-mindset.md)） | 疑点清单 |
| D7 | 交叉换手：两人互换模块 | 新疑点 |
| D8–D9 | 第 3、4 轮；写 PoC | PoC、发现草稿 |
| D10 | 内部评审与定级会 | 定级结论 |
| D11 | 交付初版报告；讲解会 | 初版报告 |
| 修复期 | 客户修复（通常另约时间） | 修复提交列表 |
| 修复复查 | 逐条复查、看差异 | 终版报告 |

### 4.2 角色

| 角色 | 职责 | 不做什么 |
|---|---|---|
| 项目负责人（Lead） | 定范围、排工、对客户负责、主持定级 | 不独占所有高危模块 |
| 审计员 A / B | 按模块审计，写 PoC 和发现 | 不单独决定最终等级 |
| 复核员（Reviewer） | 读全部发现，抽查未覆盖区域 | 不修改原始证据 |
| 客户技术联系人 | 回答设计问题，提供修复 | 不决定等级 |

> 💡 注意：如果团队只有一个人，把"复核"安排在隔天。隔天复核仍弱于第二个人复核，报告要说明人员配置。

### 4.3 工具安排

工具运行放在 D1。工具结果进入疑点清单，不直接进入报告。

| 时机 | 工具 | 用途 |
|---|---|---|
| D1 | `forge test`、`forge coverage` | 建立基线 |
| D1 | Slither、Aderyn、Semgrep | 模式扫描，人工标注真假 |
| D2–D9 | Foundry 不变量、Echidna 或 Medusa | 验证不变量 |
| D8–D9 | Foundry fork | 写 PoC |
| 按需 | Halmos、Certora Prover | 证明小范围的关键性质 |

工具的具体写法和版本见本阶段的 [B31](B31-automation-tools.md)。AI 工具的使用边界见 [B52](B52-ai-assisted-audit.md)（阶段 7）。

## 5. 内部评审与定级会

找到问题、写好 PoC 之后，发现还不能直接交给客户。它要先经过团队内部的两道关。

### 5.1 内部评审

内部评审在初版报告前至少完成一次。复核员逐条回答 4 个问题：

1. 这个发现能复现吗？PoC 在锁定的提交上运行吗？
2. 根因写对了吗？修复建议修的是根因吗？
3. 有没有重复项？同一根因的多个发现要合并。
4. 哪些模块没有发现？没有发现是因为安全，还是因为没看？

### 5.2 定级会

定级会只讨论证据。主持人按影响和可能性矩阵走。矩阵见 [A02 第 2 节](../assessment/A02-risk-rating-reporting.md)，用法见 [B14 第 3 节](B14-writing-findings.md)。

```mermaid
flowchart LR
  P["发现草稿与 PoC"] --> I["确定影响<br/>谁损失什么"]
  I --> L["确定可能性<br/>前提条件"]
  L --> M["查矩阵"]
  M --> A["调整<br/>时间锁、限额、密钥风险"]
  A --> R["写明定级理由"]
```

**读图要点：**

- 输入是 PoC，输出是一段可被客户复核的定级理由。
- 调整项要写明依据。"客户说不重要"不是依据。
- 局限：矩阵不能替代判断。分歧无法收敛时，记录两种意见，由负责人决定。

> 🧪 动手验证：打开[风险评级计算器](../interactive/severity-calculator.html)，选择同一个影响和可能性，分别勾选"已有有效的独立缓解"和"特权角色的密钥/运营安全薄弱"。记录等级变化，并写一句理由。

<details class="predict"><summary>🤔 先猜再看：一个发现只有管理员能触发。它一定是 Low 吗？</summary>

不一定。定级要看管理员的实际控制：门限、时间锁、权限范围、密钥运营。如果管理员是 2/5 多签且没有时间锁，并能转走全部资产，这个风险的可能性不能按"几乎不会发生"计算。见 [13 章 5.5.2 节](../13-non-evm-ecosystems.md) 的 Drift 案例。

</details>

## 6. 沟通规则

| 事项 | 规则 |
|---|---|
| 渠道 | 只用启动会确认的加密渠道。发现细节不进公共群组 |
| 频率 | 每 2–3 天发一次进度：已覆盖、未覆盖、阻塞项 |
| Critical | 证实后当天通知客户负责人，不等报告 |
| 已上线代码 | 如果漏洞影响已部署合约，立即进入 [A09](../assessment/A09-incident-response.md) 应急流程 |
| 范围变更 | 审计中途的新提交，先读差异，再书面确认纳入范围或放到修复复查 |
| 设计问题 | 记录问题、回答、回答人。把回答写进信任假设 |
| 报告发布 | 只有客户书面同意后才公开 |
| 客户分歧 | 保留原等级和客户回应，两者都写进报告 |

报告条目按 [T03 报告模板](../templates/T03-finding-report.md) 记录。

## 7. 修复复查与终版报告

修复复查（Fix Review）的对象是修复提交与原提交的全部差异，不只是客户标注的行。按 [A08 第 4 节](../assessment/A08-reproduce-attacks.md) 的 7 个步骤做。要点：

- 读全部差异，把每处差异对应到一条发现。无法对应的差异单独审计。
- 用原 PoC 验证：修复前攻击成功，修复后攻击失败。
- 运行全部测试和不变量，并检查修复是否引入新的入口、状态或权限。
- 给每条发现标记状态。状态用 [T03](../templates/T03-finding-report.md) 的五个词：未处理、已修复、部分修复、已接受风险、无法复现。

LunchPool 的 `test_Fix_*` 测试就是"用原 PoC 验证"的最小例子：同一组 PoC 在修复版上必须失败。

> ⚠️ 警告：终版报告的提交哈希必须等于部署的代码。部署后要比对链上字节码，见 [T04 上线门禁](../templates/T04-go-live-gate.md)。

## 8. 建立自己的方法论

流程是团队的。检查清单要你自己一点点长出来。

- **审计方法论**：你的检查清单、你的建模模板、你的疑点记录格式。
- **安全实践方法论**：给项目方的开发规范建议（测试、部署、权限、监控）。
- **做事方法论**：先建模再找漏洞；先证明再定级；先写清楚再提交。
- **思维体系**：每次审计后复盘"漏掉了什么、为什么漏掉"，把答案写进清单。

> 🎯 打个比方：一次审计像一次飞行。检查单、机组分工和塔台通话都是固定的。飞行员不靠记忆起飞。
>
> 比喻的局限：飞机的状态可以用仪表读出。代码的"正确"没有仪表，需要审计员先写出不变量。

审计为什么会漏报，见本阶段的 [B29](B29-why-audits-miss.md)。建模底稿的模板见 [B35](B35-case-method.md)（阶段 5）。个人方法文档怎样写，见 [B54](B54-expert.md)（阶段 7）。

## 13. 思考题

1. 审计完成后，项目方"只改了一个常量"就上线。审计结论还有效吗？你会怎么处理？
2. 同样 62 行 nSLOC，一个是单纯的代币，一个是自定义 AMM 曲线。工期应该相同吗？
3. 用第 4.1 节的日历，把 4 周、6,000 行、3 名审计员的项目重新排期。哪些阶段不能按人数线性压缩？
4. 客户在修复时重构了一个模块，声称"逻辑没变"。按第 7 节，你怎样处理？
5. 在[风险评级计算器](../interactive/severity-calculator.html)中，选择影响最高的一档和可能性较低的一档。勾选"特权角色的密钥/运营安全薄弱"后，等级怎样变化？你会在报告里写什么理由？
